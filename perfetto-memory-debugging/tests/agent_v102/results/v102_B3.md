# B3 — 证据边界与因果：C1（counters+sched）与 C2（heapprofd）能否证明"分配导致 CPU 抖动"

> 前置声明：本次没有连接设备、没有执行任何采集/分析命令、没有拿到你的两份 trace 原始数据。
> 下面是对**判读规则**与**预期现象**的评估，不是实测结论；凡涉及"你的 trace 里是什么"的地方，
> 都写成需要你在 UI/SQL 里核对的条件。`{{SKILL_DIR}}` = `candidate-v1.0.2`。

## 0. 结论速览

| # | 用户的说法 | 判定 | 一句话理由 |
|---|---|---|---|
| 1 | 把 C1 里的绝对时间戳直接填到 C2 的 SQL 里，就能把分配和 CPU 对齐 | **不接受（FAIL）** | 两份独立 trace 各自有独立时钟域与 `trace_bounds`；本包 SQL 的 `start_ts/end_ts` 语义是"被查询 trace 自己的纳秒时间"，填外来值只会静默 0 行或截断前缀基线；即使时钟可对齐，能得到的也只是"dump 窗口级共现"，不是逐点对齐 |
| 2 | heapprofd dump 的时间就是每次 malloc 的时间 | **不接受（FAIL）** | dump 是**窗口快照**：`window_end` 只随"带非零 timestamp 的分配"推进（free 以 `timestamp=0` 提交），分析器还按 `(upid, window_end, heap_name)` 去重；旧采集端不发 `start_timestamp` 时 `dur=0`、窗口本身不可知。它给不出单次 malloc 的时刻 |
| 3 | count 高说明调用次数多 | **限定后可作弱证据**（精确值 UNKNOWN） | `count/size` 是随机字节采样后的**估计**，有方差；可以支撑"分配活跃"，不能支撑"调用次数 = N 次"或"N 倍"，更不能单独推出 CPU 开销 |
| 4 | profiler 已经采集成功，所以可以确认是分配导致 CPU 抖动 | **不接受（FAIL）**；因果结论当前 **UNKNOWN** | 采集成功最多落在四级验收的 1~3 层（schema/运行条件/有数据），第 4 层"分析正确"不含因果；因果至少需要时间先后、剂量关系、机制证据、对照/可干预性中的多项，且业务延迟要有独立打点 |

**一句话总结**：C1 证明"目标进程在那段时间烧了多少 CPU"，C2 证明"那段时间前后，采样到的分配归因在哪条栈、保留量量级如何"。二者**各自都成立也不能相加成因果**，而且当前这两份独立采集连"同一时间窗"都还不能合法建立。

## 1. 定位路线：问题被混成了两层

用户实际上把三个不同的问题串成了一条未经检验的推理链：

| 层次 | 问题 | 需要的数据 | 当前状态 |
|---|---|---|---|
| A. 描述（占用/调度） | 目标进程是否真的周期性上升 CPU？哪个线程？on-cpu 还是 runnable？ | counters + `sched_switch`（C1） | 可判（需要 SQL 量化，不能肉眼） |
| B. 描述（分配归因） | 这段时间采样到的分配落在哪条栈、live/total 估计多少？ | heapprofd（C2） | 可判，但只到**dump 窗口**粒度，且是估计值 |
| C. 因果 | 分配**导致**了 CPU 抖动（进而导致卡顿？） | 同一时间轴上的机制证据 + 剂量 + 对照 + 业务延迟打点 | **当前证据不足（UNKNOWN）** |

需要显式区分的"不覆盖"：

- 不覆盖**每次 malloc 的时刻与耗时**：heapprofd 是"分配调用栈归因器"，不是 `malloc` 延迟分析器（候选包 `references/07-internals-and-pprof.md`）。
- 不覆盖**业务延迟/掉帧**：C1 里的 CPU/runnable 是系统状态，不是业务延迟（`references/06-quality.md` 第 0 节明确禁止用系统 runnable 状态冒充业务延迟）。
- 不覆盖**RSS 与 heap 的等价性**：`live` 估计 ≠ RSS ≠ PSS。
- 不覆盖**跨 trace 的绝对时间**，除非举证（见 §2.1）。

待验证假设（建议按这个顺序挂到下次采集上）：

- H1：目标进程的 CPU 上升是**单线程/少数线程 on-cpu 时间**的周期抬升，而不是轮询网格或整机负载抬升造成的视觉锯齿。
- H2：CPU 抬升窗口内，被采到的分配在同一 trace 的同一时间窗内显著高于基线，并且归因到与 H1 相同的线程/调用路径。
- H3：改变该分配路径的量（剂量/干预）会让 CPU 锯齿的幅度随之变化/消失，且业务打点同步改善。

只有 H1→H2→H3 都拿到证据，才能说"分配导致 CPU 抖动"；目前连 H1 都还是"用户看着像"。

## 2. 逐条评估

### 2.1 说法一：把 C1 的绝对时间戳填进 C2 的 SQL 就能对齐 —— 不接受

**三个独立层面都不成立，任一层都足以否掉这个做法。**

**(a) 时钟域层面。**
Perfetto 的 `ts` 是纳秒整数，但它是**每条 trace 自己的时间轴**：采集端记录 `clock_snapshot`，分析器（trace_processor）把它归一到 trace 内部可比较的时间基（默认 BOOTTIME 语义）。C1、C2 是两次独立会话，各自有不同的会话起点、buffer 轮转与 `trace_bounds`。

需要修正一个容易说过头的点：**"物理上绝对不可能"是不严谨的**——同一台设备、同一次 boot 的 `CLOCK_BOOTTIME` 在原理上共原点，所以不能说两份 trace 的时间戳一定无法比较。但本包的口径是**举证责任在提出对齐的人**（`references/06-quality.md` 第 0 节）：

> 不同 trace 的绝对时间戳只有在有明确时钟对齐依据（共享时钟 / 同时采集 / 共同标记并验证）时才可混用；否则只能使用该 trace 自己的相对窗口，或比较模式而不是逐点对齐。

要"直接填"至少得先把这四件事做完并留证，缺一件就只能是 UNKNOWN：

1. 两次采集**同一次 boot**（`/proc/sys/kernel/random/boot_id` 一致；重启过就自动不成立）；
2. 两份 trace 的 `clock_snapshot` 都含同一个可用时钟（同一 `clock_id`），并记录 trace_processor 实际使用的 timebase；
3. 在两次采集里各写一条**可识别的共同标记**（`trace_marker`/atrace），且至少两条标记 + 一段空闲窗，验证推算出的偏移在整段窗口内稳定；
4. 把偏移、验证标记、窗口写进记录，而不是把某个魔数硬编码进 SQL 注释里。

跨设备（比如 C1 在板端、C2 在另一台机器）或中间重启过，上面第 1 条直接不成立。

**(b) 语义层面：对齐的粒度根本不是"点"。**
C2 里 `heap_profile_allocation` 的每一行都挂在**某个 dump 的时间戳**上，同一 dump 的多行共享一个 `ts`。所以"把 C1 的 ts 填进去"并不会产生任何新的时间信息：真实发生的只是"某个 dump 窗口是否落在这个时间窗口内"这种**包含关系判断**，粒度 ≥ `dump_interval_ms`（模板默认 5000 ms）。用它去分辨"每隔几秒"的 CPU 锯齿相位，属于用观测网格解释观测网格（见 §2.2 第 3 点）。

**(c) 工程实现层面：SQL 参数有明确契约，填错是静默错误。**
本包 SQL 的参数全部按"**被查询 trace 自己的** UPID 与纳秒时间"设计，把 C1 的值填进 C2 会以两种方式安静地给出错误结果：

- `sql/03-native-live.sql`：窗口过滤发生在**前缀和之后**（文件末尾注释：`Prefix sum occurs BEFORE display-window filtering: earlier baseline is kept`）。用外来 `start_ts` 会把窗口之前的基线截掉，输出变成"区间净变化"，而不是"窗口结束时的 live 估计"——这正是 `tests/scenarios.md` A15 判不合格的那类口径错误。
- `sql/11-cpu-time-buckets.sql` / `sql/12-cpu-spike-episodes.sql`：`start_ts/end_ts = -1` 的语义是"取本 trace 的 `trace_bounds`"。填一个超出本 trace 边界的值时，递归桶数会算成 0 或只覆盖半截，结果是**空结果或半桶**；而 `target_upid = -1` 时"返回 0 行不代表没有分配"（`sql/03`、`sql/04` 头部注释都写了这一条）。把"查不到"读成"没有分配/没有开销"，是本场景最典型的错误。

**可接受的替代做法（按优先级）：**

1. **同一 trace 内比较**（`references/06-quality.md`：跨 trace 的 CPU/分配关联，优先在同一 trace 内比较）→ 见 §4，这是最小代价的正解。
2. **跨 trace 只比"模式"**：比周期长短、比幅度相对变化、比"峰值是否落在同一业务阶段"，不逐点对齐，不把两边的绝对 ts 混算。
3. 若业务上硬要逐点：先按 (a) 举证对齐，再只用**窗口级**结论，并写明偏移依据与不确定性。

### 2.2 说法二：heapprofd dump 的时间就是每次 malloc 的时间 —— 不接受

这是三条**采集器/分析器行为**决定的，不是"分析器可选开关"（`references/02-native.md` 的"dump 可见性、去重与旧采集端元数据"）：

1. **dump 窗口只随分配推进。** 每份 dump 的 `window_end` 取 `HeapTracker::committed_timestamp_`，该值只在提交**带非零 timestamp 的分配**时更新；`free` 以 `timestamp=0` 提交。也就是说，进程只是持有、不新分配时，所有周期 dump 的 `window_end` 相同——"dump 一直在出"不等于"窗口在前进"。
2. **分析器按 `(upid, window_end, heap_name)` 去重。** 同一键只保留一行 `heap_profile`。所以配置里的 `dump_interval_ms` **不等于可见 dump 数**；触发次数是 `floor((运行时长-phase)/interval)+1`，可见行数还要求每次窗口都有前进。
3. **旧采集端不提供窗口起点。** `start_timestamp` 标注 *Unset on older producers*；缺失时 `ts == ts_end`，`heap_profile.dur = 0`，**窗口区间不可知**（候选包记录的组合是：X5 tracebox v57.1 采集 + v58.2 分析器 → 6 份 dump、`dur` 全 0。你的组合是否也是这一种，需要先用 `sql/10-native-dump-capability.sql` 判定，不要假设）。

再叠加一条采样口径：`heap_profile_allocation` 是"按 dump 聚合的增量/净变化"，不是逐事件日志；`count/size` 是采样估计。所以：

- **能回答**："这 5 秒里，采样到的分配主要集中在哪条调用栈、保留量估计多少、哪一次 dump 前后在涨。"
- **不能回答**："CPU 峰值那一刻正在 malloc 什么"、"每次 malloc 发生在哪个纳秒"、"这次分配花了多久"。
- 三态：**单次 malloc 的精确时刻 = UNKNOWN**（不是 FAIL——这是数据源设计如此，不是采集坏了）。

顺带否掉一个看似聪明的变体：既然 dump 密集可以"导出"更细时间线——不行。`dump_interval_ms` 变小只改变快照密度，仍然给不出事件时刻，反而增加开销与 shmem/队列压力（`references/07-internals-and-pprof.md`）。

### 2.3 说法三：count 高说明调用次数多 —— 方向可用，精确说法不接受

拆成两个可判项：

| 说法 | 判定 | 依据 |
|---|---|---|
| "采样到的分配估计较高 → 该时间段分配活动活跃" | **可接受（弱证据）** | `Total Malloc Size/Count` 就是"分配流量"的估计；`Unreleased` 系列是"保留量"的估计 |
| "count 高 = 调用次数多（可当计数用）" | **不接受；精确次数 UNKNOWN** | 见下 |

理由：

1. **它是估计，不是计数日志。** `sampling_interval_bytes`（模板 4096）是按字节流稀疏随机采样的**平均**参数，不是"每 4096 字节固定打点"，也不是"每次 malloc 都记录"。估计量有方差，小分配热点尤其明显；同一 workload 重复多次才能谈"稳定"（`references/02-native.md`、`references/07-internals-and-pprof.md`）。已经出现在分析表里的 `count/size` **不要**再按采样间隔放大。
2. **口径要先分清。** `Total Malloc Count` 是追踪范围内累计分配次数的估计；`Unreleased Malloc Count` 是尚未配对释放的保留估计。把后者读成"调用频率"是常见误读；"live 估计较高"也可能来自长期缓存/池，而不是高频分配。
3. **大分配快路径与版本相关。** 不能拿旧 design doc 的阈值推当前采集器的行为；数学细节要以目标版本 proto/实现为准。
4. **即使次数确实多，也推不出 CPU 开销。** `references/00-routing.md` 与 `02-native.md` 都写了：高 Total 只说明分配活跃，**不独自证明**锁竞争、CPU 开销或掉帧。要谈 CPU，必须有机制证据（见 §2.4）。

补充一个会让"count 高"失真的坑：如果 C2 里目标进程有多条同名记录（preload 会 fork 一个继承 cmdline 的 heapprofd 子进程），或目标进程的多个 heap（`libc.malloc` 之外的自定义 heap），不先按 UPID+heap 过滤就聚合，会把别人的量算到目标头上（`sql/00-inventory.sql` 的 `[CANDIDATES]` 就是为此设计的，`ambiguous=1` 时必须报"未解析"而不是静默取第一行）。

### 2.4 说法四：profiler 采集成功 ⇒ 确认分配导致 CPU 抖动 —— 不接受

**"采集成功"这个事实能撑到哪一层**（`references/06-quality.md` 四级验收）：

| 级别 | C2 采集成功证明了什么 | 是否被证明 |
|---|---|---|
| 1. Schema | 配置与采集器对应的 TraceConfig proto 解析通过 | 是（若采集器接受了配置） |
| 2. 运行条件 | heapprofd 数据源/Daemon/权限/preload 就位 | 是（若确实出了数据） |
| 3. 数据 | 有目标 UPID 的分配行、非空、无明显丢数据 | 需按 §3 核对，不能默认 |
| 4. 分析/UI | 口径、UPID、窗口、单位、图形一致 | 需按 §3 核对 |
| 因果 | 分配 → CPU → 卡顿 | **不在四级验收里**，且明确由 `06-quality` 第 0 节排除 |

原话是："profiler 采集成功最多证明 schema/运行条件/有数据，**不能单独证明性能因果**。因果至少需要时间先后、剂量关系、机制证据、对照/可干预性中的多项，且业务延迟应有独立日志/打点/trace_marker 证据。"

**现在这条链缺哪几块（逐项点名）：**

1. **缺时间先后（同轴）**：两份 trace 还没有合法同轴（§2.1）。当前最多是"各自看起来都异常"。
2. **缺机制**：不知道 CPU 峰值时消耗在哪个线程、哪个函数。`sched_slice` 能给"哪个线程 on-cpu 多少 ms"，给不了"在 malloc 还是别的地方"。而 heapprofd 本身**不是** malloc 延迟分析器（`references/07`）。要机制，通常需要 CPU profile（perf 采样调用栈）或明确的阶段打点。
3. **缺剂量关系**：没试过"把该分配路径的量改一档，看 CPU 锯齿是否跟着变"。剂量关系是比"同窗出现"强得多的证据。
4. **缺对照**：C2 是带 profiler 的（Linux 上目标必须在**启动时** `LD_PRELOAD`，还可能开了 `PERFETTO_HEAPPROFD_BLOCKING_INIT=1`），C1 是不带的。两条采集的**执行条件不同**，CPU 不能直接互比。采集本身有开销（preload 客户端 shmem 映射、拷栈、同步通信；unwind 在 daemon 侧，但客户端不是零成本）——`references/02-native.md`、`07-internals-and-pprof.md` 都强调"设计收益是减少目标内工作，不是对目标完全没有影响"。
5. **缺业务时间线**：C1 说"CPU 上升"、用户说"抖动"，但没有帧号/帧间隔/阶段标记。系统 CPU/runnable 高不等于业务掉帧（`06-quality` 第 0 节）。
6. **缺"第三因"排除**：周期性锯齿完全可能是**一个周期性任务既分配又烧 CPU**（比如相机帧任务每帧新建 buffer），那么分配是"伴随现象"，不是"原因"；也可能两者都由同一个外部事件驱动。仅凭共现无法区分"分配 → CPU"与"周期性事件 → (分配, CPU)"。

**特别要防的一个混淆：观测网格伪周期。**
C1 若用 `proc_stats_poll_ms = 1000` 读 CPU，而实际负载的周期与 1 s 不成整数倍，"每隔几秒上升"完全可能是**采样混叠（aliasing）**的产物；C2 的 `dump_interval_ms`（默认 5000）则由**会话开始时计时**，与业务相位无关。因此"CPU 锯齿周期 ≈ dump 周期"不但不能当证据，反而应该先怀疑是观测网格。**正确做法**：用 `sched_switch` 派生的 `sched_slice` 做 100 ms 桶（`sql/11`）把真实 on-cpu 时间量化，不要用 1 s 轮询点的形状说话。

结论：说法四不是"因果成立"，而是"**因果 UNKNOWN**，且当前证据方向不足以支持它"。要判 FAIL 也说得通——它把一个不在验收范围内的结论当成了验收产物。

## 3. 不采新数据也能做的复核（10 分钟，全部在 UI Query 里）

这些检查能决定后面是"补采一份合并 trace"还是"直接重抓"，也可能直接推翻用户的读法。按顺序做：

| # | 检查 | 用什么 | 怎么判（三态口径） |
|---|---|---|---|
| 1 | 两份 trace 的覆盖与边界 | `sql/00-inventory.sql` 的 `trace_bounds`；`stats` 非零行 | 复现阶段被 buffer 轮转截掉 / `trace_bounds` 不覆盖峰值 → 结论只能限窗；`stats` 有 heap/ftrace 相关非零错误 → 先按 `06-quality` §3 分流 |
| 2 | C1 的目标 UPID 唯一 | `sql/00-inventory.sql` `[CANDIDATES]`（`target_name` 换成实际名） | `ambiguous=1` 或 `data_bearing` 不唯一 → 报"未解析"，**不静默取第一行**；preload 子进程 `data_bearing=0` 是常态 |
| 3 | C2 的目标 UPID 也是同一个实例 | 同上，在 C2 里再跑一次；对 `pid/start_ts/end_ts` | PID 复用/重启/同名不同实例 → 判定"两次不是同一对象"，后续只能比模式 |
| 4 | C2 的 dump 可见性 | `sql/10-native-dump-capability.sql` `[1]` 表能力 + `[3]` 汇总（无 `heap_profile` 表时用 `[4]` 降级） | `dumps` 远少于预期且 `zero_dur_dumps = dumps` → 属于"窗口不前进/旧采集端无 `start_timestamp`"，**窗口区间 = UNKNOWN**；但总量、分配/释放、符号仍可判。不要据此否定采集 |
| 5 | 量化 CPU 周期（别看形状） | `sql/11-cpu-time-buckets.sql`：`target_upid`=<C1 的 UPID>，`start_ts=-1`、`end_ts=-1`、`bucket_ns=100000000` | 得到 per-thread `cpu_ms` 序列；看是否单线程、周期多长、峰值多高。默认参数下不填 UPID 会返回 0 行——0 行不是"没 CPU" |
| 6 | 把"锯齿"变成 episode 证据 | `sql/12-cpu-spike-episodes.sql`：`bucket_ns=1000000000`、`threshold_ms` 按目标核数/基线设（默认 100.0，先看 `sql/11` 的实际量级再定） | 输出 `ts/dur/peak_cpu_ms/avg_cpu_ms`；用这些数字描述，不靠肉眼 |
| 7 | CPU 是 on-cpu 还是 runnable | `sched_slice` 只给 **on-cpu** 时间（`11/12` 都是）；包内**没有** runnable 等待的现成 SQL | runnable 这一段判 **UNKNOWN**；且即使补上，也不能当业务延迟。要谈"等锁/等 IO"，需要额外证据 |
| 8 | 观测粒度上限 | C1 的 `proc_stats_poll_ms`；C2 的 `sampling_interval_bytes`/`dump_interval_ms`/`shmem_size_bytes`/`block_client`/是否 `from_startup` | 1 s 轮询 + 5 s dump → 时间分辨力上限就是"秒级曲线形状"，永远到不了"每次 malloc" |
| 9 | 两次是不是同一负载阶段 | C2 的 `heap.status`/`app.log` 起止、C1 窗口、有无业务标记 | 一次含启动/预热、一次是稳态 → 高低不可比，只能各自与自己的基线比 |
| 10 | 相位归属 | 12 的周期 vs `dump_interval_ms` vs 业务周期 vs 系统周期任务 | 周期≈观测网格 → 先当成采样伪影；周期≈业务帧/定时任务 → 转"第三因"假设 |

**这一步的价值**：如果第 2/3 条不通过，后面全都不用做；如果第 4 条判出 `dur=0`，就把"精确持有区间"标 UNKNOWN 而不是判采集失败；如果第 5/6 条显示 CPU 峰值集中在一个与分配线程无关的线程上，说法四基本可以当场否掉。

## 4. 最小补采：一份合并 trace + 一个对照（推荐）

### 4.1 为什么这是最小

把 CPU 与分配放进**同一次会话**，跨 trace 对齐这个死结就消失了：

- 共享时钟由构造保证，不需要任何"对齐依据"；
- `sql/11`/`12`（CPU 桶/episode）与 `sql/03`/`04`（native live/调用栈）可以直接在同一 `trace_bounds` 内跑，SP 与基线口径天然一致；
- 可以把"CPU 峰值 episode"和"dump 窗口"放在同一条 Timeline 上叠加，而不是硬拼两个绝对时间轴；
- 一次采集同时满足验收所需的"sched 事件真的产生了""heap 数据真的非空"，比分别采两次更容易判断数据缺失。

### 4.2 完整配置（已填入 Linux/板端形态的目标参数；需按你的实际目标改 3 处）

生成器不提供"heapprofd + ftrace/sched + counters"一次成型的场景（`make_config.py` 的 `SCENARIOS` 是单场景），所以这里按 `references/09-advanced-configs.md` 的要求**手工合并成一份完整 TraceConfig**，字段结构沿用生成器的写法：

```text
# combined-cpu-alloc.pbtxt
# 用途：在同一 trace 内同时看 (a) 目标进程 per-thread on-cpu 时间 (b) Native 分配归因 (c) 业务阶段标记
# 预算：traced buffers 8MiB/4MiB/32MiB + heapprofd shmem 8MiB + ftrace per-CPU + 输出文件
# 生成器不产此组合，按 references/09-advanced-configs.md 合并；需用板端同版 descriptor 校验

buffers { size_kb: 8192 fill_policy: RING_BUFFER }
buffers { size_kb: 4096 fill_policy: DISCARD }
buffers { size_kb: 32768 fill_policy: DISCARD }

duration_ms: 30000

data_sources {
  config {
    name: "linux.process_stats"
    target_buffer: 1
    process_stats_config {
      scan_all_processes_on_start: true
      proc_stats_poll_ms: 1000
    }
  }
}

data_sources {
  config {
    name: "linux.sys_stats"
    sys_stats_config {
      meminfo_period_ms: 1000
      meminfo_counters: MEMINFO_MEM_AVAILABLE
      meminfo_counters: MEMINFO_MEM_FREE
      vmstat_period_ms: 1000
      vmstat_counters: VMSTAT_NR_FREE_PAGES
    }
  }
}

data_sources {
  config {
    name: "linux.ftrace"
    ftrace_config {
      buffer_size_kb: 2048
      drain_period_ms: 250
      ftrace_events: "sched/sched_switch"    # sql/11、12 依赖；有额外开销
      ftrace_events: "kmem/rss_stat"         # 仅当板端 available_events 确有此项；没有就删
      ftrace_events: "ftrace/print"          # 业务阶段标记（写 trace_marker 即可被采到）
    }
  }
}

data_sources {
  config {
    name: "android.heapprofd"
    target_buffer: 2
    heapprofd_config {
      sampling_interval_bytes: 4096
      process_cmdline: "REPLACE_WITH_ACTUAL_CMDLINE"   # ← 改：与目标 argv[0] basename 精确一致
      shmem_size_bytes: 8388608
      block_client: false
      continuous_dump_config { dump_interval_ms: 5000 }
    }
  }
}
```

**必须改的 3 处**：

1. `process_cmdline`：用目标的**实际启动名**（basename）。配置写 `memprobe` 而启动成 `/data/memprobe` 是可以的；写主机产物名（如 `memprobe_arm64`）会匹配失败，且 `PERFETTO_HEAPPROFD_BLOCKING_INIT=1` 可能一起挂住（`tests/scenarios.md` A30/A31）。
2. `kmem/rss_stat`：先按板端 `available_events` 确认，**不存在就删掉这一行**，不要为了"配置完整"保留不存在的事件名。
3. `duration_ms`：这是安全上限，不是观测时长；要大于目标机 `OBSERVE_S`。

**版本条件（不满足就降级，不要硬塞）**：

- `heapprofd_config` 字段（`sampling_interval_bytes`/`process_cmdline`/`shmem_size_bytes`/`block_client`/`continuous_dump_config`）以**板端采集器版本**的 proto/实现为准；主机 UI 新不代表板端认。
- 有匹配版本 descriptor 时跑 `python3 scripts/validate_config.py combined-cpu-alloc.pbtxt --descriptor-set <desc>`；**没有就必须标注"配置已构造，未做该版本 schema 验证"**，不能把"括号配平"当 schema 通过。
- 若 C2 实际来自 Android（API ≥ 29 才有 native profile），把采集入口换成 `adb push` + `perfetto --txt -c ...`，业务标记走 atrace；同一份 `heapprofd_config` 语义不变。

### 4.3 执行（【主机】/【目标机】分开，顺序不能颠倒）

【主机】生成/校验后推送（沿用包内已验证的会话脚本）：

```bash
# 主机：校验（有匹配 descriptor 才做这步）
python3 scripts/validate_config.py combined-cpu-alloc.pbtxt \
  --descriptor-set /absolute/work/trace_config.desc

BOARD='user@board-address'
WORK='/data/perfetto-session'          # 板端可写目录；X5 /data 是 tmpfs，注意 RAM 预算
scp combined-cpu-alloc.pbtxt scripts/linux_session_lib.sh \
    scripts/linux_heapprofd_session.sh ./libheapprofd_glibc_preload.so \
    "$BOARD:$WORK/"
```

【目标机】顺序是：起 trace → 等服务可查询 → 带 preload 启动目标 → 等 heapprofd producer 可见 → 观测 → 停目标 → SIGINT flush：

```bash
# 目标机：脚本内部已实现 4.2 的六步与失败退出码；OBSERVE_S 必须小于配置 duration_ms(30s)
WORK=/data/perfetto-session TRACEBOX=/data/tracebox OBSERVE_S=25 OUT=combined \
  sh /data/perfetto-session/linux_heapprofd_session.sh \
     /data/perfetto-session/combined-cpu-alloc.pbtxt \
     /data/perfetto-session/libheapprofd_glibc_preload.so \
     /data/perfetto-session ./path-to-test-app
```

要点（都已在脚本/文档里，但容易被跳过）：

- 不要用"先 `--background-wait` 等就绪、再启动 preload 进程"的顺序——heapprofd producer 还没注册时它等不到全部数据源；上面的顺序是"起 trace → 起 app → 等 producer"。
- `--system-sockets` 会与既有系统服务抢端点；遇到冲突就复用/改端点，**不要 pkill 别人的会话**。
- Linux 上 heapprofd 只能覆盖**启动时**预加载的进程；已经跑起来、没预加载的进程不能靠"设环境变量"补，也不能套 Android 的运行时注入（`tests/scenarios.md` A06）。
- `block_client:false` 的代价是缓冲不足时可能丢失/提前终止 → 必须查 `stats` 里的丢数据诊断，而不是只看文件非空。

【主机】拉回：

```bash
sh scripts/host_pull.sh "$BOARD" /data/perfetto-session ./captures \
  combined.pftrace combined.log combined.status combined.app.log combined.query.txt
# host_pull.sh 对 scp 失败/空文件直接非零退出——这是"采集成功"的必要条件之一
```

### 4.4 三个必带的对照与变体（按代价从低到高）

| 类型 | 做法 | 能证明什么 | 注意 |
|---|---|---|---|
| **无 profiler 对照** | 同一 workload、同一实例、同一阶段，用只含 counters+sched+标记的配置再采一次（**如果 C1 本来就是同负载/同实例的无 profiler 采集，可以直接复用 C1 当对照，并说明这一点**） | 排除"CPU 锯齿是 profiler 自己造成的"；也能看锯齿在没有 heapprofd 时是否照样存在 | 两次的负载阶段/实例必须一致；不一致就只能各自与自己的基线比 |
| **剂量关系** | 受控测试程序里把"该分配路径"的量改一档（频率或大小），其余不变；看 CPU episode 的 `peak_cpu_ms/avg_cpu_ms` 是否随之变 | 剂量关系，比"同窗出现"强得多 | 在**测试程序/可配置 workload**上做；不要在生产 cam-service 上直接改行为 |
| **干预（最强）** | 在可重启的测试环境里去掉/限制那条分配路径（如改为池化复用），看锯齿是否消失、业务打点是否同步改善 | 可干预性 + 机制 + 业务效果 | 需要改代码/构建；结论要写清是"测试构建"而非"线上已验证" |

如果**不能重启、不能 preload**：只能退回到 C1 现有数据 + smaps/counters，因果上限就是"窗口共现 + 无机制"，必须明确标 UNKNOWN，并给出"最低可做的下一步"而不是硬下结论。

## 5. 采集验收与 Perfetto UI

### 5.1 验收（先验收，再看图）

合并 trace 拉回后，按 `references/06-quality.md` 第 3 节逐项：

1. `sql/00-inventory.sql`：`trace_bounds` 覆盖"操作前—复现—恢复"，首尾没有被轮转吃掉；目标 `upid` 唯一（`[CANDIDATES]`）；`stats` 非零错误逐条读（heap/ftrace/packet 相关优先）。
2. `sql/10-native-dump-capability.sql`：`dumps`、`distinct_ts_end`、`zero_dur_dumps`。若 `zero_dur_dumps = dumps` → 窗口区间 UNKNOWN（不影响总量/分配释放/符号结论）。
3. `sched` 真的产出了：`sql/11` 能出目标 UPID 的行；出 0 行先查 `target_upid` 是否填对、`sched_switch` 是否真的被采到，而不是判"没有 CPU"。
4. 三条结论分别写在记录里：**配置 hash / 采集器版本 / UPID / 窗口 / 单位 / 是否有丢失 / 是否符号缺失**。没有符号就写"只有模块/地址粒度"，不承诺源码行。

### 5.2 轨道与 Add debug track 映射

同一个 trace、同一个窗口（"操作前—复现—恢复"），建议轨道顺序：业务阶段标记 → CPU（per-thread）→ 系统/进程内存 → native live → Native 火焰图。

| 数据 | SQL | Add debug track 设置 |
|---|---|---|
| 业务阶段标记 | `sql/07-kernel-events.sql`（或直接 `ftrace/print` 的 slice） | **Slice Track**；Timestamp=`ts`；Duration=`dur`（标记通常为 0）；Name=`name`；Pivot=`series` |
| CPU 峰值 episode | `sql/12-cpu-spike-episodes.sql` | **Slice Track**；Timestamp=`ts`；Duration=`dur`；Name 用字面量（如 `cpu_spike`） |
| per-thread CPU 桶 | `sql/11-cpu-time-buckets.sql` | **Counter Track**；Timestamp=`ts`；Value=`cpu_ms`；Pivot=`thread_name`（或 `utid`） |
| Native live 估计 | `sql/03-native-live.sql` | **Counter Track**；Timestamp=`ts`；Value=`value`（MiB）；Pivot=`series` |
| 分配热点 | `sql/04-native-callstacks.sql` | 表格看 `cumulative_live_bytes_at_end`；火焰图里选 **Unreleased Malloc Size**（看保留）或 **Total Malloc Size/Count**（看流量） |

口径提醒：

- `ts` 是**纳秒**，不要换成秒再 Add debug track；`cpu_ms` 是毫秒、`value` 是 MiB、`count` 是估计次数——单位写在轨道标题里。
- `sql/03` 的曲线是 **dump 级快照分辨率**，不是每次 malloc 的逐事件曲线，也不适用于 `dump_at_max`/ART allocation。
- `sql/04` 的 cumulative 在祖先栈会重复出现，**绝不能把结果相加当进程内存**（文件末尾注释）。
- 未实际打开 UI 验证，就写"UI 操作配方已给出"，不写"已验证显示正常"。

## 6. 如何下结论

### 6.1 逐项三态（不要用一个总状态代替）

| 结论项 | 现状 | 说明 |
|---|---|---|
| C1 内目标进程在给定窗口有周期性 on-cpu 抬升 | **可判**（跑完 `11/12` 后 PASS/FAIL） | 这是"目标进程 on-cpu 时间"，不是"业务卡顿"；周期必须来自 SQL 数字 |
| C1 与 C2 逐点时间对齐 | **FAIL** | 无对齐依据；SQL 参数语义也不支持（§2.1） |
| heapprofd dump 的 `ts` = 单次 malloc 的时刻 | **FAIL** | 快照/窗口语义（§2.2） |
| 单次 malloc 的精确调用次数 | **UNKNOWN** | 采样估计 + 方差（§2.3） |
| C2 中目标 UPID 的 live/分配量估计较高 | **可判（PASS，但须注明是采样估计与追踪范围口径）** | 需要前缀和基线；区间净变化 ≠ 结束时 live |
| 精确持有区间 | **UNKNOWN**（若 `dur=0`） | 只能给上界证据；上界证据不得反过来断言"实际持有与预期不符" |
| 分配导致 CPU 抖动 | **UNKNOWN**（当前证据不足，不是"已证伪"） | 缺机制/剂量/对照/业务时间线（§2.4） |
| 分配导致掉帧/卡顿 | **UNKNOWN**，且当前**没有任何帧证据** | 系统 runnable/CPU 不能冒充业务延迟 |

### 6.2 什么结果支持、什么结果反驳（预期现象，不是编造的实测）

| 假设"分配导致 CPU 抖动" | 支持它的证据形态 | 反驳/削弱它的证据形态 |
|---|---|---|
| 时间先后 | 同一 trace 内，分配活动（`sql/03` 的上升段/`04` 的窗口）先于或同窗于 CPU `peak_cpu_ms` | CPU 峰值落在"长时间只持有、无新分配"的窗口（`window_end` 不前进的那几份 dump 区间） |
| 机制 | `sched_slice` 显示 on-cpu 集中在**分配线程**（`sql/11` 的 `thread_name/utid`），且 `sql/04` 的热点 callsite 就落在这条线程上 | CPU 峰值主要落在与分配无关的线程；或时间花在别处（需要 CPU profile 才能进一步定位，包内不承诺） |
| 剂量 | 改一档分配量后，`12` 的 `peak_cpu_ms/avg_cpu_ms` 随之变化 | 分配量变了、CPU 幅度不变；或分配量不变、CPU 幅度大改 |
| 对照 | 无 profiler 的对照里锯齿形态一致且幅度相近（说明锯齿不是采集造成）；去掉分配路径后锯齿消失 | 锯齿只在带 profiler 的采集里出现（采集扰动）；或去掉分配路径后锯齿依旧 |
| 业务 | 业务帧间隔/阶段标记（`trace_marker`）与 CPU 峰值同窗，且去掉分配路径后业务指标改善 | 业务标记与 CPU 峰值不相关；或业务指标在"CPU 锯齿"之外的时间窗更差 |

**最强 → 最弱的证据排序**（用于判断要不要继续花钱采集）：干预 > 剂量 > 机制 + 同窗 > 单纯同窗 > "都看起来偏高"。

### 6.3 现在能说、不能说的话

**能说**：

- "C1 显示目标进程在 X–Y 窗口有周期性 on-cpu 抬升（`sql/12` 的 `ts/dur/peak_cpu_ms` 为证）。"
- "C2 显示目标 UPID 在追踪范围内有采样到的 Native 分配归因，live 估计为 Z MiB（采样估计，dump 级分辨率）。"
- "两份独立采集的绝对时间戳不能直接混用/填入对方 SQL；要建立同轴需要先举证时钟对齐，或改采一份合并 trace。"

**不能说**：

- "dump 的时间就是 malloc 的时间"、"第 N 秒发生了 M 次 malloc"。
- "count 高所以调用次数多"、"所以 CPU 高"。
- "profiler 采到了，所以因果成立"。
- "heapprofd 能告诉我这次 malloc 花了 3 ms"（它是归因器，不是延迟分析器）。
- "系统 CPU/runnable 高，所以业务卡了"。

### 6.4 一个最有价值的下一步

> **采一份合并 trace**（§4.2，含 `sched/sched_switch`、`heapprofd`、业务 `trace_marker`），然后用 `sql/12` 定位 CPU episode、`sql/11` 看峰值由哪个线程贡献、`sql/03/04` 看同窗分配归因到哪条栈。若机制对得上（同一线程/同一 callsite），再做**一档剂量**实验；有可重启的测试环境就补**干预**对照。

这一份 trace 能同时消掉当前三个未知：跨 trace 对齐、dump 粒度误解、以及"CPU 峰值到底是谁在烧"。如果连合并 trace 都做不了（例如目标不能重启、不能 preload），那么因果上限就明确停在"窗口共现"，结论里必须写 UNKNOWN，并说明"哪个指标不可测、哪些结论仍可用"。
