# B1 — ARM64 Linux `demo_svc` 两套采集方案（无 preload 低开销 trace / native heapprofd）

> 本文只依据 `candidate-v1.0.2` 的 `SKILL.md`、`references/`、`sql/`、`scripts/` 与场景输入给出方案。
> **本次未连接设备、未执行任何采集命令、未读取任何实测 trace**：下文所有曲线、数量、符号结论均为"预期现象 + 判读规则"，不是设备实测结果；标注 `UNVERIFIED` 的项必须在板上确认后才能当成前提。

## 0. 结论摘要

| | 方案 1：无 LD_PRELOAD 低开销 trace | 方案 2：native heapprofd |
|---|---|---|
| 回答什么 | 占多少、何时涨、系统压力、调度状态 | 哪条调用栈在 malloc/new、保留/累计多少 |
| 数据源 | `linux.process_stats` + `linux.sys_stats`（+ 可选 `linux.ftrace: kmem/rss_stat`、`sched/sched_switch`） | 上述计数器 + `heapprofd`（`libc.malloc`） |
| 是否重启 `demo_svc` | **不需要**，对业务零注入 | **需要**重启"专门测试实例"（preload 只在进程启动时生效，不能回溯） |
| 板端额外内存 | 8 MiB + 4 MiB traced buffer，+1 MiB/CPU ftrace 缓冲，输出文件在 tmpfs | 上述 +32 MiB discard buffer + 8 MiB heapprofd shmem |
| 主要风险 | tmpfs 上的输出文件本身抬高 shmem/RSS | preload 依赖与 socket 端点、启动期漏采、buffer 溢出 |
| 建议顺序 | **先跑**（基线、可接受性、脚本/端点先验） | 后跑，且必须与方案 1 串行，不同时开 |

硬约束（由场景输入直接推出，影响两条路线）：

1. **rootfs 只读** → 所有写入必须落在 `/data/<work>`；`--system-sockets` 的 socket 默认位置通常在 `/tmp`（常见 `/tmp/perfetto-producer.sock`、`/tmp/perfetto-consumer.sock`，以本构建 `--help`/日志实际输出为准），若 `/tmp` 落在只读 rootfs，**必须改用 `PERFETTO_PRODUCER_SOCK_NAME` / `PERFETTO_CONSUMER_SOCK_NAME` 指到 `/data`**，否则会话起不来或 producer 连不上。
2. **`/data` 是 tmpfs** → trace 文件、preload `.so`、日志都吃 RAM，并且会以 **shmem 记账**出现在**这一条 trace 自己**的 RSS 数据里。必须控制 buffer/时长/文件大小，并及时拉回、及时删除；不能一边在 `/data` 写大文件一边宣称"进程 anon 涨了"。
3. **板端无 Python、不能连外网** → 配置生成、schema 校验、分析全部在【主机】；板端只有 shell + tracebox + 目标程序。工具只能 SCP 推。
4. **版本必须成对**：板端 tracebox v57.1 决定可用字段与数据源名；主机分析器版本决定表与 SQL。配置的正式结论应来自 v57.1 源码 descriptor；拿不到时只能写"配置已构造，未做该版本 schema 验证"（见 §3.3）。
5. **本条 trace 的绝对时间戳只能在本 trace 内用**。方案 1 与方案 2 是两次独立采集，除非有共享时钟证据，否则各自用各自的相对窗口比较模式，不要按绝对 ns 硬拼成一条时间轴。

### 1.1 板端只读探测（一次性，两方案共用）

全部是只读检查，`survey.sh` 明确"不 mount、不改 sysctl、不启动 tracing"。

```bash
# 【主机】Skill 目录下
BOARD='root@<board-ip>'                 # 改成真实登录目标
SDK='/opt/perfetto-v57.1'               # 已核实的同版本 SDK（arm64）
WORK_1='/data/perfetto/b1-trace'        # 方案 1 工作目录（tmpfs）
WORK_2='/data/perfetto/b1-heap'         # 方案 2 工作目录（tmpfs）
TRACEBOX='/data/perfetto/tracebox'      # 板端 tracebox 路径（首次推送后固定）

ssh "$BOARD" "mkdir -p $WORK_1 $WORK_2"
scp scripts/survey.sh "$BOARD:$WORK_1/"
ssh "$BOARD" "sh $WORK_1/survey.sh"          > host_preflight.txt 2>&1
ssh "$BOARD" "sh $WORK_1/survey.sh --events" > available_events.txt
```

在 `host_preflight.txt` 里逐条读（不要只看 `test -d`）：

- `tracefs=` 实际路径；`current_tracer` / `tracing_on` 的现状（只记录，不改）。
- `/data` 是否为 tmpfs、`df -k /data` 余量；`/tmp`、`/dev/shm` 是否可写（`df` 有输出且目录可写）。
- `MemTotal` / `MemAvailable`：tmpfs 输出会挤占，可用内存低时要缩短时长、缩小 buffer。
- `perf_event_paranoid`（本方案两条路线都不需要 perf，记录即可，**不要**为了它改 sysctl）。
- 工具存在性：`command -v tracebox`（`survey.sh` 只证明"文件在"，不代表数据源已注册）。

再单独确认 CLI 与非注册态（`UNVERIFIED`，以实际输出为准）：

```bash
# 【目标机】
"$TRACEBOX" --version
"$TRACEBOX" --help | grep -E -- '--background|--system-sockets|--txt|--background-wait'
"$TRACEBOX" perfetto --query --long
```

判读规则（来自 `references/05-platforms.md` §3.2 与 §4.2）：

- `--background` / `--txt` / `-o` 是两条脚本的生命线，缺失则脚本不可用，只能改用该构建支持的等价参数。
- `--background-wait` **不作为前提**：heapprofd producer 尚未注册时它可能等不到全部数据源；本方案用脚本的"起 trace → 起 app → 等 producer"顺序。
- `perfetto --query` 里**看不见 heapprofd 不能直接判"不支持"**：某些 heap producer 按需出现，要结合真实启动日志判断。反过来，`--query` 看得见也**不证明**目标已被采样。

## 2. 执行位置与变量作用域（两方案通用，写错会直接采空）

| 变量 | 归属 | 谁解析 | 说明 |
|---|---|---|---|
| `BOARD` `SDK` `HOST_OUT` `PRELOAD_SRC` | **主机** | 主机 shell | 只在本机 `/bin/sh` 里存在 |
| `WORK_1` `WORK_2` `TRACEBOX` `APP_DIR` `APP_CMD` `OBSERVE_S` | **目标机** | 目标机 shell（脚本内读取） | 通过 `ssh "$BOARD" "WORK=... TRACEBOX=... sh ..."` 以**环境前缀**注入 |
| `$!` `$(...)`、`kill -0 $TPID`、`$(cat *.pid)` | **目标机** | 目标机 shell | **绝对不能**出现在主机双引号可展开的位置；它们必须留在板端脚本里 |
| `PWD`/相对路径 | 混合 | — | 远程命令里一律用绝对路径，避免登录 shell 的 cwd 差异 |

落地规则：

1. 主机只负责"生成、推送、拉起远程命令、拉回、分析"；一切 PID、超时、信号都在目标机解析。
2. 远程命令里出现的 `$WORK`、`$TRACEBOX` 是**主机变量被展开后**的字面值（可接受，因为值是主机已知的常量）；远程命令里**不要**再出现 `$!`、`$(...)`、`$$`。
3. `linux_trace_session.sh` 与 `linux_heapprofd_session.sh` 都通过 `linux_session_lib.sh` 解析 `TRACEBOX`：先看环境变量，再 `command -v tracebox`，都没有就 `exit 127`。统一显式传 `TRACEBOX`，不要依赖 PATH。

## 4. 方案 1：不需要 LD_PRELOAD 的低开销 trace（sched / RSS / 系统计数器）

### 4.1 定位路线

- **问题**：`demo_svc` 占多少、什么时候涨、涨的时候系统在干什么。
- **可验证假设**（任选其一，先写下再采集）：
  - H1：RSS 增长主要发生在复现操作的窗口内，并与 `MemAvailable` 下降同时出现；
  - H2：短时尖峰在 1 s 轮询下不可见，需要 `rss_stat` 事件级观测；
  - H3：内存压力/回收期间，`demo_svc` 的可运行状态异常（需 sched）。
- **数据源**：`linux.process_stats`（进程元数据 + 按进程 RSS）、`linux.sys_stats`（全系统 meminfo/vmstat）、可选 `linux.ftrace`（`kmem/rss_stat`；或 `sched/sched_switch`）。
- **不覆盖**：谁分配（→ 方案 2）、PSS/私有脏页（→ smaps/dumpsys 快照，需与 trace 时钟对应）、CMA/ION/dma-buf 对象归属（→ `cma:` 事件 + 快照，且要求实际存在）、page cache 归属（file RSS 是结果，不是原因）。
- **注意**：本方案**不需要重启 `demo_svc`**，这是"低开销/低扰动"的核心优势；如果业务侧有可授权的阶段标记（日志/trace_marker），可以另加，但属于额外集成，不能宣称现成轨道。

### 4.2 完整采集配置（已填入目标参数）

三档按开销递增，**推荐只跑 1B 一条**（计数器 + RSS 事件同一条 trace，30 s）。再需要调度证据时**另开一次** 1C，不要默认把 sched 塞进 1B。

#### 1B（推荐）计数器 + RSS 事件，30 s

由 `rss-spike` 生成，等价于：`python3 scripts/make_config.py rss-spike --platform linux --events available_events.txt --duration-ms 30000 --poll-ms 1000`（生成器会在事件清单缺 `kmem/rss_stat` 时直接报错并提示改用 overview）：

```text
# b1-counters.pbtxt —— 计数器 + rss_stat；单位：ms / KiB
buffers { size_kb: 8192 fill_policy: RING_BUFFER }
buffers { size_kb: 4096 fill_policy: DISCARD }

duration_ms: 30000

data_sources {
  config {
    name: "linux.process_stats"
    target_buffer: 1
    process_stats_config {
      scan_all_processes_on_start: true
      proc_stats_poll_ms: 1000
    }
  }
}

data_sources {
  config {
    name: "linux.sys_stats"
    target_buffer: 0
    sys_stats_config {
      meminfo_period_ms: 1000
      meminfo_counters: MEMINFO_MEM_TOTAL
      meminfo_counters: MEMINFO_MEM_FREE
      meminfo_counters: MEMINFO_MEM_AVAILABLE
      meminfo_counters: MEMINFO_BUFFERS
      meminfo_counters: MEMINFO_CACHED
      meminfo_counters: MEMINFO_ANON_PAGES
      meminfo_counters: MEMINFO_SHMEM
      meminfo_counters: MEMINFO_SLAB
      meminfo_counters: MEMINFO_SWAP_TOTAL
      meminfo_counters: MEMINFO_SWAP_FREE
      meminfo_counters: MEMINFO_CMA_TOTAL
      meminfo_counters: MEMINFO_CMA_FREE
      vmstat_period_ms: 1000
      vmstat_counters: VMSTAT_NR_FREE_PAGES
      vmstat_counters: VMSTAT_PGFAULT
      vmstat_counters: VMSTAT_PGMAJFAULT
      vmstat_counters: VMSTAT_PSWPIN
      vmstat_counters: VMSTAT_PSWPOUT
    }
  }
}

data_sources {
  config {
    name: "linux.ftrace"
    target_buffer: 0
    ftrace_config {
      buffer_size_kb: 1024
      drain_period_ms: 250
      ftrace_events: "kmem/rss_stat"
    }
  }
}
```

参数与单位说明：

- `proc_stats_poll_ms` / `meminfo_period_ms` / `vmstat_period_ms` 单位 ms，默认 1000；**不要**为了"看得更细"普遍降到 100 ms——每次轮询都要扫进程/读 `/proc`，是实打实的开销。短尖峰优先靠 1B 的 `rss_stat` 事件，而不是把轮询调到极限。
- `kmem/rss_stat` 事件由内核 RSS 记账路径产生，**允许有批处理与记录丢失**；它给出的是"某一时刻该类别绝对记账字节数"，不是每次 malloc 一条日志，也不是逐页精确时间线。不要把"事件时间间隔"说成"保证 1 ms 分辨率"。
- `buffer_size_kb` 是**每 CPU** 的 ftrace 环形缓冲；整机占用 ≈ CPU 核数 × 1024 KiB。CPU 多、事件多时可能溢出（见 §4.7 的 stats 检查）。
- `fill_policy: RING_BUFFER` 让旧的普通 counter 数据被轮转掉；`DISCARD` 的那块是 ftrace 通道的兜底。**trace_bounds 必须覆盖复现窗口**，否则先怀疑轮转。
- 若该内核缺 `MEMINFO_CMA_*` / 某些 vmstat 字段，结果是**没有点**，不是 0；不要补零画线。
- `demo_svc` 不需要写进配置：以上都是整机数据源，目标通过分析阶段按 UPID 过滤（这也是"零注入"的原因）。

#### 1A（保底，零 ftrace）：只有轮询

`kmem/rss_stat` 不存在时使用，等价于 `python3 scripts/make_config.py overview --platform linux --duration-ms 30000 --poll-ms 1000`——把上面 1B 里的整个 `linux.ftrace` 块删掉，其余不变。此时**必须声明盲区**："1 s 轮询，短于 1 s 的 RSS 尖峰可能完全不可见；不承诺捕捉 150 ms 级峰值。"

#### 1C（可选，独立一次）：加 `sched/sched_switch`

`python3 scripts/make_config.py overview --platform linux --events available_events.txt --sched --duration-ms 30000`（`--sched` 要求事件清单里确有 `sched/sched_switch`，否则生成器报错）。

- 开销：`sched_switch` 是高频事件，`references/01-counters.md` 明确把它算作"显式额外开销"；高负载板上 1024 KiB/CPU 很容易溢出，需要在验收里看丢失率；确需长跑可把 `buffer_size_kb` 提到 4096，代价是每 CPU 多占 RAM（tmpfs 板上要计入预算）。
- 用途仅限：把 `demo_svc` 相关线程的 runnable/睡眠状态与内存事件对时；**它不能独自说明所有等待原因**，也不等于业务帧延迟。

#### 要不要用 mmap/perf 路线

本场景没要求"谁 mmap 了多大"，且 `mmap` 模板要求 `--arch aarch64 --perf-confirmed` 并真的验证过 perf tracepoint 采样；`perf_event_paranoid` 不能简单解读为可用。默认**不启用**，不要顺手加上去。

### 4.3 操作步骤（标【主机】/【目标机】）

> 端口/时长为示例值；`WORK_1`、`TRACEBOX` 已在 §2 定义。目标：单次 30 s 采集，`TIMEOUT_S=45`（= 时长 + 15 s 余量，便于把"超时"判成配置/环境问题而不是正常结束）。

**步骤 1【主机】准备目录与文件**

```bash
ssh "$BOARD" "mkdir -p $WORK_1 && df -k /data"
scp "$SDK/tracebox-arm64" scripts/linux_session_lib.sh \
    scripts/linux_trace_session.sh "$BOARD:$WORK_1/"
# 板上已存在同名 tracebox 且版本已核实则不要覆盖（避免换掉已知可用的二进制）
```

**步骤 2【主机】生成配置**（`available_events.txt` 来自 §1.1）

```bash
python3 scripts/make_config.py rss-spike --platform linux \
  --events available_events.txt --duration-ms 30000 --poll-ms 1000 > b1-counters.pbtxt
# 若报 "Target lacks kmem/rss_stat"：改用 overview（即 1A），并在结论里写明轮询盲区
```

可选 schema 验证（有 v57.1 源码时）：

```bash
protoc -I "$V571_SRC" --include_imports \
  --descriptor_set_out="$PWD/v571.desc" protos/perfetto/config/trace_config.proto
python3 scripts/validate_config.py b1-counters.pbtxt --descriptor-set v571.desc
```

**步骤 3【主机】推送配置**

```bash
scp b1-counters.pbtxt "$BOARD:$WORK_1/"
```

**步骤 4【目标机】启动采集**（由主机发起；本命令会阻塞到会话结束，约 30–35 s）

```bash
ssh "$BOARD" "WORK=$WORK_1 TRACEBOX=$TRACEBOX \
  sh $WORK_1/linux_trace_session.sh $WORK_1/b1-counters.pbtxt b1-counters 45"
```

脚本行为（`scripts/linux_trace_session.sh`）：`rm -f` 旧的 4 个产物 → `tracebox --txt -c ... -o ... --background` 并记录 PID 到 `b1-counters.pid` → 每 1 s 轮询该 PID → 自然退出或超时后 `SIGINT`（再 `TERM`，各等 10 s）→ 等 `.pftrace` 非空（最多 5 s）→ 写 `b1-counters.status`（`DONE size_bytes=...`）。

**步骤 5【主机/另一终端】复现业务（与采集并行，顺序上必须在采集已启动之后）**

```bash
# 采集已在跑的 30 s 窗口内执行；用板端时钟打点，便于后续在 trace 内定位窗口
ssh "$BOARD" 'date +%s.%N; <你的复现命令>; date +%s.%N'
```

只操作"已获准的专门测试实例"；**不要**重启生产服务、不要清 cache、不要动别人正在跑的 tracing 会话。业务侧若有自己的日志/帧标记，记录其时间戳，作为后面判"相关性"的独立证据。

**步骤 6【目标机】提前停止（只有需要时才做）**

正常结束靠 `duration_ms: 30000`，不需要人干预。要提前结束，只对本会话 PID 发 `SIGINT`（它就是在 `b1-counters.pid` 里的那个进程）：

```bash
ssh "$BOARD" 'kill -INT "$(cat '"$WORK_1"'/b1-counters.pid)"'
```

**禁止** `pkill traced` / `killall tracebox`：板端可能同时存在别人的会话，脚本 `stop_tracebox()` 也只对本次 PID 发信号。

**步骤 7【主机】拉回（失败必须非零退出）**

```bash
mkdir -p ./captures/b1-trace
sh scripts/host_pull.sh "$BOARD" "$WORK_1" ./captures/b1-trace \
  b1-counters.pftrace b1-counters.log b1-counters.status b1-counters.pid
```

`host_pull.sh` 对每个文件 `scp -q` 失败或落地为空立即 `exit 1`，成功时打印 `size=` 与 `sha256=`。**空文件、缺文件、SCP 非零都算采集失败**，不得继续往下宣称成功。

**步骤 8【主机】清理（确认拉回并核对 sha256 之后）**

```bash
ssh "$BOARD" 'rm -f '"$WORK_1"'/b1-counters.pftrace '"$WORK_1"'/b1-counters.log'
```

只删本次自己的文件；脚本/二进制留着复用。tmpfs 上删除即释放 RAM。

### 4.4 观测/持续时间

| 参数 | 取值 | 理由 |
|---|---|---|
| `duration_ms` | 30000 | 覆盖"操作前 5 s → 复现 20 s → 恢复 5 s"的最小完整窗口 |
| `proc_stats_poll_ms` / meminfo / vmstat | 1000 | 默认轮询；粗于 RSS 事件，避免自伤开销 |
| `rss_stat` | 事件级 | 补足 1 s 轮询的盲区；不承诺毫秒级分辨率 |
| 脚本 `TIMEOUT_S` | 45 | 必须 > duration；若日志出现 `timeout; sending SIGINT`，说明会话没按 `duration_ms` 自行结束，要当异常查 |
| 重复次数 | ≥2 次同负载 | 第二次用于"同样操作是否同样变化"；单次不可判趋势 |
| 温机 | 先短跑 5 s 冒烟 | 验证端点/配置/输出路径，再正式跑；冒烟不算证据 |

### 4.5 停止与 flush

- 正常路径：`duration_ms` 到期 → tracebox 自行收尾写文件 → 脚本等 PID 退出 → 检查文件非空。**"命令返回 0" 不等于 "已 flush"**，flush 的判据是：PID 已退出 + `.pftrace` 非空 + `status` 有 `DONE`。
- 中断路径：`SIGINT` 是官方允许的优雅停止方式；脚本等 10 s，不行才 `TERM`。若 `TERM` 后仍不退，脚本 `exit 3`——这是失败，不是完成。
- 落盘后若发现 `size_bytes` 明显偏小（例如 < 几百 KiB 且有 sched），先怀疑 buffer 溢出或会话被提前终止，而不是"数据本来就少"。
- 采集期间**不要**在同一块板上并行第二个 tracebox 会话（ram/CPU 互相污染，且 `--system-sockets` 还会端点冲突）。

### 4.6 失败条件（先查这里，再改配置）

| 现象 | 退出码/来源 | 最小下一步 |
|---|---|---|
| `ERROR: tracebox not found` / `not executable` | 127（`linux_session_lib.sh`） | 显式传 `TRACEBOX=/data/perfetto/tracebox` 并 `ls -l`/`chmod +x` |
| `ERROR: config not readable` | 2（`linux_trace_session.sh`） | 检查 scp 后的文件（tmpfs 断电即丢；也可能是先 rm 掉了） |
| `FAIL: tracebox did not exit` | 3 | 看 `.log`；确认 `duration_ms` 被识别、无版本不兼容字段；必要时手工 `SIGINT` 后重跑 |
| `FAIL: <out>.pftrace missing or empty` | 4 | 看 `.log` 里的 stderr；典型：socket 不可写（`/tmp` 只读）、config 被拒、`-o` 目录不可写 |
| `.log` 里 `timeout; sending SIGINT` | 警告（非失败） | 说明会话没按 duration 自己结束，按异常处理（配置 duration 是否被截断/版本行为） |
| trace 只有系统 counter、没有 `rss_stat` 行 | 数据层 | 板上 `available_events` 复查；`grep 'kmem:rss_stat' events/kmem/rss_stat/format`；没有就是没有，退回 1A 并声明盲区 |
| `stats` 里有 ftrace 丢包/overrun 非零 | 数据层 | 缩短时长 / 提高 `buffer_size_kb`（每 CPU 代价）/ 去掉 sched |
| `trace_bounds` 起点晚于"操作前" | 数据层 | buffer 被轮转；缩小时长或增大 ring buffer 后重跑 |
| SCP 失败 / 落地 0 字节 | 1（`host_pull.sh`） | 板上文件是否已被删/被下一次 run 覆盖；重新拉 |

### 4.7 采集验收（按级别，逐项判 PASS / FAIL / UNKNOWN）

先确认文件能打开，再在 Perfetto UI 的 Query (SQL) 或本机 Trace Processor 里逐条执行（**不要**把一次 CSV 导出当原始证据；保留 `.pftrace` 原件）。

```sql
-- 1) 时间范围：是否覆盖 操作前→复现→恢复
SELECT * FROM trace_bounds;

-- 2) 目标进程实例：demo_svc 是否唯一？PID 复用/重启会多行
SELECT upid, pid, name, start_ts, end_ts FROM process
WHERE name = 'demo_svc' OR name GLOB '*/demo_svc'
ORDER BY upid;

-- 3) 轨道发现：确认 counter 轨道名与单位（bytes vs kB vs pages）
SELECT id, name FROM counter_track ORDER BY name, id;
SELECT pct.upid, p.id AS track_id, pct.name
FROM process_counter_track pct LEFT JOIN process p USING (upid)
ORDER BY pct.upid, pct.name;

-- 4) 每类 count 的量级与覆盖（空 = 该 counter 根本没采，不是 0）
SELECT pct.upid, pct.name, COUNT(*) AS rows, MIN(c.ts) AS first_ts, MAX(c.ts) AS last_ts
FROM process_counter_track pct JOIN counter c ON c.track_id = pct.id
WHERE pct.upid = <步骤2得到的UPID>
GROUP BY pct.id ORDER BY pct.name;

-- 5) 非零错误/数据丢失（info 级不一律判失败，但 heap/ftrace 相关要看完）
SELECT name, idx, severity, source, value FROM stats
WHERE value <> 0 AND (severity <> 'info' OR name GLOB '*ftrace*' OR name GLOB '*heap*')
ORDER BY severity, name, idx;

-- 6) 表能力（决定下面用哪套 SQL）
SELECT name FROM sqlite_master
WHERE name GLOB '*heap*' OR name GLOB '*ftrace*' OR name GLOB '*counter*';
```

验收清单：

| 检查 | PASS 判据 | 失败/未知怎么写 |
|---|---|---|
| 目标 UPID | `demo_svc` 恰好 1 个覆盖复现窗口的实例 | 多实例 → 报"未解析"，按 PID 复用分别给窗口，不静默取第一行 |
| 窗口 | `trace_bounds` 覆盖操作前与恢复段 | 被轮转 → FAIL，重跑 |
| counters | 目标 UPID 的 RSS 轨道有 `rows ≥ duration/poll`（30 s/1 s ≈ 30） | 行数为 0 → UNKNOWN：该 counter 未采，不是"内存没变" |
| RSS 事件 | `kmem/rss_stat` 事件存在且 `mm_id` 能对到目标地址空间 | 缺 → 1B 降级为 1A，声明盲区；不要把事件发线程 PID 当内存所属进程 |
| ftrace 丢失 | `stats` 无影响结论的 overrun/丢失 | 有 → FAIL（结论降级） |
| 文件完整性 | 主机侧 `sha256` + `size_bytes` 与板上一致 | 不一致 → 重拉 |
| 对照动作 | 有一个已知测试动作（例如一次已知大小的分配/一次已知 sleep）在 trace 中可见 | 没有对照 → 只能判"采到了"，不能判"分析口径对" |

**验收必含一个已知测试动作**：零错误不等于数据正确。建议复现前先做一次"已知量"动作（例如让测试实例分配并保持一个已知大小，或起一段已知时长的忙循环），在 trace 里能对上，才说明单位/口径没跑偏。

### 4.8 Perfetto UI

在主机浏览器打开 `ui.perfetto.dev`（或用本机 Trace Processor CLI；先 `trace_processor --help` / `trace_processor_shell --help` 确认该版本支持哪个子命令，**不要**把统一 CLI 的参数套到老 `trace_processor_shell` 上）。

1. 打开 `b1-counters.pftrace`；Timeline 搜索 `demo_svc`，核对 PID 与 UPID 对应的**实例**（PID 复用会显示成两条）。
2. 只保留相关轨道，缩放到一个明确窗口：操作前 → 复现 → 恢复。
3. **配方 A（RSS 分类）**：执行 `sql/00-inventory.sql` 的轨道发现语句，再执行 `sql/01-rss-timeline.sql`（把 `-1` 换成上一步的 UPID）。结果列 `ts, value, series`，然后 Add debug track：

   | 设置 | 值 |
   |---|---|
   | Track type | Counter Track |
   | Timestamp column | `ts` |
   | Value column | `value` |
   | Pivot on | `series` |

   得到 `anon` / `file` / `shmem` / `total RSS` 四条带 UPID 的 MiB 轨道。它们来自**同一时刻对齐**的数据，不是各类别峰值简单相加。

7. 若在 tmpfs 上写入的 trace 文件让 `shmem` 曲线自己抬起来：在图上**明确标注这一段是采集自身产物**，不要算进业务内存。

### 4.9 怎么判读（口径）

- `rss_stat.size` 是**该类别当时的绝对量**，同一地址空间/类别取观测最大值；**不能 `sum(size)`**。总 RSS 要把同一时刻的分类值对齐后相加；`max(anon)+max(file)+max(shmem)` 可能拼出一个从未出现过的峰值。
- `curr` 是"当前任务与被更新地址空间是否相同"，`mm_id` 是地址空间关联键；`curr=0` 时不能把事件发出线程的 PID 当内存所属进程。进程重启/PID 复用必须用 UPID 区分。
- RSS ≠ PSS ≠ heap live ≠ 虚拟映射 ≠ CMA/dma-buf；差值**不能直接**定性为泄漏或碎片。
- `MemAvailable` 是内核估算的"无需换出即可供新负载使用的量"，不是"任意高阶连续分配一定能成功"。
- 轮询与事件可能被解析成同名/合并的 counter 轨道：先看 track ID 和实际输入再解释；需要严格证明轮询盲区时，做"1A vs 1B"两次可重复对照，而不是在同一条 trace 里假设两条独立曲线。
- **内存尖峰不是掉帧的证明**：需要时间先后 + 剂量关系 + 机制证据 + 业务侧独立打点；`sched_switch` 只能说明调度状态的一部分。
- 三态判定：能对上窗口和量级 → PASS；明确违反（如窗口被轮转、ftrace 大量丢失）→ FAIL；缺字段/未执行 → **UNKNOWN**，并写清"哪个指标不可测、哪些结论仍可用"。
- 本次能说明的：占用曲线、系统压力背景、增长是否与复现同步。**不能**说明：谁分配的、是不是泄漏真因、是否导致卡顿。最有价值的下一步：如果 H1 成立 → 方案 2 定位分配栈；如果 H2 成立（轮询看不见尖峰）→ 保持 1B 的 `rss_stat` 并配合方案 2 的短窗快照。

## 5. 方案 2：native heapprofd 分配调用栈（LD_PRELOAD）

### 5.1 定位路线与前提

- **问题**：`demo_svc` 的 malloc/new 保留（Unreleased）或累计（Total）由哪条调用栈造成。
- **前提（缺一不可）**：
  1. 进程**动态链接 glibc**（用户已给）；静态链接程序不走 LD_PRELOAD。
  2. `libheapprofd_glibc_preload.so` 与板端 tracebox **同版本、同架构（ARM64）**，且其 `NEEDED` 依赖在只读 rootfs 里**全部可解析**（不可解析时只能把缺失库放到 `/data` 并用 `LD_LIBRARY_PATH`，见 §5.3 A3）。
  3. producer/consumer 的 socket 端点**可写且不与他人冲突**。
  4. 允许**重启专门测试实例**；已运行且未预加载的进程不能靠设置环境变量回溯。
- **不覆盖**：attach 之前已存在的内存（heapprofd 不回溯）；自定义 allocator/pool 的池内对象生命周期（只能看到 backing block）；直接 mmap/设备 ioctl 分配；ART/managed heap（本机是普通 Linux，不用 `android.java_hprof`）。
- **与方案 1 的关系**：heapprofd 回答"谁分配"，RSS 曲线回答"占多少"，两者**不能互相替代**，也不能把两条独立 trace 的绝对时间戳硬拼。

### 5.2 完整采集配置（已填入目标参数）

生成命令（**必须**在主机，板端无 Python）：

```bash
python3 scripts/make_config.py native --platform linux --process demo_svc \
  --duration-ms 90000 --sampling 4096 --dump-ms 5000 > b1-heap.pbtxt
```

`duration_ms: 90000` 是**安全上限**，不是观测时长；观测时长由脚本 `OBSERVE_S=40` 控制，两者之间必须留出启动/查询/flush 的余量（见 §5.4 的算术）。

```text
# b1-heap.pbtxt —— native heapprofd；sampling 单位 bytes，时长/间隔 ms，buffer KiB
buffers { size_kb: 8192 fill_policy: RING_BUFFER }
buffers { size_kb: 4096 fill_policy: DISCARD }
buffers { size_kb: 32768 fill_policy: DISCARD }

duration_ms: 90000

data_sources {
  config {
    name: "linux.process_stats"
    target_buffer: 1
    process_stats_config {
      scan_all_processes_on_start: true
      proc_stats_poll_ms: 1000
    }
  }
}

data_sources {
  config {
    name: "linux.sys_stats"
    target_buffer: 0
    sys_stats_config {
      meminfo_period_ms: 1000
      meminfo_counters: MEMINFO_MEM_TOTAL
      meminfo_counters: MEMINFO_MEM_FREE
      meminfo_counters: MEMINFO_MEM_AVAILABLE
      meminfo_counters: MEMINFO_BUFFERS
      meminfo_counters: MEMINFO_CACHED
      meminfo_counters: MEMINFO_ANON_PAGES
      meminfo_counters: MEMINFO_SHMEM
      meminfo_counters: MEMINFO_SLAB
      meminfo_counters: MEMINFO_SWAP_TOTAL
      meminfo_counters: MEMINFO_SWAP_FREE
      meminfo_counters: MEMINFO_CMA_TOTAL
      meminfo_counters: MEMINFO_CMA_FREE
      vmstat_period_ms: 1000
      vmstat_counters: VMSTAT_NR_FREE_PAGES
      vmstat_counters: VMSTAT_PGFAULT
      vmstat_counters: VMSTAT_PGMAJFAULT
      vmstat_counters: VMSTAT_PSWPIN
      vmstat_counters: VMSTAT_PSWPOUT
    }
  }
}

data_sources {
  config {
    name: "android.heapprofd"
    target_buffer: 2
    heapprofd_config {
      sampling_interval_bytes: 4096
      process_cmdline: "demo_svc"
      shmem_size_bytes: 8388608
      block_client: false
      continuous_dump_config { dump_interval_ms: 5000 }
    }
  }
}
```

关键参数与判据：

- `sampling_interval_bytes: 4096` 是**随机字节采样的平均间隔**，不是"每 4096 字节固定打点"，更不是"每次 malloc 都记录"。已输出的 `size/count` 是估计值，**不要再乘采样间隔**。小分配热点方差大：同一 workload 重复两轮再下结论。分配量极大时可试 16384 做对照，但那是"是否还能回答问题"的取舍，不是安全/准确的固定推荐。
- `block_client: false` → 运行时缓冲不足会**丢数据或提前结束**，所以验收必须查 buffer 溢出/断开。反过来 `true` 会把采集压力传到目标线程，不能把由此产生的延迟归因给业务。**`block_client` 与 `PERFETTO_HEAPPROFD_BLOCKING_INIT` 是两件事**：前者管运行时反压，后者管启动期等待初始化。
- `shmem_size_bytes: 8388608`（8 MiB）是 heapprofd client 的共享内存预算，和 traced buffer 不是一层：调大 traced buffer 不一定解决它；长期产生速率大于处理速率时，调大谁都不解决。
- `process_cmdline: "demo_svc"` 要求**精确名字、不接受 glob**（生成器会拒绝通配符）。`argv[0]` 的实际形态（`./demo_svc` 还是绝对路径）必须与这里一致，否则会出现"有进程、有 heapprofd、但目标 heap 无数据"。本方案统一：从 `APP_DIR` 用 `./demo_svc` 启动，配置写 `demo_svc`。
  - `UNVERIFIED`：该 v57.1 构建对 `process_cmdline` 的匹配细节（是否按 basename 归一）。若冒烟出现"producer 可见但 `alloc_rows=0`"，第一件事就是改成**绝对路径字符串**，同时改启动命令与该配置字段，然后重跑冒烟。
- 数据源名：生成器在 Linux 下也输出 `android.heapprofd`（这是 Perfetto heapprofd 的注册名）。**以 `tracebox perfetto --query --long` 的实际输出为准**；若该构建注册名不同，改 `name:` 并记录依据，不要凭印象断言。
- 本配置**不含** `heaps:` 字段 → 默认 native heap（通常显示为 `libc.malloc`）。验收时用 `SELECT DISTINCT heap_name` 核对真实名字，不要假定。
- `dump_at_max`（peak 模式）**不用于本方案**：本次要"哪条栈在保留"，用 continuous dump + Unreleased；peak 模式是另一种语义，不要混着解释。
- 预算：8 + 4 + 32 MiB traced buffer（tracebox 侧）+ 8 MiB shmem + 输出文件（tmpfs，吃 RAM）+ ftrace 每 CPU 缓冲。**上板前 `df -k /data`，低于约 100 MiB 余量就先缩短时长或清理**。

### 5.3 操作步骤（【主机】/【目标机】，严格按序）

**A. 【目标机】前提检查（在任何采集之前）**

A1. 版本与 CLI：

```bash
"$TRACEBOX" --version
"$TRACEBOX" --help 2>&1 | grep -E -- '--system-sockets|--background|--txt'
```

A2. 服务与 producer 现状（只查询，不杀别人的会话）：

```bash
"$TRACEBOX" perfetto --query --long
```

- 看得见 heapprofd → 好，但只证明"生产者会注册"，不证明目标被采到。
- 看不见 → **不要**立刻判失败：heap producer 通常**按需**随会话出现；真正的判据是下面脚本里 app 启动后它是否出现。

A3. preload 依赖可解析性（rootfs 只读 = 缺库无法安装，这一步决定方案 2 能否成立）：

```bash
# 【主机】取 NEEDED 列表
readelf -d "$SDK/libheapprofd_glibc_preload.so" | grep NEEDED
# 【目标机】逐条确认存在（示例）

```

- 全部存在 → 继续。
- 有缺失 → 也不能装到只读 rootfs；把缺失库随 preload 一起推到 `$WORK_2`，运行时用 `LD_LIBRARY_PATH=$WORK_2`（见 A5 的 wrapper 注意事项）。**这属于降级路径，必须写进记录**。
- `UNVERIFIED`：主机是否有 `readelf`；是否允许执行 preload 做一次冒烟（用 `LD_PRELOAD=... /bin/sh -c 'echo ok'` 观察是否有 `error while loading shared libraries`；若卡住说明在等 producer，直接 Ctrl-C，不要设 `BLOCKING_INIT`）。

A4. 端点与写权限（`/tmp` 只读则必须换端点）：

```bash
ls -ld /tmp; touch /tmp/.b1_probe 2>/dev/null && echo tmp_writable && rm -f /tmp/.b1_probe || echo tmp_RO
ls -ld "$WORK_2"
```

A5. 目标实例形态（必须与配置字符串一致）：

```bash
# 【目标机】确认测试实例的启动形态与可执行性
ls -l /data/demo_test/demo_svc   # APP_DIR=/data/demo_test, APP_CMD=./demo_svc
```

- 若 `demo_svc` 需要在自己的 cwd 写运行时文件，`APP_DIR` 必须指到可写目录（`/data` 下）；此时启动形态是绝对路径 → **配置的 `process_cmdline` 也要跟着改**（见 §5.2 最后一条）。
- `cd` 到只读目录本身没问题（脚本只做 `cd "$APP_DIR"`），但程序自己的写操作会失败，先确认。
- `UNVERIFIED`：`/data`（tmpfs）是否挂 `noexec`。挂 noexec 时测试实例必须放在 rootfs（可执行、只读无妨），`APP_DIR` 指 rootfs 目录。

**B. 【主机】生成与推送**

```bash
python3 scripts/make_config.py native --platform linux --process demo_svc \
  --duration-ms 90000 --sampling 4096 --dump-ms 5000 > b1-heap.pbtxt

# 可选：有 v57.1 descriptor 时做第 1 级校验
python3 scripts/validate_config.py b1-heap.pbtxt --descriptor-set v571.desc

ssh "$BOARD" "mkdir -p $WORK_2"
scp b1-heap.pbtxt scripts/linux_session_lib.sh scripts/linux_heapprofd_session.sh \
    "$SDK/libheapprofd_glibc_preload.so" "$BOARD:$WORK_2/"
```

（缺库降级时再加：`scp <缺失的 lib*.so> "$BOARD:$WORK_2/"`）

**C. 【目标机】一个命令完成"起 trace → 起 app → 等 producer → 观测 → 停 → flush"**

```bash
ssh "$BOARD" "WORK=$WORK_2 TRACEBOX=$TRACEBOX OBSERVE_S=40 \
  PERFETTO_PRODUCER_SOCK_NAME=$WORK_2/producer.sock \
  PERFETTO_CONSUMER_SOCK_NAME=$WORK_2/consumer.sock \
  sh $WORK_2/linux_heapprofd_session.sh \
     $WORK_2/b1-heap.pbtxt $WORK_2/libheapprofd_glibc_preload.so \
     /data/demo_test ./demo_svc"
```

为什么是这个顺序（脚本 `linux_heapprofd_session.sh` 的实际行为，`references/05-platforms.md` §4.2）：

1. 带端点起 tracebox（`--background`，PID 写 `heap.pid`）。**若显式给了 `PERFETTO_*_SOCK_NAME`，脚本自动不加 `--system-sockets`**——这正是绕开只读 `/tmp` 与既有会话冲突的开关。
2. 轮询 `tracebox perfetto --query`（最多约 20 s）直到服务可查询；不可查询 → `exit 3`。
3. `cd APP_DIR`，以 `LD_PRELOAD=<preload> PERFETTO_HEAPPROFD_BLOCKING_INIT=1 ./demo_svc` 后台启动，PID 写 `heap.app.pid`，stdout/stderr 进 `heap.app.log`。
   - `BLOCKING_INIT=1` 的作用是等初始化完成，减少**首次 malloc 之前**的遗漏；代价是可能阻塞在初始化。脚本据此在 2 s 后检查进程是否还活着，死亡即 `exit 4`（所以**不需要**再套外层 `timeout`；若要手工重放，`timeout` 必须放在 `env` 外层，避免 timeout 本身被预加载）。
   - 不需要也不能给"已经在运行的 `demo_svc`"补环境变量：preload 只在 exec 时生效。
4. 轮询 `--query --long` 等 `heapprofd` 出现（最多 10 s）。**这一步才是 producer 真的在的判据**；不出现 → `exit 5`。
5. `sleep OBSERVE_S`（40 s）观测；期间若 tracebox 已退出 → `exit 6`（说明 `duration_ms` 不够，回 §5.4 调）。
6. `SIGTERM` 停 app（最多等 10 s，再 `KILL`）→ 等 2 s 让数据收口。
7. `stop_tracebox`：`SIGINT` 等 10 s、再 `TERM` 等 10 s，SIGINT 是 Perfetto 的优雅停止/flush 渠道；不退 → `exit 7`。
8. 等 `.pftrace` 非空（5 s），否则 `exit 8`；成功写 `heap.status`（`DONE size_bytes=...`）。

> 不要改成"先 `--background-wait` 再起 app"：heapprofd producer 未注册时它可能等不到全部数据源。也**不要**用 `sleep` 假装完成了就绪握手。

**D. 【主机/另一终端】复现**：观测窗口内执行获准的复现操作（同 §4.3 步骤 5），记录板端时钟或业务日志时间戳，用于把"某条调用栈的保留增长"对到"某个业务阶段"。

**E. 【主机】拉回**

```bash
mkdir -p ./captures/b1-heap
sh scripts/host_pull.sh "$BOARD" "$WORK_2" ./captures/b1-heap \
  heap.pftrace heap.log heap.status heap.query.txt heap.app.log
```

`heap.query.txt` 是 producer 现状的证据，`heap.app.log` 里可能有 preload 的连接/失败信息；两者都要拉回，不要只拉 trace。

**F. 【目标机】清理**（核对 sha256 后）：删本次的 `heap.pftrace`/日志；保留 tracebox/preload/脚本。确认没有残留的 `demo_svc` 测试实例（脚本已 TERM→KILL），**不要** `pkill` 任何别人的进程。

### 5.4 观测/持续时间与算术

| 参数 | 取值 | 说明 |
|---|---|---|
| `duration_ms`（配置） | 90000 | **安全上限**；会话到点即结束，不会等观测结束 |
| `OBSERVE_S`（脚本） | 40 | 真正的观测时长：足够覆盖"启动期 + 一轮复现 + 一次释放" |
| `dump_interval_ms` | 5000 | 连续快照之间 5 s；**不等于**每次 malloc 的时间 |
| `sampling_interval_bytes` | 4096 | 起点值；高分配率可试 16384 做对照 |
| 时间预算 | 起 trace+查询 ≈1–3 s，app 启动 ≥2 s，等 producer ≤10 s，观测 40 s，停 app ≈2 s，flush ≤10 s ≈ **≤67 s < 90 s** | 若 `OBSERVE_S` 调大，必须等比调大 `duration_ms`；否则 `exit 6` |

`OBSERVE_S` 的选择取决于假设：

- 看**保留/泄漏**：要跨"操作 → 释放/清理 → 稳定"三个阶段，40 s 是下限；重复两轮，比较**同一业务阶段**的同口径数值。
- 看**启动分配**：进程在 trace 已就绪后才启动（脚本顺序保证），可比对 `heap.app.log` 的启动时间与 trace 起点，但**不承诺**覆盖 pre-main/loader/全部启动分配 → 那部分标 UNKNOWN。
- 看**短尖峰（例如 150 ms 级）**：5 s 一份 dump 天然对不上；改用方案 1 的 `rss_stat`，或在确实需要 heap 峰值时用 `dump_at_max`（peak）模式，两者峰值不能混为一个指标。

### 5.5 失败条件

| 现象 | 来源 | 先查什么 / 最小下一步 |
|---|---|---|
| `ERROR: config not readable` / `preload library not readable` / `app dir not found` | 退出码 2 | scp 是否成功；这三是 tmpfs，重启/断电即丢 |
| `FAIL: tracing service not queryable` | 3 | `.log`：端点是否可写（`/tmp` 只读？`$WORK` 权限？）；`PERFETTO_*_SOCK_NAME` 是否与既有服务撞了；**不要**去 pkill 别人的 traced |
| `FAIL: test process died during startup` | 4 | `tail -30 heap.app.log`：preload 依赖解析失败、ABI 不符、`BLOCKING_INIT` 卡死、程序自身启动参数错 |
| `FAIL: heapprofd producer/data source not visible` | 5 | `heap.query.txt`：该构建是否注册 heapprofd；端点是否被 tracebox 子进程继承；**不要**只凭一次空查询判"不支持" |
| `FAIL: tracebox exited before observation ended` | 6 | `duration_ms` 太短；或会话被 `duration` 之外的 trigger 结束 |
| `FAIL: tracebox did not exit` | 7 | 手工 `SIGINT` 看是否 flush；检查输出目录是否写满（tmpfs） |
| `FAIL: heap.pftrace missing or empty` | 8 | 输出目录空间；tracebox stderr；会话其实没采到 |
| SCP 失败/空文件 | 1（`host_pull.sh`） | 重新拉；确认没被下一次 run 的 `rm -f` 覆盖 |
| trace 里有 `demo_svc` 却没有目标 heap 数据 | 数据层 | 依次查：cmdline 形态、权限、preload 是否真的加载（`/proc/<pid>/maps` 在采集期查一次，或看 app.log）、并发 profiling 拒绝、buffer 溢出 |
| 只有地址没有函数名 | 数据层 | Build ID + unstripped ELF/独立 debug 文件 + `llvm-symbolizer`；不要拿另一次构建的同名库 |
| 采集期间目标明显变慢 | 数据层 | `block_client:false` 下的丢失对照；tmpfs 输出与小内存的叠加；保留未开 profiler 的对照 |

### 5.6 采集验收（逐项 PASS / FAIL / UNKNOWN）

```sql
-- [1] 表能力：本分析器有没有 heap_profile / heap_profile_allocation
SELECT name FROM sqlite_master
WHERE name IN ('heap_profile','heap_profile_allocation') ORDER BY name;

-- [2] 时间范围
SELECT * FROM trace_bounds;

-- [3] 目标 UPID 候选（把 target_name 改成 'demo_svc'）：仅当恰好一个 data_bearing=1 才用
--     直接用 sql/00-inventory.sql 的 [CANDIDATES] 语句，不要手写简版
--     注意：Linux preload 客户端会 fork 一个继承 cmdline 的 heapprofd 子进程，通常 data_bearing=0

-- [4] 实际 heap 名（不要假定就是 libc.malloc）
SELECT upid, heap_name, COUNT(*) AS rows, SUM(CASE WHEN size > 0 THEN 1 ELSE 0 END) AS pos_rows,
       COUNT(DISTINCT ts) AS dumps, MIN(ts) AS first_ts, MAX(ts) AS last_ts
FROM heap_profile_allocation
GROUP BY upid, heap_name ORDER BY rows DESC;

-- [5] dump 可见性 / 零宽 dump（v58.x 分析器才有 heap_profile 表）
--     用 sql/10-native-dump-capability.sql 的 [2][3]，把 -1 换成 UPID、heap 名换成 [4] 的真名

-- [6] 符号覆盖度（先看有没有名字，再谈栈）
SELECT COUNT(*) AS frames,
       SUM(CASE WHEN f.name IS NOT NULL THEN 1 ELSE 0 END) AS named,
       SUM(CASE WHEN m.name IS NOT NULL THEN 1 ELSE 0 END) AS mapped
FROM stack_profile_frame f
LEFT JOIN stack_profile_mapping m ON m.id = f.mapping;

-- [7] 错误/丢失
SELECT name, idx, severity, source, value FROM stats WHERE value <> 0 ORDER BY severity, name;
```

| 检查 | PASS 判据 | 不通过时怎么写 |
|---|---|---|
| 目标 UPID | 候选里**恰好一个** `data_bearing=1`，且与 `heap.app.log` 的启动时间一致 | 多个 → 报"未解析"，按进程实例分窗口；**不要**静默取第一行，也不要因为"另一条有数据"就换目标 |
| 目标 heap | 目标 UPID + 真实 heap 名有 `alloc_rows > 0`（含正 size 行） | 0 行 → 先按 §5.5 最后一行排查，不要直接判"没有泄漏" |
| 快照数/跨度 | 活动 dump 数与 `OBSERVE_S` 同量级（40 s / 5 s ≈ 8 次触发） | 明显偏少 → 见下面"dump 可见性" |
| dump 可见性 | 用 `sql/10` 区分"采集失败"与"窗口不可见" | `zero_dur_dumps == dumps` → 精确持有区间 **UNKNOWN**，但总量/分配释放/符号仍可判 |
| 符号 | `named` 占比可接受，mapping 名能对上模块 | 只有地址 → 先按模块归因，标注"定位粒度=模块" |
| 错误 | `stats` 无非零的 buffer 溢出/断开/unwind 失败 | 有 → 缩小目标/降采样/缩短时长后重跑，结论降级 |
| 对照 | 有一次"已知分配 + 已知释放"的动作，能在 profile 中看到对应的正/负变化 | 没有 → 只能判"采到了 profile"，不能判"分析正确" |

**关于 dump 数与 `dur=0`（版本条件，务必先判再解释）**：

- **dump 的窗口结束时刻只随"带非零时间戳的分配"推进**；长时间只持有、不新分配时，周期 dump 的 `window_end` 相同。
- **分析器按 `(upid, window_end, heap_name)` 去重**，所以 `dump_interval_ms` **不等于**可见 dump 数：触发次数 `≈ floor((运行时长-phase)/interval)+1`，可见行数还要求每次窗口有前进。
- **旧采集端不提供窗口起点**（`ProfilePacket.ProcessHeapSamples.start_timestamp` 标注 *Unset on older producers*）：缺失时分析器令 `ts == ts_end` → `dur = 0`，**窗口区间不可知**。
- 因此板端 v57.1 + 较新主机分析器时，**6 份 dump、`dur` 全 0 是预期组合**（`references/02-native.md` 的采集器行为，非本包在本机的实测）。此时：`dur=0` ≠ 采集失败；但**精确持有区间是 UNKNOWN**，只能用上界证据，且上界证据**不得**反过来断言"实际持有比预期短"。想把可见 dump 变多，要么在持有期保留低开销分配让窗口前进，要么换发布该字段的采集器版本——**不要**去改 SQL 阈值凑通过。

### 5.7 Perfetto UI

1. 打开 `heap.pftrace`，先做 `sql/00-inventory.sql` 验收，确认 UPID。
2. 展开目标进程的 **Native heap profile** 轨道，点一段 profile slice：
   - **Unreleased Malloc Size / Count**：追踪范围内分配而尚未配对释放的**估计量**，用于"哪条路径保留了内存"；
   - **Total Malloc Size / Count**：累计流量（含后来释放的），用于"谁反复大量分配"。
   - 火焰图宽度由**所选指标**决定，**不是函数执行耗时**；self 是以该帧为叶子的量，cumulative 含下游。要定位调用者就保留足够父栈，不要只说"malloc 很大"。
3. **dump 级 live 曲线**：`sql/03-native-live.sql`（先填 UPID/heap/窗口）→ Counter Track，`ts` / `value` / `series`。它是**快照分辨率**的保留量估计，不是逐次 malloc 曲线，也不适用于 ART allocation 或 `dump_at_max`。
4. **热点调用栈表**：`sql/04-native-callstacks.sql`（先过滤 UPID/heap/时间，再做递归聚合）。返回的是"帧/调用点的累计值表"，**不是时间轴**；祖先栈会重复出现下游量，**绝不能**把结果求和当进程内存。整机概览只有确实需要时才用 `sql/05-native-global-summary.sql`，并且标题要写清"全进程汇总"，不能标成 `demo_svc`。
5. **和方案 1 对时**：优先在同一 trace 内比较（本配置已带 process_stats/sys_stats）；两次独立 trace 之间只比较**模式**（形状/量级/先后），不按绝对 ns 逐点对齐，除非有明确时钟对齐证据。
6. 缺符号时图上只有地址：先按 mapping/Build ID 归因并标注，再按 `references/06-quality.md` §5 做离线符号化（`trace_processor bundle --symbol-paths <unstripped> --verbose in.pftrace out.tar`；旧 SDK 用其 `traceconv/trace_processor` 对应路径，不混用新旧 CLI）。命令返回 0 也要检查"还有多少帧未解析"。

### 5.8 怎么判读（口径）

- `heap_profile_allocation` 用正/负行表达分配/释放变化。**先按 `(upid, heap_name, ts)` 聚合，再累计**得到追踪范围内的 live 估计；只取区间内正负变化得到的是**净变化**，不是区间结束时的完整 live（需要窗口之前的追踪基线）。
- continuous dump 按快照汇总，**不能从 dump 时间反推每次 malloc 的真实发生时刻**；5 s 一份 dump 不会还原 150 ms 的 live 尖峰。
- **持续未释放只是"泄漏候选"**：先定义"对象何时应该释放"，再重复操作/清理/等待后比较同一业务阶段。正常缓存、池扩容、异步释放不能仅凭"红色/火焰图很宽"判泄漏。
- 高 **Total** 说明分配活跃，**不独自证明**锁竞争、CPU 开销或掉帧；profiler 采集成功最多证明 schema/运行条件/有数据，**不能**证明性能因果。
- `RSS vs heap live` 不一致时按顺序核对：覆盖时间 → 进程/heap → 采样 → 驻留/映射类别 → allocator 保留；**不要**写 `heap <= malloc_info <= RSS` 这种普遍不成立的大小链，也不要仅凭差值归因"碎片"。
- 三态：总量、分配/释放、dump 数、符号 → 可判 PASS/FAIL；精确持有区间（`dur=0`）、pre-main 启动分配、自定义 allocator 池内对象 → **UNKNOWN**，写清"哪个指标不可测、哪些结论仍可用"。
- 最有价值的下一步：拿到调用栈后，用方案 1 的同负载 trace 验证"该路径的保留增长是否与 RSS 增长同步"，并加业务侧独立打点确认是否影响延迟——**同步不等于因果**。

## 6. 两方案对照与资源预算

| 项 | 方案 1（1B） | 方案 2 |
|---|---|---|
| 目标进程扰动 | 无（不重启、不注入） | 重启测试实例 + `BLOCKING_INIT` 可能阻塞初始化 |
| traced buffer | 8 MiB ring + 4 MiB discard | 8 + 4 + 32 MiB discard |
| ftrace | 1024 KiB/CPU（仅 rss_stat；1C 再加 sched） | 不开 ftrace |
| 其它内存 | 输出文件（tmpfs，吃 RAM 并计 shmem） | 上述 + 8 MiB heapprofd shmem + `.so` + 日志 |
| 时长 | 30 s（可重复 2 轮） | 上限 90 s / 观测 40 s |
| 串行要求 | 先跑；与方案 2 不并行 | 后跑；与方案 1 不并行 |
| 端点 | 默认 `--system-sockets` 可用则用；`/tmp` 只读时同方案 2 换端点（方案 1 的脚本固定不加 `--system-sockets`，见下） | 显式 `PERFETTO_*_SOCK_NAME` 到 `/data` |

> 方案 1 的 `linux_trace_session.sh` 直接 `tracebox --txt -c ... --background`，**不传** `--system-sockets`，因此走该构建的默认端点；若默认端点在只读 `/tmp`，需要用 `PERFETTO_*_SOCK_NAME` 环境变量（脚本不会清掉环境，tracebox 会继承）或改用 heapprofd 脚本的同等思路。这一点 `UNVERIFIED`，必须在板上用第一条 5 s 冒烟确认——这也是"先跑方案 1 做冒烟"的另一个理由。

三条不可妥协的收尾纪律：

1. **只恢复本次会话实际改动、且仍由本次拥有的设置**；`survey.sh` 不改任何设置，不要顺手清空 trace/关事件/把 buffer 恢复成硬编码值。
2. **不 `pkill`/`killall` 任何 traced/tracebox**；只对本次记录的 PID 发 `SIGINT`。

## 8. 一页版执行顺序（把上面压成 checklist）

**第一轮：冒烟（约 10 s，零业务影响）**
1. 【目标机】`survey.sh` + `--events` → 记 tracefs、rss_stat/sched 有无、`df`、`/tmp` 可写性。
2. 【目标机】`tracebox --version` / `--help` / `perfetto --query --long`。
3. 【主机】`make_config.py overview --duration-ms 5000` → 推 → `linux_trace_session.sh ... 20` → 拉回 → `trace_bounds` 非空、有 process 表。
   - 若冒烟失败：先修端点/路径/权限，**不要**继续做 heapprofd。

**第二轮：方案 1 正式（30 s × 2 轮）**
4. 【主机】`make_config.py rss-spike --duration-ms 30000`（无 rss_stat 则 overview）→ 推。
5. 【目标机】`WORK/TRACEBOX ... linux_trace_session.sh cfg b1-counters 45`；【另一终端】窗口内复现 + 打点。
6. 【主机】`host_pull.sh` 拉 `.pftrace/.log/.status/.pid` → 核对 sha256。
7. 【主机】`sql/00-inventory` → UPID → `sql/01-rss-timeline` → Counter Track（ts/value/series）→ 记录观察与 UNKNOWN。

**第三轮：方案 2（上限 90 s / 观测 40 s）**
8. 【目标机】preload `NEEDED` 逐条确认；端点与 `APP_DIR` 形态确认。
9. 【主机】`make_config.py native --process demo_svc --duration-ms 90000` → 推（+ preload）。
10. 【目标机】`WORK/TRACEBOX/OBSERVE_S=40 PERFETTO_*_SOCK_NAME=... sh linux_heapprofd_session.sh cfg preload /data/demo_test ./demo_svc`。
11. 【主机】`host_pull.sh` 拉 `heap.pftrace heap.log heap.status heap.query.txt heap.app.log`。
12. 【主机】`sql/00-inventory` [CANDIDATES] → 唯一 UPID → `sql/10` 判 dump 可见性 → `03-native-live` + `04-native-callstacks` + UI 火焰图（Unreleased / Total）。
13. 【主机】`stats` 查 buffer 溢出/断开/unwind；`stack_profile_frame` 查符号；缺符号走离线符号化。
14. 【目标机】清理本次产物，确认无残留测试实例，不动他人会话。

**结论怎么写**：先写实际观察（UPID、窗口、指标与量级），再写推论与支持证据，最后写仍缺的因果环节；未执行的设备/UI 项一律标 `UNVERIFIED`，缺证据的判据一律标 `UNKNOWN` 并写清"哪个指标不可测、哪些结论仍可用"。
