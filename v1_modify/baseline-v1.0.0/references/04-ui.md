# Perfetto UI：从正确数据到可读图表

依据：[S01/S04/S06/S11/S12](sources.md)，可选新版功能 [S27](sources.md)。不要求画一个模仿Perfetto的图片；交付真实trace、SQL与原生UI操作。图表是否存在由实际数据决定。

## 通用布局

打开本次原始 `.pftrace` / helper 的 `raw-trace`，先做 [采集验收](06-quality.md)。在 Timeline 搜索目标进程，核对 PID 与 UPID对应的实例；只保留相关轨道，缩放到一个明确的“操作前—复现—恢复”时间窗口。

建议按“业务阶段/帧事件→系统内存→目标RSS→内核分配/回收→heap profile”顺序固定轨道。轨道标题带进程、指标和单位；用同一窗口比较，不通过裁掉异常段、平滑尖峰或重设零点制造结论。统一MiB只是展示转换，保存原始bytes用于复算。

## 配方 A：RSS 分类与系统压力

先运行 `sql/00-inventory.sql` 的轨道发现语句，再运行 `sql/01-rss-timeline.sql`。其中 `ts` 是trace绝对纳秒，`value` 是MiB，`series`包含类别与UPID。

在查询结果的 Timeline / Add debug track 中选择：

| 设置 | 值 |
|---|---|
| Track type | Counter Track |
| Timestamp column | ts |
| Value column | value |
| Pivot on | series |

得到anon/file/shmem/总RSS分别命名的轨道。它们不是每个类别峰值简单叠加；总RSS来自同时刻对齐的数据。若标准库不存在，使用 `sql/02-counter-fallback.sql` 查看原始采样点，并检查单位；不能为了省事将所有counter都除1048576。

系统侧从 inventory 选 MemAvailable/CmaFree 对应 track ID，确认原值单位后转MiB；vmstat另建标注“pages/events”的轨道。无CMA字段不画一条零值CMA线。

只固定本次问题需要的几条轨道；进程太多时先按UPID筛选再Add debug track。事件/轮询可能合流到同名轨道，需按实际来源解释。

## 配方 B：Native 火焰图与dump级live曲线

展开目标进程下 Native heap profile，点击一段profile slice。先选 Unreleased Malloc Size 看保留量，再切 Total Malloc Size/Count 看分配流量。连续slice可以选择一段窗口，但选区统计与“这个时刻完整live”不是同一个概念，按02-native的时间口径解释。

火焰图宽度由选定指标决定，**不是函数执行耗时**。函数的self量是以它为归因叶子的量；cumulative包含下层路径。点击宽栈逐级查看，必要时搜索业务模块/函数；先保留足够父栈再定位到调用者，避免只说“malloc很大”。

配套执行 `sql/03-native-live.sql`→Counter Track，映射ts/value/series，可展示普通Native profile的dump级保留量估计。它不是每次malloc的逐事件曲线，不适用于ART allocation或dump_at_max。150ms峰值可能在一次5秒dump之前已释放。

热点表用 `sql/04-native-callstacks.sql`，先填写选定UPID与时间。仅需整份trace的全进程概览时才用 `sql/05-native-global-summary.sql`；两者标题必须区分，避免把整机汇总标为cam-service。

缺符号时图形可能只有地址。先按模块/Build ID检查并符号化，不能承诺在没有debug信息时出现源码行号。

## 配方 C：ART 对象图与支配树

打开graph trace中的heap快照标记，进入Heap Dump Explorer；有的UI版本也提供侧栏入口或Flamegraph中的Drill down。确认进程和快照时刻。

| 面板/视图 | 适合的问题 |
|---|---|
| Overview / Classes | 哪些类型对象多、浅大小大 |
| Objects / instance detail | 选定对象有哪些字段、引用和反向引用（取决于输入格式） |
| shortest path to GC root | 一条能解释对象可达的短路径 |
| Dominators / dominator path | 谁独占地保持这批对象可达 |
| Flamegraph Top Down / Bottom Up | 从root往下看，或从对象类型反查持有者 |
| Strings / Arrays / Bitmaps | 有完整HPROF内容时看重复内容与位图 |
| Callstack | 支持且采到了OOME调用栈时，查看失败分配线程 |

在指标中区分Object Size/Count与Dominated Object Size/Count。最短路径的子树不等于可释放的独占保留量。完整HPROF与Perfetto graph都能提供结构分析，但graph不能自动展示不存在的文本/像素。

当前Explorer的过滤器包含Show Stack、Hide Stack、Show From Frame、Hide Frame及Pivot（可见时对应SS/HS/SFF/HF/P前缀）。先按UI提示使用；Hide Frame只是折叠栈帧，不意味着从统计中删除其内存。不要把过滤后的局部图当全堆总量。

用 `sql/06-art-snapshots.sql` 比较同UPID、同类的不同graph_sample_ts；先看完整快照和对象数，再追实例。不要连接不同快照的所有对象后求和当“当前堆”。

## 配方 D：CMA/回收/业务事件同轴

`sql/07-kernel-events.sql` 输出 `ts,dur=0,name,series`，Add debug track选Slice Track，映射Timestamp=ts、Duration=dur、Name=name、Pivot=series。这是**事件标记轨道**，零时长不代表操作真的耗时为零。

要画CMA分配或direct reclaim耗时条，先依据实际格式和正确配对键生成 `ts=start_ts,dur=end_ts-start_ts`。并发或缺事件的配对不可信时，只画原始标记，不伪造持续时间。把帧完成/帧间隔与内存变化放同轴，说明相关性和仍待证明的因果环节。

## 配方 E：已有 pprof

直接打开`.pprof`或gzip压缩的profile，选择侧栏Aggregate Profiles，先选文件/scope，再选sample type与unit。`alloc_space`与`inuse_space`、bytes与count是不同口径；按文件实际提供的名称选择。

这是一张独立聚合火焰图，不应该期待RSS曲线或逐分配时间轴。多个metric不能相加成“总内存”。详见07-internals-and-pprof及`sql/08-pprof.sql`。

## 可选：Memscope / Memory Overview

当前官方另有Memscope实时内存浏览、Memory Overview事后分类浏览入口。可用设备连接支持时，在侧栏Memscope观察系统和进程趋势；Memory Overview适合从采到的smaps与heap数据进一步下钻。它们仍在活跃开发，特定smaps录制能力还有Android构建版本限制，因此本Skill不把它们作为X5 v57.1基础方案的必需条件；没有smaps不会凭RSS自动补出完整映射组成图。

## 可视化验收

最终展示或交付时写明：进程/UPID、时间窗口、数据源、单位、采样/快照间隔、是否有丢失和符号缺失。至少能从图回到对应SQL或原始事件。没有实际打开UI验证，就写“UI操作配方已给出”，不写“已验证UI显示正常”。
