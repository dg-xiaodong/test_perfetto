# B1 方案：ARM64 Linux 上 `demo_svc` 的采集生命周期

> 边界声明：本文只做方案、配置与验收设计，**没有执行任何命令、没有连接设备、没有产生实测数据**。文中的时间、条数和量级都是“计划参数”或“应看到的判据”，不是设备实测结果；凡依赖目标版本/构建/挂载/符号的条件都单独标为**待实测**或**UNKNOWN**。
>
> 已知环境（题面）：ARM64 Linux、`demo_svc` 动态链接 glibc、允许重启专门的测试实例、rootfs 只读、`/data` 可写但是 tmpfs、板端 tracebox v57.1、主机有对应分析器、板端无 Python/无外网、SSH/SCP 可用、已有匹配的 `libheapprofd_glibc_preload.so`。

## 0. 结论：两套方案各自的定位

| | 方案 A：不注入的低开销 trace | 方案 B：native heapprofd 调用栈 |
|---|---|---|
| 回答的问题 | 何时涨、涨多少、系统压力、线程调度是否同窗 | 哪条调用栈在分配、哪些调用栈的分配未释放 |
| 数据源 | `linux.process_stats` + `linux.sys_stats`；可选 `linux.ftrace`（`sched/sched_switch`，`kmem/rss_stat` 需确认存在） | `android.heapprofd` + 同一份计数器（用于 UPID/时间对齐） |
| 是否改目标启动 | 否，不需要 LD_PRELOAD | 是，专用测试实例必须以 LD_PRELOAD 启动 |
| 能否回溯已运行进程 | 只能从现在往后观测 | **不能**；必须重启专用实例再预加载 |
| 典型开销 | 轮询 1s + 12MiB traced buffer；加 sched 时每 CPU 1MiB ftrace buffer | traced buffer 44MiB + 客户端 shmem 8MiB + 采样/展开开销 |
| 主要盲区 | 不能归因到调用栈；1s 轮询可能漏短尖峰；RSS 分类不等于 malloc | heap 是采样估计；不等于 RSS；看不到直接 mmap/设备 buffer/自定义 allocator 内部对象 |
| 建议先做 | 是，先建立基线与时间线 | 在确认工具链能力、并能重启专用实例后再做 |

两套方案共用同一条“主机生成与验收、目标机只执行采集、跑完立即拉回”的流程。**只缺 3 个会改变具体命令的输入**：① SSH 的 `用户@地址`；② `/data`、`/tmp` 的挂载标志（是否 `noexec`、可写、余量）与 tracefs 实际路径；③ 专用测试实例的启动命令/参数。其余项都按板端只读勘察结果决定，不凭记忆假设。

## 1. 路线、待验证假设与不覆盖范围

### 方案 A

- 待验证假设：“`demo_svc` 的 RSS 变化与某个业务阶段/系统压力/调度延迟同窗”。
- 所选数据源：进程级计数器（RSS 等）、系统级 meminfo/vmstat；必要时才加 `sched_switch` 与 `rss_stat`。
- 不覆盖：分配调用栈、malloc live/泄漏、直接 `mmap`、设备/CMA/dma-buf 归属、ART（本机不适用）。RSS 上涨也不自动等于泄漏，更不能单独证明掉帧因果。

### 方案 B

- 待验证假设：“某条业务路径在持续分配且未释放，或某阶段分配量异常高”。
- 所选数据源：heapprofd 的 libc malloc heap（普通 native 增量 profile，5s 连续 dump）。
- 不覆盖：RSS/驻留页、启动前已发生的分配（不回溯）、直接 `mmap`/ioctl/设备页、自定义 pool 内部对象生命周期、Java heap。`Unreleased` 只是泄漏**候选**，`Total` 只是分配流量，二者都不等于进程内存占用。

如果最终要解释“RSS 高但 heap 不高”，按“覆盖时间→进程/heap→采样→映射/驻留类别→allocator 保留”的顺序核对，不直接把差值定性为碎片。

### 2.2【主机 + 目标机】只读勘察

把只读脚本推过去，采集环境和事件清单（脚本不修改系统、不 mount、不改 sysctl）：

```bash
# 【主机】
BOARD='<user>@<board-address>'
WORK="$PWD/v101-b1"; mkdir -p "$WORK"
scp "$SKILL_DIR/scripts/survey.sh" "$BOARD:/data/survey.sh"
ssh "$BOARD" 'sh /data/survey.sh'            > "$WORK/survey.txt" 2>&1
ssh "$BOARD" 'sh /data/survey.sh --events'   > "$WORK/available_events.txt" 2>&1
```

逐项记录并判定（这些结果直接决定后面的分支）：

| 检查项 | 判定 | 对方案的影响 |
|---|---|---|
| tracefs 路径与 `available_events` 是否非空 | 实际可读且有内容 | 为空/不可读 → 方案 A 的 ftrace 分支不可用，只能计数器 |
| `sched:sched_switch` 是否存在 | events 中查 | 不存在 → 不加 sched，A2 取消 |
| `kmem:rss_stat` 是否存在 | events 中查 | 不存在 → 短尖峰只能靠 1s 轮询，明确盲区 |
| `/data` 挂载标志与余量 | `/proc/mounts` + `df -k /data` | `noexec` → 不能从 `/data` 执行 tracebox/preload；余量不足 → 缩短时长或降采样 |
| `/tmp` 是否可写 | `/proc/mounts` + `df -k /tmp` | tracebox 的 socket/临时目录需要可写；只读 rootfs 下 `/tmp` 不一定可用 |
| `/dev/shm` 是否可写 | `df -k /dev/shm` | 作为 shmem/socket 的备选检查项，不预设一定可用 |
| 页大小、glibc 版本、CMA/内存余量 | survey 输出 | 用于单位换算与预算；CMA 字段缺失时按 UNKNOWN，不填零 |
| perf paranoid | 仅记录 | 本方案**不使用** `linux.perf`，不需要改它 |

若 `/data` 是 tmpfs，则 trace、测试日志、heapprofd 的 buffer 与输出文件都**占 RAM**；采集期间还要留出系统与目标进程的余量，并做到跑完立即拉回、立即清理。

### 2.3【主机】二进制与预加载库静态检查

这些检查只在主机做，板端不需要 Python/readelf：

```bash

python3 scripts/validate_config.py "$WORK/native.pbtxt" \
  --deploy-name demo_svc --binary "$SDK/demo_svc"
#    PASS: 含 PT_INTERP（动态链接），且配置目标名与启动名 basename 一致
#    FAIL: 无 PT_INTERP → 方案 B 直接不可用，只能走 A 或换构建
#    注意：这里的 demo_svc 必须是"实际部署到板端的那份"或与其 Build ID 一致的副本

# 2) preload 库架构与依赖（在主机查看 SDK 副本）
file "$SDK/libheapprofd_glibc_preload.so"
readelf -h "$SDK/libheapprofd_glibc_preload.so" | grep -E 'Class|Machine'
readelf -d "$SDK/libheapprofd_glibc_preload.so" | grep NEEDED
readelf -V "$SDK/libheapprofd_glibc_preload.so" | grep -o 'GLIBC_[0-9.]*' | sort -Vu | tail
#    要求：AArch64；NEEDED 库在板端可解析；所需最高 GLIBC 版本 ≤ 板端 glibc（题面称匹配，仍需核实）
```

### 2.4【主机】版本与 schema 条件

- 板端采集器：tracebox v57.1；主机分析器：题面称“对应”，仍要记录实际版本（`trace_processor_shell --help` 或统一 `trace_processor --help`，两者参数语法不同，不要混用）。
- 有与 v57.1 匹配的 Perfetto 源码与 protoc 时，生成 descriptor 并做精确校验：

```bash
cd "$PERFETTO_SRC_v571"
```

## 3. 变量作用域与 SSH/SCP 约定

| 名称 | 所在位置 | 作用域 | 规则 |
|---|---|---|---|
| `BOARD` / `WORK` / `SDK` / `TRACEBOX_ARM64` | 主机 shell | 仅主机当前 shell | 不导出给远端；写进 `ssh '...'` 单引号内不会被主机展开 |
| `/data/...` 路径 | 目标机 | 远端绝对路径 | 远端命令用单引号整体包住，避免主机变量插值 |
| `LD_PRELOAD=/data/libheapprofd_glibc_preload.so` | 目标机 | **只作用于被启动的 demo_svc 这一条命令** | 用 `env LD_PRELOAD=... 命令` 前缀；**绝不在启动 tracebox 的 shell 里 export**，否则 tracebox/子进程也被预加载 |
| `PERFETTO_HEAPPROFD_BLOCKING_INIT=1` | 目标机 | 只作用于 demo_svc | 同上；它让首次分配等待 heapprofd 初始化，socket/目标名不对时会挂住，必须配 `timeout` |
| 脚本内变量（`EV`/`TRACE`/`LOG`） | 目标机 `/data/run_*.sh` | 仅该脚本进程 | 不写系统配置；不修改 rootfs |
| `LD_LIBRARY_PATH` / `TMPDIR` 等 | 目标机 | 不全局设置 | 是否被 tracebox 识别需查该构建 `--help`/日志，不凭记忆假设生效 |

其他约定：

- 只启动/停止**本次专用测试实例**；不 `pkill` 别人的 tracing 会话，不重启生产服务，不关闭 SELinux，不改安全 sysctl，不清 tracefs。
- 输出文件名带本次会话标识，避免覆盖未拉回的旧证据。
- 靶进程同名多实例时，用启动时间/PID 区分；分析时以 UPID 为准，不按名字猜。

时间关联：工作负载日志用 `date +%s%N` 记录只是 CLOCK_REALTIME；Perfetto 的 `ts` 是 trace 时钟。两者不能直接相减；若需要严格对齐，另行建立时钟换算并标为 UNKNOWN，直到有证据。

## 4. 方案 A：不注入的低开销 trace（sched / RSS / 系统计数器）

### 4.1 数据源、持续时间与开销

- **A1 基线（默认执行）**：`linux.process_stats`（`scan_all_processes_on_start:true`，`proc_stats_poll_ms:1000`）+ `linux.sys_stats`（meminfo/vmstat 各 1000ms）。`duration_ms:30000`。不开启任何 ftrace，开销最小；进程在采集开始后启动的，由周期轮询发现（1s 粒度，启动瞬间的极短阶段可能不在第一个样本里）。
- **A2 可选加 sched（仅在需要“内存变化是否同窗伴随调度延迟”时）**：在 A1 基础上追加 `linux.ftrace` 的 `sched/sched_switch`，`duration_ms:10000`。`sched_switch` 是额外高频事件，属于**显式增加开销**，不默认与 30s 基线一起开。
- **A2' 可选 `kmem/rss_stat`**：只有当 `available_events` 确认存在时才加。它提供事件驱动的 RSS 变化，能改善 1s 轮询盲区；但仍是内核记账事件，不是每次 malloc 的逐笔日志，也不能 `sum(size)`。
- 预算：A1 的 traced buffers 为 8MiB + 4MiB；A2 另加每 CPU 1MiB ftrace buffer（`buffer_size_kb:1024`，总占用 = CPU 数 × 1MiB）和 250ms drain。tmpfs 上这些同样吃 RAM。

**不重启目标的替代**：如果本次不重启 `demo_svc`，仍可采 A1 观察运行中行为，但“启动阶段”与“操作前基线”的覆盖就是 UNKNOWN；题面允许重启专用实例，建议重启后按 4.4 的顺序执行。

### 4.2 A1 完整配置（`overview`）

```bash
# 【主机】生成（本次未执行，下面给出模板展开结果供核对）

  --duration-ms 30000 --poll-ms 1000 > "$WORK/a1_counters.pbtxt"
```

### 4.3 A2 完整追加块（sched；rss_stat 按需）

生成器的 `kernel-pressure --sched` 会同时挑选目标实际存在的 cma/oom/直接回收/部分 compaction 事件再附加 `sched_switch`；如果只是要 sched、或目标没有这些压力事件，按“在 A1 末尾追加一个完整的 `linux.ftrace` data source”合并，不能只丢一个片段给用户猜位置。同时把 `duration_ms` 改成 10000：

```text
data_sources {
  config {
    name: "linux.ftrace"
    target_buffer: 0
    ftrace_config {
      buffer_size_kb: 1024
      drain_period_ms: 250
      ftrace_events: "sched/sched_switch"
      # 仅当 available_events 确认存在 kmem:rss_stat 时，才额外加下面一行：
      # ftrace_events: "kmem/rss_stat"
    }
  }
}
```

```bash
# 【主机】若目标确有压力事件，也可直接生成 A2 变体
python3 scripts/make_config.py kernel-pressure --platform linux \
  --events "$WORK/available_events.txt" --sched --duration-ms 10000 \
  > "$WORK/a2_pressure_sched.pbtxt"
# 若事件不满足生成器条件，它会报错；此时不要伪造事件，用上面的手工合并完整配置并标记为模板变体
```

### 4.4 启动顺序、观测窗口与执行位置

顺序原则：**先起采集 → 记录基线 → 启动/恢复专用测试实例并执行测试动作 → 恢复观察 → 让有限时长会话自然结束**。计数器没有 heapprofd 那样的“就绪握手”，脚本里的 `sleep` 只是工作负载分段，**不作为“已采到”的证据**；最终用 `trace_bounds` 与 counter 行数验收。

推荐用一个目标机脚本保证顺序与标记（由主机推送；仅操作本次实例）：

```sh
#!/bin/sh
# /data/run_a1.sh ——【目标机】执行；只操作本次专用测试实例
set -u
EV=/data/b1_events.log
echo "trace_start $(date +%s%N)" >> "$EV"
/data/tracebox --txt -c /data/a1_counters.pbtxt \
  -o /data/a1_counters.pftrace > /data/a1_counters.log 2>&1 &
TPID=$!

sleep 5
echo "workload_start $(date +%s%N)" >> "$EV"
/data/demo_svc <获准的测试参数> >> /data/demo_svc_test.log 2>&1 &
DPID=$!

sleep 15
echo "workload_stop $(date +%s%N)" >> "$EV"
kill -TERM "$DPID" 2>/dev/null || true

wait "$TPID"
echo "trace_exit=$? $(date +%s%N)" >> "$EV"
```

```bash
# 【主机】首次准备与启动
scp "$WORK/a1_counters.pbtxt" "$WORK/run_a1.sh" "$BOARD:/data/"
ssh "$BOARD" 'chmod +x /data/run_a1.sh; sh /data/run_a1.sh'
# A2 变体同法：推送 a2 配置，脚本里的文件名和 duration 对应替换
```

30s 内的观测分段：0–5s 基线（实例未起或旧实例状态），5–20s 测试负载，20–30s 恢复/收尾。若实例原本常驻，先记录“重启前”的 PID/启动时间，再只停本次专用实例。

### 4.5 停止、flush、SCP 与清理

- 首选**自然结束**（`duration_ms` 到点）；不要用“跑一半就拉文件”的方式验收。
- 需要提前停时，只对本次 `TPID`（或精确匹配本次命令行的进程）发 `SIGTERM`，等进程退出、日志落盘后再拉；不要 `pkill -f tracebox` 波及别人的会话。v57.1 的 SIGTERM flush 细节属于**待实测**，能在 30s 内结束时不必冒这个风险。
- 拉回并校验：

```bash
# 【主机】
scp "$BOARD:/data/a1_counters.pftrace" "$BOARD:/data/a1_counters.log" \
    "$BOARD:/data/b1_events.log" "$WORK/"
ssh "$BOARD" 'sha256sum /data/a1_counters.pftrace'
sha256sum "$WORK/a1_counters.pftrace"
```

- 清理只删本次产物（tracebox/库/配置可留着复用），因为 `/data` 是 tmpfs，及时释放 RAM；不清理 tracefs、不把 buffer 恢复成某个硬编码值。

### 4.6 方案 A 的失败条件与最小下一步

| 现象 | 先查 | 处理 |
|---|---|---|
| tracebox 启动即失败 | `/tmp` 是否可写、tracefs 是否可访问、rootfs 只读导致的 socket/临时目录问题 | 换到可写目录/按该构建 `--help` 确认 socket 目录参数；无法解决就报告，不 remount 系统盘 |
| 配置被拒 | stderr、字段/枚举拼写、采集器版本 | 用匹配 descriptor 校验，保留失败日志，不删字段“试到能跑” |
| trace 有系统计数器但无目标进程 | 目标是否在采集期启动、UPID 是否选错、同名多实例 | 按 4.4 顺序重启实例；分析按 UPID/PID/start_ts 对齐 |
| 没有 sched 数据 | `available_events` 是否真有 `sched_switch`、ftrace buffer/丢事件 | 无事件就不加；有事件但为空时查 stats 与 trace_bounds，不伪造轨道 |
| 没有 rss_stat | events 清单 | 退回 1s 轮询并明确“短尖峰可能漏”，不把轮询说成事件级 |
| 采样点明显偏少 | `proc_stats_poll_ms`、会话实际时长、buffer 轮转 | 检查 trace_bounds 与 stats；必要时延长基线或缩短采集范围 |
| `/data` 余量快速下降/系统变慢 | `df -k /data`、trace 文件大小、tmpfs 占 RAM | 立即停采、拉回、清理；缩短时长或降低轮询频率 |
| 采集后业务异常 | 是否有对照、采集开销 | 保留无采集对照；不把采集扰动归因给业务 |

### 4.7 方案 A 的采集验收、SQL 与 UI

【主机】先执行 `sql/00-inventory.sql` 的独立检查语句（`trace_bounds`、`process`、`counter_track`/`process_counter_track`、`stats`），再执行：

- `sql/01-rss-timeline.sql`：把 `-1` 换成目标 UPID，得到 anon/file/shmem/总 RSS 的 MiB 序列（总 RSS 来自同一时刻对齐值，不是各类别峰值相加）。
- `sql/02-counter-fallback.sql`：本机标准库缺失时，用 inventory 选出的真实 `track_id` 看原始采样点；**保留原生单位**，核实后再换算。
- `sql/07-kernel-events.sql`：A2 的 sched 事件标记（`ts,dur=0,name,series`），UI 里 Add debug track → Slice Track；零时长只代表标记，不代表操作耗时。

UI（Counter Track）映射：Timestamp=`ts`，Value=`value`，Pivot=`series`；系统计数器从 inventory 里选对应 track，确认单位后再转 MiB。事件/轮询可能被解析成同名/合并轨道，要按实际 track 来源解释，不承诺“天然有独立轮询曲线”。

**四态验收（本次需实测判定）**：

| 检查 | PASS | FAIL | UNKNOWN |
|---|---|---|---|
| 时间范围 | `trace_bounds` 覆盖完整 30s（含基线/负载/恢复） | 开头或结尾被轮转/截断，关键段缺失 | 未执行采集 |
| 目标身份 | 恰有一个 `demo_svc` UPID，PID/start_ts 与本次实例一致 | 选到别的实例或 PID 复用导致混用 | 多实例无法区分 |
| 计数器数据 | 进程 RSS/系统 meminfo 行数约等于“时长/轮询周期”，窗口内连续 | 行数为 0 或时间断档且无法解释 | 标准库/字段不可用 |
| sched（A2） | `sched_switch` 有实际数据，`trace_bounds` 覆盖窗口 | 配置了但无事件且 events 清单确认存在 | 未加 A2 或事件不存在 |
| rss_stat（可选） | 事件行存在，按 member 绝对值读、不 sum | 事件丢失严重且影响判读 | 内核无该事件 |
| 错误统计 | stats 中无影响结论的非零错误/数据丢失 | 明确 buffer 溢出/丢事件导致结论不可用 | 诊断字段缺失 |
| 结论口径 | 只描述占用/时间相关性与盲区 | 把 RSS 上涨直接判成泄漏/掉帧根因 | 缺业务标记与对照 |

### 4.8 方案 A 能说明什么、不能说明什么

- 能说明：目标 RSS 在哪个阶段变化、系统 MemAvailable/回收活动是否同窗、调度切换是否在时间上靠近；`rss_stat` 存在时能改善短时尖峰的观测。
- 不能说明：谁分配、是否泄漏、RSS 与帧延迟的因果关系。1s 轮询会漏掉更短的尖峰；事件/轮询的合并轨道要按实际来源解释。
- 若 A1 发现“RSS 只在负载期上涨、恢复后回落”，下一层才是 B（调用栈归因）；若 B 也不足，再考虑 smaps/映射与直接 `mmap` 路线。

## 5. 方案 B：native heapprofd 分配调用栈采集

### 5.1 启动模型与硬前提

- **不回溯**：普通 Linux 的 heapprofd 依赖进程启动时加载 `LD_PRELOAD`；给已运行、未预加载的进程设置环境变量或套 Android 注入流程都无效。题面允许重启专用实例，因此流程是“**起会话 → 用 preload 启动专用实例**”。
- 不能修改生产服务启动项（rootfs 只读，且不应动生产配置）；专用实例由人工携带 env 启动。
- 动态链接 glibc 只是必要条件之一；静态链接、ABI/glibc 版本、socket 路径、unwind/符号、权限仍需逐级验证。
- `PERFETTO_HEAPPROFD_BLOCKING_INIT=1` 可减少“首次分配早于初始化”的遗漏，但目标名/socket 不对时会挂住；必须用 `timeout` 包住目标，`timeout` 放在 `env` 外层，避免它自己也被预加载。

参数口径：

- `sampling_interval_bytes` 是**随机字节采样的平均间隔**，不是每 4096 字节固定打点，也不是每次 malloc 都记录；输出表里的 size/count 已是分析器统计口径，不再乘采样间隔。

- 低内存变体（仅在 A1 证明内存余量紧张时考虑，明确标记为模板变体、可能更多丢数据）：把 heapprofd 的 traced buffer 从 32768 降到 8192、`shmem_size_bytes` 从 8MiB 降到 4MiB，并接受“可见 dump/样本更少”的后果；不要静默修改后宣称与默认等价。

### 5.4【目标机】启动顺序、执行、停止与拉回

核心顺序（不可颠倒）：

1. 只停/确认本次**专用测试实例**（记录旧 PID/启动时间）；不要动其它实例。
2. 起 tracebox 会话（`--system-sockets --background-wait`）。等待它返回成功；**返回成功只证明数据源就绪，不证明随后启动的目标已被采样**。
3. 立刻用 `LD_PRELOAD + BLOCKING_INIT` 启动专用实例，跑测试动作。
4. 等待目标结束、会话自然结束并完成 flush。
5. 主机拉回 trace/日志/事件标记，校验 SHA256。
6. 清理本次 `/data` 产物，释放 tmpfs。

```sh
#!/bin/sh
# /data/run_native.sh ——【目标机】执行；只操作本次专用测试实例
set -u
EV=/data/b1_events.log
TRACE=/data/native.pftrace
LOG=/data/native.log

echo "session_attempt $(date +%s%N)" >> "$EV"
# 1) 先起会话；--background-wait 返回 0 才继续
/data/tracebox --system-sockets --background-wait --txt \
  -c /data/native.pbtxt -o "$TRACE" > "$LOG" 2>&1
RC=$?
echo "session_rc=$RC $(date +%s%N)" >> "$EV"
[ "$RC" -eq 0 ] || exit 1

# 2) 就绪后再启动目标；env 只作用于这一条命令
timeout 25s env \
  LD_PRELOAD=/data/libheapprofd_glibc_preload.so \
  PERFETTO_HEAPPROFD_BLOCKING_INIT=1 \
  /data/demo_svc <获准的测试参数> >> /data/demo_svc_test.log 2>&1
echo "target_rc=$? $(date +%s%N)" >> "$EV"

# 3) 等有限会话结束：目标 25s < 会话 30s，留余量；以文件大小稳定作为结束的弱证据
sleep 10
s1=$(stat -c %s "$TRACE" 2>/dev/null || echo 0)
sleep 2
s2=$(stat -c %s "$TRACE" 2>/dev/null || echo 0)
echo "trace_size=$s1->$s2 $(date +%s%N)" >> "$EV"
sync
```

执行：

```bash
# 【主机】
ssh "$BOARD" 'chmod +x /data/run_native.sh; sh /data/run_native.sh' \
  > "$WORK/run_native.out" 2>&1
```

**`--background-wait` 的降级路径**（该版本/构建不支持时）：在主机终端 A 前台运行同一条 tracebox 命令（不 `--background-wait`），用 `tracebox perfetto --query` 确认恰好出现本次会话，再在主机终端 B 执行第 2 步的目标命令。不要用“随便 sleep 一下就启动目标”并宣称覆盖了启动分配；如果既没有就绪返回也无法确认会话已起，则本次采集只能标为“启动覆盖 UNKNOWN”，或按工具实现改用 notify-fd 握手。

**停止与 flush**：

- 首选让 `duration_ms` 自然到点（目标 25s < 会话 30s，留出 flush 时间）；目标先退出不影响会话继续到点。
- 必须提前停时，只对本次 tracebox 进程发 `SIGTERM`（按精确命令行确认 PID），等待退出与日志落盘；**不要在拉文件前 `kill -9`**，不要把未完成的文件当证据。SIGTERM 的 flush 语义在本构建上属于待实测。
- 若目标被 `timeout` 杀掉（`target_rc=124`），说明 `BLOCKING_INIT` 没等到握手：先查目标名 basename、socket 目录、tracebox 是否真的启动 heapprofd producer，修好后重跑；目标进程被杀的那次数据不可用于“业务已运行”的结论。

```bash
scp "$BOARD:/data/native.pftrace" "$BOARD:/data/native.log" \
    "$BOARD:/data/demo_svc_test.log" "$BOARD:/data/b1_events.log" "$WORK/"
ssh "$BOARD" 'sha256sum /data/native.pftrace'
sha256sum "$WORK/native.pftrace"
```

### 5.5 方案 B 的失败条件与最小下一步

| 现象 | 先查 | 处理 |
|---|---|---|
| tracebox 起不来 | `/tmp`/socket 目录可写、tracefs、权限、是否已有系统实例冲突 | 复用现有服务或按实现调整端点；不 `pkill` 别人的会话；无法解决则停止并报告 |

| 采集后开始掉帧/变卡 | `block_client`、采样开销、tmpfs 输出 | 保留无采集对照；改用 `block_client:false`（已设）并检查数据缺失，不把采集延迟归因业务 |

### 5.6 方案 B 的采集验收、dump 可见性与 SQL/UI

先明确“三种存在”不是一回事：采集端字段（v57.1 不提供 `start_timestamp`）、分析器表（v58.2 有 `heap_profile`，v57.1 没有）、实际 trace 数据（行数/时间跨度）。只有第三种能说明“采到了”。

【主机】执行：

1. `sql/00-inventory.sql`：`trace_bounds`、`process`、`stats`；再跑文件内 `[CANDIDATES]`，把 `target_name` 改成 `demo_svc`。判读：仅当**恰好一个**候选 `data_bearing=1` 时用它；Linux preload 客户端会 fork 一个继承 cmdline 的 heapprofd 子进程，通常 `data_bearing=0`，不要因为它“也有记录”而改选。用户已给 PID/UPID 时沿用并核对 identity。
2. `sql/03-native-live.sql`：填 UPID、`libc.malloc`、`start_ts/end_ts`，得到**dump 级** live 估计（普通 native 增量表，不是每次 malloc，不适用于 ART/peak）。
3. `sql/04-native-callstacks.sql`：填同一 UPID/heap/时间，按 callsite/父栈聚合得到热点表。cumulative 在祖先栈会重复，**不能把结果求和当总内存**；更细的源码行/内联用原生 UI。
4. `sql/10-native-dump-capability.sql`：先查 `heap_profile` 表是否存在；v57.1 分析器没有该表时用文件末尾 `[4]` 的降级语句（只统计活动 dump 的 `activity_dumps`/alloc/free 字节）。
5. `sql/05-native-global-summary.sql` 仅在要看整份 trace 全进程概览时使用；它汇总所有进程且不带可过滤 upid，不能标成 `demo_svc` 单进程结论。

**v57.1 的 dump 可见性判读（关键）**：

- dump 窗口结束时刻只随**带非零 timestamp 的分配**推进；长时间只持有、不新分配时，周期 dump 的 `window_end` 可能相同。
- 分析器按 `(upid, window_end, heap_name)` 去重，所以配置里的 `dump_interval_ms` 不等于可见 dump 数；可见行还要求窗口前进。
- v57.1 不提供窗口起点，`heap_profile.dur` 可能全为 0：**精确持有区间 = UNKNOWN**，但总量、分配/释放、dump 数、符号仍是可判项。不要因为 `dur=0` 就否定全部结论，也不要用 dump 窗口去断言“实际持有与预期不符”；需要窗口证据时，换发布该字段的采集器，或在采集侧让窗口前进，不改 SQL 阈值去凑通过。

预期名义触发约 5–6 次 dump（25s 目标、5s 间隔），**实际可见数以 SQL 为准**。

**验收四态（本次需实测判定）**：

| 检查 | PASS | FAIL | UNKNOWN |
|---|---|---|---|
| 时间范围 | `trace_bounds` 覆盖“会话就绪→目标 25s→结束” | 关键启动/负载段被截断 | 未执行 |
| 目标身份 | 唯一 data-bearing UPID，PID/start_ts 与本次实例一致 | 取到 preload 子进程/别的实例的数据 | 多候选无法区分 |
| heap 数据 | `heap_profile_allocation` 有该 UPID+`libc.malloc` 的行，时间落在窗口内 | 0 行且已排除名字/socket/权限/并发原因 | 分析器无该表且降级语句也无活动 dump |
| dump 数/跨度 | 与“运行时长/间隔”同量级，`first/last` 落在会话内 | 明显为 0 或全在窗口外 | dump 窗口不可判（`dur=0`）时，精确持有区间 UNKNOWN |
| 统计/日志 | 无非预期错误、无影响结论的丢数据；日志无 fatal | 明确 shmem 溢出/断开/展开失败使结论不可用 | 诊断字段缺失 |
| 符号 | 目标模块函数名可解析，Build ID 匹配 | 明确 Build ID 不匹配/符号错配 | 只有地址/缺 unstripped 文件 |
| 结论口径 | 只把 `Unreleased` 当泄漏候选，`Total` 当流量 | 把高 Total 直接判泄漏/CPU 根因 | 无重复负载/无对象生命周期定义 |

**符号化（主机）**：保存与 trace 中 Build ID 匹配的未剥离 ELF/独立 debug 文件与 libc 调试信息；按本机版本用 `trace_processor bundle --symbol-paths <dir> --verbose <trace> <out>`（若该版本支持），旧 SDK 走其 traceconv/trace_processor 支持的路径。即使命令返回 0 也要检查未解析模块/帧；符号包不保证每帧都有文件/行号。

**UI**：打开本次原始 `.pftrace` → 目标进程 → Native heap profile 轨道；先看 Unreleased Malloc Size，再切 Total Malloc Size/Count。火焰图宽度是“选定指标的字节量/次数”，**不是函数耗时**；`sql/03` 可 Add debug track（Counter Track，ts/value/series）展示 dump 级 live 估计，但它不是逐 malloc 曲线，也不适用于 peak 模式。

### 5.7 方案 B 能说明什么、不能说明什么

- 能说明：采样到的分配归因到哪些调用栈；在“相同业务阶段、重复操作、清理/等待”前后，`Unreleased` 是否回落，`Total` 是否异常活跃。
- 不能说明：RSS 占用（heap 采样 ≠ RSS）、直接 `mmap`/设备 buffer、pool 内部对象生命周期、启动前已存在的分配；高 Total 也不等于锁竞争/CPU/掉帧。单次采样有随机方差，结论至少重复一次相同负载。
- 一个最有价值的下一步：若热点调用栈缺少函数名，先找 Build ID 匹配的未剥离二进制/符号；若问题是 150ms 级 live 尖峰，5s dump 粒度不够，改用 `rss_stat` 事件或 peak 模式（`dump_at_max`，另一套分析语义），不要把两者混成一个指标。

| 维度 | 方案 A | 方案 B |
|---|---|---|

| 结束方式 | 自然到点；必要时精确 SIGTERM | 自然到点（目标先退）；必要时精确 SIGTERM |

| 主要风险 | 轮询盲区、tmpfs 余量、ftrace 开销 | 名字/socket 不对导致 BLOCKING_INIT 挂起、dump 可见性、符号缺失 |
| 回答层级 | 占用/时间/压力 | 分配调用栈 |
