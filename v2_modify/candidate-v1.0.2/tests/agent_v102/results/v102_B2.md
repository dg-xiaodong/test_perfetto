## 0. 结论先说

1. 你给的窗口 "trace 内 1.2 s–4.8 s" 是 **trace 相对偏移**，而 `sql/11`/`sql/12` 的
   `start_ts/end_ts` 是**绝对 ns**（`trace_bounds.start_ts` 通常是开机时钟，量级 1e12 以上）。
   所以第一步必须做 **`window_ns = trace_bounds.start_ts + 偏移`** 换算；把 `1200000000`
   直接填进 `start_ts` 会让窗口落在"开机后 1.2 s"，在真实 trace 上几乎必然返回空集，
   而且这种空集极易被误读成"目标进程没有 CPU"。这是本场景最大的口径坑。
2. 分桶必须用 **桶区间与 sched_slice 区间求交集**（`min(end, bucket_end) - max(ts, bucket_start)`），
   不能"把整段 `dur` 记到 `ts` 所在桶"。两者在**总量上守恒且相同**，所以
   **总量校验无法判别对错**；必须用"跨桶时间片"做逐桶数值判别（第 5 节夹具）。
3. episode 必须**先筛出 spike 桶、再对 spike 序列编号**（`bucket_index - ROW_NUMBER()`）。
   若先对全部桶编号再筛 spike，中间即使只有 1 ms 的安静桶，也会把两个 episode 并成一个。
4. `sql/12` 是**进程级**（该 UPID 所有线程求和）episode；你要求的"每线程 CPU"由 `sql/11` 给出。
   两者口径不同，不要拿 `sql/11` 的线程值去套 `sql/12` 的进程级阈值。需要线程级 episode 时用第 3.4 节变体。

## 1. 定位路线

| 项 | 内容 |
|---|---|
| 问题 | 目标进程 UPID 42 在 trace 相对 1.2–4.8 s 内，每线程 CPU 时间如何分布；哪些连续 100 ms 桶 CPU ≥ 5 ms |
| 待验证假设 | H1：该窗口内存在 1 个以上连续高 CPU episode，且被真实安静间隔切开；H0：高 CPU 是单线程造成（用线程级桶区分） |
| 数据源 | `sched_slice`（由 `sched/sched_switch` 派生）→ 每个 `utid` 的 on-CPU 区间；`thread`(upid) 做进程归属；`trace_bounds` 定位窗口 |
| 单位 | `ts/dur` 一律 **ns**；桶宽 10^8 ns = 100 ms；输出 `cpu_ms = ns/1e6`；阈值 5.0 ms |
| 不覆盖 | 墙钟延迟/掉帧（CPU 时间 ≠ 业务耗时）；off-CPU 等待与可运行队列（`thread_state`/`sched_waking`）；每 CPU 利用率与频率；跨 trace 对齐 |
| 前置条件 | 该 trace 必须真的采到了 sched 数据。**先查 `sched_slice` 行数**；为 0 时结论只能是 UNKNOWN（"未采到"），不能写成"CPU 为 0" |

不做设备采集：trace 已存在。仅当验收发现 `sched_slice` 为空/严重丢失时才需要补采，
最小追加是 `linux.ftrace` 的 `sched/sched_switch`（`make_config.py kernel-pressure --platform linux
--events available_events.txt --sched` 会加入该事件，且要求 events 文件里确实列出
`sched/sched_switch`，否则脚本直接 `ValueError`；生成的 pbtxt 是 recipe，须用**板端采集器版本**
的 descriptor 校验，不能把主机 UI 新版当依据）：

```pbtxt
data_sources {
  config {
    name: "linux.ftrace"
    target_buffer: 0
    ftrace_config {
      buffer_size_kb: 1024      # 按目标机预算调整；sched 事件量大
      drain_period_ms: 250
      ftrace_events: "sched/sched_switch"
    }
  }
}
```

## 3. 可运行 SQL

### 3.0 SQL-0：把相对窗口换算成绝对 ns（必做）

```sql
SELECT start_ts                                   AS tb_start_ns,
       end_ts                                     AS tb_end_ns,
       start_ts + 1200000000                      AS win_start_ns,  -- 1.2 s 相对
       start_ts + 4800000000                      AS win_end_ns,    -- 4.8 s 相对
       (4800000000 - 1200000000) / 100000000      AS expected_buckets
FROM trace_bounds;
```

判定：`expected_buckets = 36`；且 `win_end_ns <= tb_end_ns`，否则 trace 不足 4.8 s，
窗口后半段没有数据 —— 必须报告"窗口被 trace 末端截断"，不能把它当成"后半段安静"。

取到值后，把 `start_ts`/`end_ts` 以**字面量**填进下面两条 SQL 的 `params`。

### 3.1 SQL-1：每线程 100 ms CPU 桶（`sql/11-cpu-time-buckets.sql` 原样 + 填参）

仅替换 `params` 一行，其余（交集公式、分组、排序）保持包内已验证实现不变：

```sql
-- 11-cpu-time-buckets.sql  （params 已按 UPID 42 / trace 相对 1.2–4.8 s / 100 ms 填入）
-- 未执行：参数中的尖括号需换成 SQL-0 得到的具体 ns 字面量
WITH RECURSIVE
params AS (
  SELECT 42 AS target_upid,
         <SQL0.win_start_ns> AS start_ts,
         <SQL0.win_end_ns>   AS end_ts,
         100000000           AS bucket_ns
),
bounds AS (
  SELECT
    p.target_upid,
    CASE WHEN p.start_ts >= 0 THEN p.start_ts ELSE t.start_ts END AS start_ts,
    CASE WHEN p.end_ts   >= 0 THEN p.end_ts   ELSE t.end_ts   END AS end_ts,
    p.bucket_ns
  FROM params p CROSS JOIN trace_bounds t
  WHERE p.bucket_ns > 0
),
buckets(bucket) AS (
  SELECT 0
  UNION ALL
  SELECT bucket + 1
  FROM buckets
  WHERE bucket + 1 <
        (SELECT CAST((end_ts - start_ts + bucket_ns - 1) / bucket_ns AS INTEGER)
         FROM bounds)
)
SELECT
  th.utid,
  th.tid,
  th.name AS thread_name,
  b.target_upid,
  b.start_ts + bk.bucket * b.bucket_ns AS ts,
  bk.bucket AS bucket_index,
  SUM(
    MIN(s.ts + s.dur, b.start_ts + (bk.bucket + 1) * b.bucket_ns)
    - MAX(s.ts, b.start_ts + bk.bucket * b.bucket_ns)
  ) / 1000000.0 AS cpu_ms,
  COUNT(*) AS overlapping_slices
FROM sched_slice s
JOIN thread th USING (utid)
CROSS JOIN bounds b
JOIN buckets bk
  ON s.ts < b.start_ts + (bk.bucket + 1) * b.bucket_ns
 AND s.ts + s.dur > b.start_ts + bk.bucket * b.bucket_ns
WHERE th.upid = b.target_upid
  AND s.dur > 0
  AND s.ts < b.end_ts
  AND s.ts + s.dur > b.start_ts
GROUP BY th.utid, th.tid, th.name, b.start_ts, b.bucket_ns, bk.bucket
ORDER BY ts, cpu_ms DESC;
```

输出语义：每行 = (线程, 桶) 的 CPU 毫秒数，`ts` 是**桶起点绝对 ns**。
`overlapping_slices` 是命中该桶的 sched_slice 条数（跨桶片会同时计入两个桶，所以
`SUM(overlapping_slices) > 片数` 属正常，不能拿来当"分配了多少次"）。

### 3.2 SQL-2：进程级 spike episode（`sql/12-cpu-spike-episodes.sql` 原样 + 填参）

阈值 5.0 ms、桶宽 100 ms：

```sql
-- 12-cpu-spike-episodes.sql  （params 已按 UPID 42 / 1.2–4.8 s / 100 ms / 5 ms 填入）
-- 未执行
WITH RECURSIVE
params AS (
  SELECT 42 AS target_upid,
         <SQL0.win_start_ns> AS start_ts,
         <SQL0.win_end_ns>   AS end_ts,
         100000000           AS bucket_ns,
         5.0                 AS threshold_ms
),
bounds AS (
  SELECT
    p.target_upid,
    CASE WHEN p.start_ts >= 0 THEN p.start_ts ELSE t.start_ts END AS start_ts,
    CASE WHEN p.end_ts   >= 0 THEN p.end_ts   ELSE t.end_ts   END AS end_ts,
    p.bucket_ns,
    p.threshold_ms
  FROM params p CROSS JOIN trace_bounds t
  WHERE p.bucket_ns > 0
),
buckets(bucket) AS (
  SELECT 0
  UNION ALL
  SELECT bucket + 1
  FROM buckets
  WHERE bucket + 1 <
        (SELECT CAST((end_ts - start_ts + bucket_ns - 1) / bucket_ns AS INTEGER)
         FROM bounds)
),
cpu AS (
  SELECT
    bk.bucket AS bucket_index,
    SUM(
      MIN(s.ts + s.dur, b.start_ts + (bk.bucket + 1) * b.bucket_ns)
      - MAX(s.ts, b.start_ts + bk.bucket * b.bucket_ns)
    ) / 1000000.0 AS cpu_ms
  FROM sched_slice s
  JOIN thread th USING (utid)
  CROSS JOIN bounds b
  JOIN buckets bk
    ON s.ts < b.start_ts + (bk.bucket + 1) * b.bucket_ns
   AND s.ts + s.dur > b.start_ts + bk.bucket * b.bucket_ns
  WHERE th.upid = b.target_upid
    AND s.dur > 0
    AND s.ts < b.end_ts
    AND s.ts + s.dur > b.start_ts
  GROUP BY bk.bucket
),
flagged AS (
  SELECT bucket_index, cpu_ms,
         CASE WHEN cpu_ms >= (SELECT threshold_ms FROM bounds) THEN 1 ELSE 0 END AS spike
  FROM cpu
),
spikes AS (
  SELECT bucket_index, cpu_ms,
         bucket_index - ROW_NUMBER() OVER (ORDER BY bucket_index) AS grp
  FROM flagged
  WHERE spike = 1
)
SELECT
  b.start_ts + MIN(s.bucket_index) * b.bucket_ns AS ts,
  (MAX(s.bucket_index) - MIN(s.bucket_index) + 1) * b.bucket_ns AS dur,
  MIN(s.bucket_index) AS first_bucket,
  MAX(s.bucket_index) AS last_bucket,
  COUNT(*) AS buckets_in_episode,
  MAX(s.cpu_ms) AS peak_cpu_ms,
  AVG(s.cpu_ms) AS avg_cpu_ms
FROM spikes s CROSS JOIN bounds b
GROUP BY s.grp
ORDER BY ts;
```

三条必须写进结论的口径：
- `dur` 是**桶粒度**的 episode 跨度（`(last-first+1)×100 ms`），起点对齐桶边界，
  不代表真实"CPU 一直满"的精确区间；实际活跃区间只会更窄。
- `WHERE spike = 1` 发生在 `ROW_NUMBER()` 之前（SQL 的 WHERE 先于窗口函数），
  所以 `grp` 是在 spike 序列上连续编号 —— 这正是安静间隔能切断 episode 的原因。
- 只输出"至少 1 个 spike 桶"的 episode；没有任何 spike 时结果为空，含义是
  "在本次阈值/窗口下未发现 episode"，不等于"CPU 不忙"（阈值是人为口径）。

### 3.3 SQL-4（辅助）：逐桶 spike 标记（含 0 填补），用于验证安静间隔

```sql
-- 派生自 sql/12 的 cpu CTE；新增 buckets LEFT JOIN 补出全部 36 个桶。
-- 未执行。COALESCE 成 0 的前提：该窗口 sched 数据完整（A3 检查通过）；
-- 若 stats 显示 ftrace 丢失，缺失桶必须标 UNKNOWN，不能补 0。
WITH RECURSIVE
params AS (
  SELECT 42 AS target_upid,
         <SQL0.win_start_ns> AS start_ts,
         <SQL0.win_end_ns>   AS end_ts,
         100000000 AS bucket_ns, 5.0 AS threshold_ms
),
bounds AS (
  SELECT p.target_upid,
         CASE WHEN p.start_ts >= 0 THEN p.start_ts ELSE t.start_ts END AS start_ts,
         CASE WHEN p.end_ts   >= 0 THEN p.end_ts   ELSE t.end_ts   END AS end_ts,
         p.bucket_ns, p.threshold_ms
  FROM params p CROSS JOIN trace_bounds t
  WHERE p.bucket_ns > 0
),
buckets(bucket) AS (
  SELECT 0 UNION ALL
  SELECT bucket + 1 FROM buckets
  WHERE bucket + 1 <
        (SELECT CAST((end_ts - start_ts + bucket_ns - 1) / bucket_ns AS INTEGER) FROM bounds)
),
cpu AS (
  SELECT bk.bucket AS bucket_index,
         SUM(MIN(s.ts + s.dur, b.start_ts + (bk.bucket + 1) * b.bucket_ns)
             - MAX(s.ts, b.start_ts + bk.bucket * b.bucket_ns)) / 1000000.0 AS cpu_ms
  FROM sched_slice s
  JOIN thread th USING (utid)
  CROSS JOIN bounds b
  JOIN buckets bk
    ON s.ts < b.start_ts + (bk.bucket + 1) * b.bucket_ns
   AND s.ts + s.dur > b.start_ts + bk.bucket * b.bucket_ns
  WHERE th.upid = b.target_upid AND s.dur > 0
    AND s.ts < b.end_ts AND s.ts + s.dur > b.start_ts
  GROUP BY bk.bucket
)
SELECT b.start_ts + bk.bucket * b.bucket_ns AS ts,
       bk.bucket AS bucket_index,
       COALESCE(c.cpu_ms, 0.0) AS cpu_ms,
       CASE WHEN COALESCE(c.cpu_ms, 0.0) >= b.threshold_ms THEN 1 ELSE 0 END AS spike
FROM buckets bk
CROSS JOIN bounds b
LEFT JOIN cpu c ON c.bucket_index = bk.bucket
ORDER BY bucket_index;
```

配套的"间隔检查"（把上面结果整体放进 `sf` CTE 后）：

```sql
-- 相邻 spike 桶序号差 >1 ⇒ 中间至少有一个非 spike 桶 ⇒ 这里是 episode 边界
WITH sf AS ( /* 上面 SQL-4 的完整结果 */ ),
sp AS (SELECT bucket_index FROM sf WHERE spike = 1)
SELECT bucket_index,
       bucket_index - LAG(bucket_index) OVER (ORDER BY bucket_index) AS delta
FROM sp
ORDER BY bucket_index;
```

断言：`delta` 只允许为 `1`（同 episode 内）或 `>1`（被安静桶切开）；若出现 `delta = 1`
跨越了你认为的安静段，说明安静段里本来就有 spike 桶（数据如此），而不是"分组错了"。

### 3.4 SQL-3：线程级 spike episode（**变体**，非包内已验证实现）

只在确认"阈值要作用在单线程"时使用；与 SQL-2 的差异是三处：`cpu` 带 `utid`、
`flagged` 透传线程列、`ROW_NUMBER()` 按 `utid` 分区：

```sql
-- 未执行；派生自 sql/12，仅改变聚合维度，交集公式与阈值判据不变
WITH RECURSIVE
params AS (
  SELECT 42 AS target_upid,
         <SQL0.win_start_ns> AS start_ts,
         <SQL0.win_end_ns>   AS end_ts,
         100000000 AS bucket_ns, 5.0 AS threshold_ms
),
bounds AS (
  SELECT p.target_upid,
         CASE WHEN p.start_ts >= 0 THEN p.start_ts ELSE t.start_ts END AS start_ts,
         CASE WHEN p.end_ts   >= 0 THEN p.end_ts   ELSE t.end_ts   END AS end_ts,
         p.bucket_ns, p.threshold_ms
  FROM params p CROSS JOIN trace_bounds t
  WHERE p.bucket_ns > 0
),
buckets(bucket) AS (
  SELECT 0 UNION ALL
  SELECT bucket + 1 FROM buckets
  WHERE bucket + 1 <
        (SELECT CAST((end_ts - start_ts + bucket_ns - 1) / bucket_ns AS INTEGER) FROM bounds)
),
cpu AS (
  SELECT th.utid, th.tid, th.name AS thread_name, bk.bucket AS bucket_index,
         SUM(MIN(s.ts + s.dur, b.start_ts + (bk.bucket + 1) * b.bucket_ns)
             - MAX(s.ts, b.start_ts + bk.bucket * b.bucket_ns)) / 1000000.0 AS cpu_ms
  FROM sched_slice s
  JOIN thread th USING (utid)
  CROSS JOIN bounds b
  JOIN buckets bk
    ON s.ts < b.start_ts + (bk.bucket + 1) * b.bucket_ns
   AND s.ts + s.dur > b.start_ts + bk.bucket * b.bucket_ns
  WHERE th.upid = b.target_upid AND s.dur > 0
    AND s.ts < b.end_ts AND s.ts + s.dur > b.start_ts
  GROUP BY th.utid, th.tid, th.name, bk.bucket
),
flagged AS (
  SELECT utid, tid, thread_name, bucket_index, cpu_ms,
         CASE WHEN cpu_ms >= (SELECT threshold_ms FROM bounds) THEN 1 ELSE 0 END AS spike
  FROM cpu
),
spikes AS (
  SELECT utid, tid, thread_name, bucket_index, cpu_ms,
         bucket_index - ROW_NUMBER() OVER (PARTITION BY utid ORDER BY bucket_index) AS grp
  FROM flagged
  WHERE spike = 1
)
SELECT s.thread_name, s.utid, s.tid,
       b.start_ts + MIN(s.bucket_index) * b.bucket_ns AS ts,
       (MAX(s.bucket_index) - MIN(s.bucket_index) + 1) * b.bucket_ns AS dur,
       MIN(s.bucket_index) AS first_bucket,
       MAX(s.bucket_index) AS last_bucket,
       COUNT(*) AS buckets_in_episode,
       MAX(s.cpu_ms) AS peak_cpu_ms,
       AVG(s.cpu_ms) AS avg_cpu_ms
FROM spikes s CROSS JOIN bounds b
GROUP BY s.utid, s.tid, s.thread_name, s.grp
ORDER BY ts, s.utid;
```

一致性关系（可用作交叉校验，也是区分两种口径的证据）：
对任一桶，`SUM(SQL-3 的 cpu_ms) == SQL-2 的 cpu_ms`（同一批 sched_slice，只是聚合维度不同）；
**但 episode 集合通常不同**：两个线程交替忙时，线程级会得到两个各自更短的 episode，
进程级是一个把两段连起来的长 episode（见夹具 C4）。

## 4. Perfetto UI：debug track 映射

前提：`Query (SQL)` 里跑通并核对结果；然后在该结果面板用 **Add debug track**。

| 图 | Track type | Timestamp | Duration | Value | Pivot on / Name |
|---|---|---|---|---|---|
| 每线程 CPU 桶（SQL-1） | **Counter Track** | `ts` | — | `cpu_ms` | `Pivot on = thread_name`（轨道名写 `cpu_ms / 100ms bucket`） |
| 进程 spike episode（SQL-2） | **Slice Track** | `ts` | `dur` | — | `Name` 无列则 UI 里直接填字面量 `cpu_spike`；或临时加 `'cpu_spike' AS name` 列后 `Name = name` |
| 线程 spike episode（SQL-3） | **Slice Track** | `ts` | `dur` | — | `Pivot on = thread_name` |
| 逐桶 spike 0/1（SQL-4） | Counter Track | `ts` | — | `spike` | 无（y 轴只有 0/1，作为"底层标记"轨道放在 episode 轨道上下对照） |

必须注意的 UI 细节：

- `ts` 是**绝对纳秒**，Add debug track 直接选 `ts`，**不要** `ts/1e9`。把 ns 换成秒再画会导致
  轨道跑到时间轴外（scenarios A26 的典型错误）。
- 计数器轨道在"没有行的桶"处没有数据点，Perfetto 会跨点连线；如果目标线程在窗口内根本没跑，
  不要用光滑连线暗示"CPU 一直很低"。要画连续 0 线，用 SQL-4 的补零版本，并在轨道名标注"0 为补零"。
- `thread_name` 可能为 NULL 或同名（同名多线程会并到一条轨道）。需要区分时把 SQL-1 的
  第二列换成 `th.name || ' / ' || th.tid AS thread_name`，Pivot 仍用该列；这只改展示列，不改判据。
- 先 `Search` 目标进程核对 PID/UPID 实例（PID 复用、preload fork 同名子进程都会造成混淆），
  再缩放到同一"操作前—复现—恢复"窗口；episode 轨道与 CPU 桶轨道**必须同一窗口**截图/比较。
- 没有实际打开 UI 验证 → 只能写"UI 配方已给出"，不能写"UI 显示正常"。

### 5.1 错误实现（反面教材，只用于对照，不要执行交付）

```sql
-- 反例 A：整段 dur 记到 ts 所在桶；不裁剪窗口；不处理负桶
SELECT th.utid,
       CAST((s.ts - <win_start_ns>) / 100000000 AS INTEGER) AS bucket_index,
       SUM(s.dur) / 1000000.0 AS cpu_ms
FROM sched_slice s
JOIN thread th USING (utid)
WHERE th.upid = 42
GROUP BY th.utid, bucket_index;
-- 反例 B：改成按 ts+dur 记到结束桶（同性质错误，方向相反）
-- 反例 C：CROSS JOIN buckets + WHERE 只判 s.ts 是否落在桶内（整段仍记整段）
```

### 5.2 判别夹具（可直接套进 `tests/test_cpu_sql.py` 的 `load()`/`insert()` 结构）

夹具公共设置：`trace_bounds = (0, 5000000000)`，窗口 `start_ts=1200000000, end_ts=4800000000`，
`bucket_ns=100000000`，`threshold_ms=5.0`，窗口内共 36 个桶（bucket 0 = [1.2s,1.3s)）。

**夹具 C1（跨桶 + 恰好命中阈值，最强判别用例）**，`utid=5`（upid 42）：

| sched_slice | 区间 |
|---|---|
| A | `ts=1285000000, dur=8000000`（1.285–1.293 s） |
| B | `ts=1295000000, dur=10000000`（1.295–1.305 s） |

正确实现（SQL-1）逐桶：

| bucket_index | 桶区间 | cpu_ms | 来源 |
|---|---|---|---|
| 0 | 1.200–1.300 | **13.0** | A 全 8 ms + B 的前 5 ms |
| 1 | 1.300–1.400 | **5.0** | B 的后 5 ms |

正确实现（SQL-2，阈值 5）：bucket0=13≥5、bucket1=5≥5，序号相邻 ⇒ **1 个 episode**：
`ts=1200000000, dur=200000000, first=0, last=1, buckets=2, peak=13, avg=9`。

错误实现（反例 A）：bucket0 = 8+10 = **18.0**，bucket1 **无行** ⇒ episode 为
`ts=1200000000, dur=100000000, buckets=1, peak=18, avg=18`。

| 判别字段 | 正确 | 反例 A | 能否判别 |
|---|---|---|---|
| bucket1 是否有行 | 有，5.0 | 无 | ✅ |
| bucket0 cpu_ms | 13.0 | 18.0 | ✅ |
| episode `dur` | 200000000 | 100000000 | ✅ |
| episode `buckets_in_episode` | 2 | 1 | ✅ |
| episode `peak_cpu_ms` | 13 | 18 | ✅ |
| `SUM(cpu_ms)` 全窗口 | 18.0 | 18.0 | ❌ **总量守恒，不能判别** |

最后一行是本用例的核心：**"总量对得上"绝不能作为分桶正确的证据**，必须逐桶比对。

**夹具 C1b（覆盖 06-quality 要求的 90–120 ms 跨桶回归）**：单个片
`ts=1250000000, dur=100000000`（1.25–1.35 s，正好 100 ms 跨桶）→ 正确 bucket0=50、bucket1=50，
episode 2 桶 / dur 200 ms / peak 50；反例 A 得到 bucket0=100、bucket1 无行，
episode 1 桶 / dur 100 ms / peak 100。

**夹具 C2（窗口边界裁剪）**：

| sched_slice | 正确（交集裁剪） | 反例 A（起始桶 + 不裁剪） | 只做 `s.ts >= start` 过滤 |
|---|---|---|---|
| `ts=1190000000, dur=20000000`（1.19–1.21 s） | bucket0 = **10 ms** | bucket0 = 20 ms（`CAST(-0.1 AS INTEGER)=0`，负桶被截成 0） | 整片丢掉 → 0 行 / 0 ms |
| `ts=4790000000, dur=20000000`（4.79–4.81 s） | bucket35 = **10 ms** | bucket35 = 20 ms（未按 `end_ts` 裁剪） | 20 ms |

这个夹具说明窗口两端**两个方向都会错**：左边界容易漏算（负桶被丢），也容易多算；
右边界容易多算。单看某一边的数值无法发现，必须两端各测一次。

**夹具 C3（安静间隔不能吞）**，让安静桶"有行但低于阈值"（现实中最常见）：

| sched_slice | 桶 | cpu_ms |
|---|---|---|
| `ts=1300000000, dur=100000000` | 1 | 100 |
| `ts=1400000000, dur=1000000` | 2 | 1（安静，有行） |
| `ts=1500000000, dur=1000000` | 3 | 1（安静，有行） |
| `ts=1600000000, dur=1000000` | 4 | 1（安静，有行） |
| `ts=1700000000, dur=100000000` | 5 | 100 |

正确（SQL-2）：spike 桶 = {1,5}，`ROW_NUMBER` 在**筛后**编号（1→1, 5→2），
`grp = 1-1=0, 5-2=3` ⇒ **2 个 episode**：`(ts=1300ms, dur=100ms)`、`(ts=1700ms, dur=100ms)`。

反例 D（**错误分组**）：先对全部 5 个有行的桶算 `bucket - ROW_NUMBER()`，再筛 spike：

```sql
-- 反例 D：先编号后筛选 ⇒ 安静桶把编号"顶"在一起，两个 episode 被合并
bad AS (
  SELECT bucket_index, cpu_ms,
         bucket_index - ROW_NUMBER() OVER (ORDER BY bucket_index) AS grp
  FROM flagged                       -- 注意：这里包含 spike=0 的安静桶
)
SELECT ... FROM bad WHERE <spike 条件> GROUP BY grp;
```

桶 1..5 的 `grp` 全部为 0 ⇒ 得到 **1 个 episode**：`ts=1300ms, dur=500ms, buckets=5`。
判别点：episode 数 2 vs 1；第二个 episode 的存在性（`ts=1700ms` 那一行消失）。

补充：**安静桶"没有行"和"有行但 <5 ms"都要切断 episode**。前者靠 spike 序号不连续，
后者靠"先筛 spike"；两种都必须测（C3 测后者，把 C3 里 2/3/4 的片删掉就变成前者，
仍然必须得到 2 个 episode）。

**夹具 C4（口径反例：线程级 vs 进程级）**，`utid=5` 两片占 bucket1、2，`utid=6` 两片占 bucket3、4，
每片 100 ms：

| 查询 | 结果 |
|---|---|
| SQL-2（进程级） | 1 个 episode：`ts=1300ms, dur=400ms, buckets=4` |
| SQL-3（线程级） | 2 个 episode：`utid5 ts=1300ms dur=200ms`、`utid6 ts=1500ms dur=200ms` |

这条不是"错"，而是提醒：**题目没锁口径时，报出的 episode 数会随口径变化**，
交付时必须写明用的是哪一个，并把另一口径作为对照给出。

### 5.3 为什么反例 A 在实际 trace 上"看起来也像真的"

- 单线程、片不跨桶时（绝大多数片），反例 A 与正确实现**完全一致**，所以抽查一两片发现不了。
- 总量守恒，仪表盘/汇总数字一致。
- 只有"跨桶片 + 桶恰好跨阈值"时结论才分叉 —— 而这正是 06-quality 要求回归里
  "跨桶时间片至少覆盖一次 90–120 ms 跨桶"的原因。所以验收必须**故意构造**跨桶用例，
  不能等 trace 里自然出现。

## 6. 如何验证"跨桶区间"和"安静间隔"（可执行步骤，本次未执行）

### V1 总量守恒（必要但不充分）

```sql
SELECT SUM(MIN(s.ts + s.dur, x.end_ts) - MAX(s.ts, x.start_ts)) / 1000000.0 AS total_cpu_ms
FROM sched_slice s
JOIN thread th USING (utid)
CROSS JOIN (SELECT <win_start_ns> AS start_ts, <win_end_ns> AS end_ts) x
WHERE th.upid = 42 AND s.dur > 0
  AND s.ts < x.end_ts AND s.ts + s.dur > x.start_ts;
```

必须等于 SQL-1 的 `SUM(cpu_ms)`（也等于 SQL-3 按线程求和）。**相等只证明总量对，不证明分桶对**；
它仍值得跑，因为它能抓"窗口裁剪写错/漏算整片"这类错误（C2 就会破坏守恒或改变总量）。

### V2 单桶逐片展开（验证跨桶确实被切开）

以 bucket 1（[1.3 s,1.4 s)）为例：

```sql
WITH w AS (SELECT <win_start_ns> AS w0 FROM trace_bounds)   -- 或直接写字面量
SELECT s.utid, s.ts, s.dur,
       MIN(s.ts + s.dur, w.w0 + 1400000000) - MAX(s.ts, w.w0 + 1300000000) AS clipped_ns
FROM sched_slice s
JOIN thread th USING (utid)
CROSS JOIN w
WHERE th.upid = 42 AND s.dur > 0
  AND s.ts < w.w0 + 1400000000
  AND s.ts + s.dur > w.w0 + 1300000000
ORDER BY s.ts;
```

判定：`SUM(clipped_ns)/1e6` **必须逐位等于** SQL-1 中该桶的 `cpu_ms`；
且任一 `clipped_ns < s.dur` 的行就是"被桶边界切开"的证据 —— 这类行的存在说明
"整段记到起始桶"会算错，必须检查它落在哪一侧。若窗口内**没有任何** `clipped_ns < s.dur` 的行，
则本 trace 无法区分两种实现，**必须标注"该窗口无跨桶片，分桶正确性未被这条验证覆盖"**，
改跑夹具 C1（或用更小 `bucket_ns` 重切）。

### V3 安静间隔（结构检查）

1. 跑 SQL-4 得到 36 行 `(bucket_index, cpu_ms, spike)`，先确认行数 = 36，`bucket_index` 0..35 连续。
2. 跑"间隔检查"：相邻 spike 桶的 `delta` 只能为 1 或 >1。
3. 交叉：SQL-2 的 episode 边界必须与 `delta > 1` 的位置一一对应；
   `SUM(buckets_in_episode)` 必须等于 spike 桶总数。
4. 反证：把某个安静桶的 CPU 人为（在夹具里）抬过阈值，episode 数应减少 1 —— 若不减少，
   说明分组依赖了错误的东西（例如把 `spike` 判断写成了常量）。

### V4 第二实现交叉（同数据、不同构造）

在 SQL-4 结果上再套一层，用 `LAG(spike)` 找 episode 起点：

```sql
SELECT bucket_index, cpu_ms FROM (
  SELECT bucket_index, cpu_ms,
         CASE WHEN spike = 1 AND COALESCE(LAG(spike) OVER (ORDER BY bucket_index), 0) = 0
              THEN 1 ELSE 0 END AS episode_start
  FROM <SQL-4 的结果>
) WHERE episode_start = 1;
```

其行数必须等于 SQL-2 的 episode 数，`bucket_index` 集合必须等于 SQL-2 的 `first_bucket` 集合。
注意：这是"同一份 sched 数据的另一种构造"，不是独立数据源，所以它只能抓实现 bug，
不能代替 V2 对交集语义的验证。

### V5 数据验收（先做，否则上面全是空中楼阁）

```sql
-- A1 目标身份：UPID 42 存在且是你要的那个实例（PID 复用/同名子进程要排除）
SELECT upid, pid, name, start_ts, end_ts FROM process WHERE upid = 42;

-- A2 sched 数据是否真的采到（表存在 ≠ 有数据）
SELECT COUNT(*) AS sched_slices, MIN(ts) AS first_ts, MAX(ts) AS last_ts
FROM sched_slice s JOIN thread th USING (utid) WHERE th.upid = 42;

-- A3 丢失/截断
SELECT name, idx, severity, source, value FROM stats
WHERE value <> 0 AND (severity <> 'info' OR name GLOB '*ftrace*' OR name GLOB '*sched*')
ORDER BY severity, name;
```

- A2 为 0 ⇒ 结论 **UNKNOWN（未采到 sched 数据）**，不是"CPU 0"，也不是"无 episode"。
- A2 的 `first_ts` 晚于窗口起点 ⇒ 窗口前段无数据，前几个桶是 UNKNOWN，不能补 0。
- A2 的 `last_ts` 早于窗口终点 ⇒ 末段同理。
- A3 有 ftrace 丢失 ⇒ 丢包区间内的桶判 UNKNOWN；只有丢了也不影响结论时才继续，
  并在结论里写明丢包范围。
- 期望桶数 36；实际输出桶数不足 36 时，先分清是"窗口被截断"、"递归 CTE 写错"还是"SQL 被改了"。

## 8. 如何下结论

| 观察 | 支持 | 反驳 | 不能推出 |
|---|---|---|---|
| SQL-1 有 36 个桶、逐桶值与 V2 展开一致、总量守恒 | 分桶实现正确（含跨桶） | 若某桶 `clipped_ns` 之和与 `cpu_ms` 不符 ⇒ 分桶/裁剪有 bug | 不能推出 CPU 高导致掉帧 |
| SQL-2 得到 k 个 episode，且 V3 的 `delta>1` 位置一一对应 | "窗口内存在 k 段连续高 CPU" | 若 V4 的起点集合不同 ⇒ 分组实现有 bug | 不能把 episode 数当"卡顿次数" |
| SQL-1 显示 CPU 集中在个别 `utid` | 支持 H0（单线程主导） | 若多个 utid 各占少量而进程级过阈值 ⇒ 支持"整体并发高" | 不能说明该线程内部在做什么（需调用栈/函数级数据） |
| 窗口内无 spike 桶 | 在**本阈值/本窗口**下无 episode | 阈值 5 ms 是人为口径，降到 1 ms 可能就有 | 不能说"进程不忙"或"没有性能问题" |
| A2=0 或 A2 首末未覆盖窗口 | 只能报 UNKNOWN | — | 不能报"CPU 为 0"、不能报"无 episode" |

**当前证据能说明什么**：什么都不能说明 —— 没有任何 trace 数据被读取或执行。
本文能确定的只有方法：窗口要换算、分桶要用交集、episode 要先筛后编号、阈值口径要声明、
验收要用跨桶与安静桶两组夹具。

**一个最有价值的下一步**：在目标 trace 上跑 A1–A3 + SQL-0，
确认 `sched_slice` 非空且窗口落在 trace 内；再跑 SQL-1 与 V2，
拿**一个真实跨桶片**逐桶对账。这一步同时验证"数据在不在"和"交集实现对不对"，
比先看 episode 数量更有价值 —— 没有这一步，episode 的数字无法解释。
