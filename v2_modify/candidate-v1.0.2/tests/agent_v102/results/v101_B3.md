# B3 — 证据边界与因果：逐条评估与最小补采建议

## 0. 前提与结论边界

- 本次只读到你对两份采集的**描述**（C1 的内容、C2 的内容、目标 UPID），没有打开 C1/C2 的原始 trace，没有执行命令、SQL 或设备操作。下面全部是**判读规则**，不是本次实测结论。
- 判定采用三态：**PASS**（证据满足条件）、**FAIL**（证据明确违反条件）、**UNKNOWN**（缺少该结论所需的证据）。
- 先把总评放在前面：三条表述里，**只有"count 高说明分配活跃（估计次数多）"在限定口径下可以接受**；"把 C1 绝对时间戳直接填进 C2 SQL 就能对齐分配与 CPU"、"dump 时间就是每次 malloc 时间"、"采集成功所以确认是分配导致 CPU 抖动"都不可接受。
- C1 与 C2 是两份**独立采集**，这是整件事最关键的限制：在证明"两份数据在同一时钟域、覆盖同一时间窗与同一进程实例"之前，两份数据之间**连时间上的共现都没有建立**，不能进入因果讨论。

## 1. 逐条评估

### 说法 1：把 C1 里的绝对时间戳直接填到 C2 的 SQL 里，就能把分配和 CPU 对齐

**判定：不可接受（FAIL，当前证据下为 UNKNOWN 条件未满足）。**

原因分三层：

1. **时钟域与覆盖同一性未验证（跨 trace 的前提）。**
   - 两份 trace 的 `ts` 都是各自文件内的绝对纳秒。只有当它们**同一台设备、同一次开机（中间没有重启）、时钟域一致，并且时间窗确实重叠**时，数值才可比。任何一条不成立，直接比较就是错的。
   - 必须核对：各 trace 的 `trace_bounds`、时钟快照/时钟域、boot 标识、目标 `UPID/PID` 是否同一进程实例（重启、PID 复用、同名 preload 子进程 `data_bearing=0` 都会让"目标"悄悄换人）。
2. **时间戳语义不匹配（即使时钟一致也不等于对齐了分配）。**
   - C2 的分析对象 `heap_profile_allocation` 以 dump/窗口为单位聚合：行上的 `ts` 对应 dump 窗口的结束/提交时刻（本包 `sql/10-native-dump-capability.sql` 就是用 `a.ts = h.ts_end` 关联），不是"每次 malloc 的时刻"（详见说法 2）。
   - 把 C1 的某个绝对时刻填成 C2 SQL 的 `start_ts`/`end_ts`，实际语义是"筛出窗口结束落在该时刻附近的 dump 行"。5 秒一份连续 dump 时，很可能筛出 0 行——而 **0 行不等于没有分配**（`sql/03-native-live.sql`、`sql/04-native-callstacks.sql` 头部的注释已明确：`-1` 或空结果表示未解析，必须先解析目标）。
   - "每隔几秒 CPU 上升"是一个**周期现象**，不是单个时间戳。要关联必须先从 C1 数据中得出带起止纳秒的分析窗口 `[t0,t1]`，并写清这个窗口是怎么从数据里定义的。
3. **正确的对齐方式不是"填时间戳"，而是"共享时钟域 + 明确窗口"。**
   - 首选：把 counter/sched 与 heapprofd 放进**同一份 trace**，此时所有 `ts` 天然同一时钟域，不存在跨文件注入。
   - 其次（复用现有两份 trace）：先做上面的时钟/开机/窗口/UPID 四项核对，全部通过后才允许用绝对纳秒做**窗口级粗对齐**；并且要写明粒度是"样本/dump 窗口"，不是"逐次 malloc"。

**可以接受的部分**：在同一份 trace 内，counter/sched 的 `ts` 与 heap profile 的 `ts` 是同一时钟域，按时间窗口取交集是合法操作。

**需要的额外证据**：时钟域与 boot 一致性、两份 trace 的时间窗重叠、目标 UPID 为同一进程实例、窗口定义、C2 的 dump 窗口起点是否可知（`dur>0`）。

### 说法 2：heapprofd dump 的时间就是每次 malloc 的时间

**判定：不可接受（FAIL）。这是采集器行为决定的，不是分析器的可选功能。**

- 连续 dump 是把**窗口内的分配行为聚合成快照**；`heap_profile_allocation` 用正分配/负释放表达变化，是窗口级聚合，不是逐事件日志。
- dump 的窗口结束时刻只在**提交带非零 timestamp 的分配**时前进；`free` 以 `timestamp=0` 提交。因此长时间只持有、不新分配时，多份周期 dump 的 `window_end` 会相同。
- 分析器按 `(upid, window_end, heap_name)` 去重，所以配置里的 `dump_interval_ms` **不等于**可见 dump 数；触发次数和可见行数要分开看。
- 旧采集端不提供 `start_timestamp` 时，Trace Processor 会令 `ts == ts_end`、`dur = 0`，此时**窗口起点不可知**，精确时间对齐直接是 UNKNOWN；`dur = 0` 只说明"不能用 dump 窗口界定持有区间"，不等于采集失败。
- 采样是随机字节采样（平均间隔，不是"每 4096 字节固定打点"），分析表里的 size/count 已是估计量，**不要再乘采样间隔**；单次小分配可能根本没被采中。

**可以接受的部分**：给定 UPID/heap/dump 行，可以回答"在**这个 dump 窗口内**，这些调用栈的分配累计量/保留量估计是多少"；不能回答"哪一毫秒发生了哪一次 malloc"。

**需要的额外证据**：如果确实需要逐分配时间线，heapprofd 给不出。要么换以事件为主的数据源（如 mmap syscall 等，且只覆盖其可见路径），要么接受 dump 级粒度并写明分辨率。

### 说法 3：count 高说明调用次数多

**判定：限定口径下可接受（PARTIAL），不能当作精确调用次数，也不能据此推 CPU。**

- 先分清是哪一个 count：**Total Malloc Count**（窗口内累计分配次数估计，含之后被释放的）与 **Unreleased Malloc Count**（分配后尚未配对释放的次数估计）。"count 高"指哪个必须写明，两者含义不同。
- count 是**采样估计**：按分配字节流随机采样后的统计量，不是逐调用精确计数。小分配热点方差大，需要一个可重复的相同 workload 多跑几次，才能说"这是稳定热点"；大分配快路径的实现差异要按对应版本实现核对。
- "live 估计较高"也要限定口径：它只是**追踪范围内**分配未释放的估计，不等于 RSS，不等于进程实际占用；如果只取区间内的行，得到的是**净变化**，不是区间结束时的完整 live（需要窗口之前的基线）。
- count 高只说明"分配活跃/次数多（估计）"，不包含耗时、锁、缺页、allocator 内部行为；官方口径明确：heapprofd 是**分配调用栈归因器，不是 malloc 耗时分析器**，延迟/CPU 问题需要 CPU、调度或额外定时证据。
- 还要先确认数据质量：目标 UPID 正确、分配行非空、符号是否可读。否则"count 高"可能是看错进程或缺失符号下的误读。

**需要的额外证据**：采样间隔与 trace 元数据、重复试验、明确指标名；要谈 CPU 必须另采 sched/perf/授权时间标记。

### 说法 4：profiler 已经采集成功，所以可以确认是分配导致 CPU 抖动

**判定：不可接受（FAIL）。这是把"采集验收"当成了"因果证明"。**

- 采集验收是四级：**schema → 运行条件 → 数据 → 分析/UI**。前两级只说明"配置能解析、环境具备"，第三级说明"目标有数据"，第四级也只要求口径正确——而**相关性仍不自动等于因果**。
- "C1 与 C2 是两份独立采集"意味着连最弱的一步都没过：**没有证明分配活动和 CPU 上升在同一时间窗、同一进程实例上同时发生**。两个在不同时间窗独立成立的"现象 A"和"现象 B"，推不出"A 导致 B"。
- 即使合成同一份 trace，要谈"分配导致 CPU 抖动"至少要补齐：
  1. 同一 UPID、同一时间窗内，分配活动与 CPU 上升同时出现；
  2. CPU 上升确实落在**分配路径/分配线程**：需要 `sched_switch` 的线程级 runtime，或 perf CPU 采样命中 malloc/allocator 帧，或经授权的应用阶段/帧标记；
  3. **排除观察者效应**：heapprofd 有共享内存、拷栈、同步与 daemon 处理成本，dump 周期本身可能产生周期性 CPU。"每隔几秒 CPU 上升"与 5 秒 dump 周期的重合必须先被排除，否则可能是 profiler 自己在抖；
  4. 排除其他周期源：业务周期任务、GC、IO、调度；
  5. **消融/对照**：减少或绕开分配路径后抖动应随之变化；无 profiler 的同负载对照应能看到业务侧抖动是否本来就存在。

- 另一个必须自查的点：C1 里的"每隔几秒"如果是 1 秒轮询 counter 得出的，就存在**混叠**——1 秒采样无法分辨亚秒级 CPU 尖峰，"周期性"可能是采样相位造成的假象。需要 `sched_switch` 切片或更细事件确认，而不是把轮询点当作真实波形。

**可以接受的部分**：可以说"已成功采到 C2 的 allocation 数据"（数据级）；不可以说"因此分配导致 CPU 抖动"。

**判定：因果结论 FAIL；真实成因 UNKNOWN。**

## 2. 总评表

| # | 主张 | 判定 | 可保留的说法 | 还缺的决定性证据 |
|---|---|---|---|---|
| 1 | C1 绝对时间戳直接填进 C2 SQL 即可对齐分配与 CPU | FAIL（条件未满足） | 同一 trace 内按窗口对齐是合法的；跨 trace 需先验证时钟/开机/窗口/UPID | 时钟域与 boot 一致、窗口重叠、同一进程实例、dump 窗口起点可知 |
| 2 | heapprofd dump 时间 = 每次 malloc 时间 | FAIL（采集器行为） | 可回答"某 dump 窗口内的聚合分配量/保留量估计" | 逐分配时间 heapprofd 不提供；需要事件型数据源或接受 dump 级粒度 |
| 3 | count 高 = 调用次数多 | PARTIAL（限定口径） | 可说明"该窗口内分配活跃/被采样的次数估计高" | 明确指标名（Total/Unreleased）、采样间隔、重复试验；CPU 需另证 |
| 4 | 采集成功 ⇒ 分配导致 CPU 抖动 | FAIL（因果不成立） | 可说明"已采到 allocation 数据" | 同窗共现、分配路径归因、观察者效应排除、消融/对照 |

## 3. 下一步最小补采 / 验证建议（按优先级）

### P0（最高优先）：单 trace 同时采，把"跨文件对齐"变成"同文件对齐"

目标：**一份 trace 内同时包含 process/sys counter、`sched_switch`、heapprofd**，并且覆盖同一业务窗口、同一进程实例。

注意：本包生成器没有现成的"sched + heap 同时"场景，需要把两段**合并成一份完整 TraceConfig**（不能只给片段让用户猜嵌套位置）。下面是合并模板，`TARGET`/duration/poll 按实际替换；**未做本次版本 schema 验证**，数据源名与字段按目标采集器版本核对：

```text
# 合并模板（示意；字段/数据源名以采集器版本为准）
buffers { size_kb: 8192 fill_policy: RING_BUFFER }
buffers { size_kb: 4096 fill_policy: DISCARD }
buffers { size_kb: 32768 fill_policy: DISCARD }
duration_ms: 30000

data_sources { config {
  name: "linux.process_stats"
  target_buffer: 1
  process_stats_config {
    scan_all_processes_on_start: true
    proc_stats_poll_ms: 1000
  }
} }
data_sources { config {
  name: "linux.sys_stats"
  target_buffer: 0
  sys_stats_config {
    meminfo_period_ms: 1000
    meminfo_counters: MEMINFO_MEM_FREE
    meminfo_counters: MEMINFO_MEM_AVAILABLE
    vmstat_period_ms: 1000
    vmstat_counters: VMSTAT_PGFAULT
  }
} }
data_sources { config {
  name: "linux.ftrace"
  target_buffer: 0
  ftrace_config {
    buffer_size_kb: 1024
    drain_period_ms: 250
    ftrace_events: "sched/sched_switch"
  }
} }
data_sources { config {
  name: "android.heapprofd"          # 数据源名按目标版本核对
  target_buffer: 2
  heapprofd_config {
    sampling_interval_bytes: 4096
    process_cmdline: "TARGET"
    shmem_size_bytes: 8388608
    block_client: false
    continuous_dump_config { dump_interval_ms: 5000 }
  }
} }
```

执行前必须核对的运行条件（缺一不可，不能因为"生成成功"就当作可用）：

- `sched/sched_switch` 是否在目标 `available_events` 中真实存在；没有就退回 counter 方案并写明分辨率损失；
- heapprofd producer 是否可用、权限/启动方式是否与 C2 相同（尤其是普通 Linux 的 LD_PRELOAD/启动顺序；不能给已运行、未 preload 的进程凭空补 hook）；
- `block_client:false` 会带来丢失/提前终止风险，需检查 stats 与日志；
- `dump_interval_ms` 与分析粒度必须匹配：5 秒 dump 只能给 5 秒粒度。若 CPU 周期更短，要么接受"只能对齐到 5 秒窗口"的表述，要么更密 dump（开销上升），**不要用插值伪造更细的分配时间线**。

### P1（与 P0 配套，用来排除观察者效应）

同一负载、同一 duration，**去掉 heapprofd**，只采 counters+sched：

```bash
# 主机生成（示例；--events 来自目标机实际 available_events）
python3 scripts/make_config.py kernel-pressure --platform linux \
  --events available_events.txt --sched --duration-ms 30000 > control-noheap.pbtxt
```

判读：

- 对照里"每隔几秒 CPU 上升"依然存在 → 该周期**与 profiler 无关**（至少不是 profiler 造成的），才值得继续追"分配是否参与"；
- 只有开 profiler 才出现 → 优先怀疑采集开销 / dump 周期本身，而不是业务分配。

### P2（在同一份 trace 内做时间关联，允许的写法）

- 用 `sched_switch` 推导目标进程/线程的**线程级 runtime**，定位 CPU 上升窗口 `[t0,t1]`（不要用 1 秒轮询 counter 的采样点直接当波形）。
- 在**同一 trace** 内取该 UPID + `libc.malloc` 的 `heap_profile_allocation` 行，按 dump 窗口（`ts_end`，若 `dur>0`）判断哪些 dump 与 `[t0,t1]` 相交。
- 结论只能写成"这些 dump 窗口内的分配活动与 CPU 上升窗口重叠"；**不要**写成"某次 malloc 导致了这段 CPU"。
- 关联前先跑 `sql/00-inventory.sql`（确认 UPID、候选与歧义）和 `sql/10-native-dump-capability.sql`（确认 `dumps`、`distinct_ts_end`、`zero_dur_dumps`）。若 `zero_dur_dumps == dumps`，精确窗口是 **UNKNOWN**，不能拿 `dump_interval_ms` 反推"应该有几份 dump 与实际不符"。
- 参考 SQL（示意，表名/函数按本机 Trace Processor 版本核对；`<UPID>` 用 inventory 结果，不要填 -1 后把空结果当"无分配"）：

```sql
-- 线程级 CPU 切片：先定位 CPU 上升发生在哪个线程
SELECT s.ts, s.dur, s.cpu, t.name AS thread_name, p.name AS process_name, p.upid
FROM sched_slice s
JOIN thread t USING (utid)
JOIN process p USING (upid)
WHERE p.upid = <UPID> AND s.dur > 0
ORDER BY s.ts;
-- sched_switch 只说明调度状态的一部分，不能独自解释所有等待原因。
```

### P3（若坚持复用现有 C1/C2，不重采）

先按顺序核对四项，全部通过才允许做窗口级粗对齐：

1. 是否同一台设备、同一次开机（中间没有重启）；
2. 两份 trace 的时钟域是否一致，`trace_bounds` 覆盖的时间是否重叠；
3. C1 的目标与 C2 的目标是否为**同一进程实例**（UPID/PID、是否重启、是否误用同名 preload 子进程）；
4. C1 的"周期"能否用事件级数据（sched 切片）复现，而不是 1 秒轮询的混叠。

任何一项不通过 → 只能分别描述两个现象，**不能对齐，更不能因果**。
另外：不要直接把 C1 的单个绝对时间戳填进 C2 的 `start_ts = end_ts`（大概率筛出 0 行，而 0 行不等于没有分配）。

### P4（如果要把"CPU 高"落到分配路径）

- 需要 CPU 侧证据：perf 采样调用栈（命中 malloc/allocator 帧；Linux perf 权限与 producer 先做 preflight，`--perf-confirmed` 不是开权限的开关），或 sched 的线程级 runtime，或经授权的应用阶段/帧标记。
- 有了这些仍只是"CPU 花在分配相关路径上"；要证明"分配导致 CPU 抖动"，还需要**消融**（减少分配/复用对象后抖动变化）和**无 profiler 对照**。

## 4. 补采后的采集验收（不通过不能进入分析）

- 目标 UPID 正确；PID 复用/重启/同名进程未混；C1 与 C2 指向同一实例。
- `trace_bounds` 覆盖完整复现窗口；开头的启动阶段与结尾没有因 buffer 轮转丢掉关键证据。
- C2：`heap_profile_allocation` 有目标 UPID + `libc.malloc` 行；记录 `dumps`、`distinct_ts_end`、`zero_dur_dumps`。
- `dur = 0` 时按三态写：**精确持有/对齐窗口 UNKNOWN**；总量、分配/释放、符号等仍可判 PASS/FAIL，不要因为 `dur=0` 把全部结论判未知。
- 符号：没有 unstripped ELF / 独立 debug 文件时先按模块归因，不承诺源码行号。
- 记录 `sampling_interval_bytes`、`dump_interval_ms`、是否 `block_client`；采样是估计，重复同一 workload 再看稳定性。
- C1：确认 counter 的单位与采样周期；用 `sched_switch` 切片确认"周期性上升"不是 1 秒轮询混叠。
- 检查 stats 与 collector/daemon 日志：heap/ftrace/packet 相关 data loss、并发拒绝、socket 断开、unwind 失败等，字段名以实际版本输出为准。

## 5. 如何下结论（判读规则）

- **支持"分配与 CPU 相关"的最低证据**：同一 trace、同一 UPID、时间窗真实重叠；线程级 CPU 上升落在分配线程/分配路径；无 profiler 对照下业务侧抖动仍存在；消融后抖动变化。
- **削弱或反驳**：CPU 上升只在开 profiler 时出现（观察者效应）；CPU 上升线程与分配线程不同；时间窗不重叠；目标不是同一进程；分配数据为空/符号缺失；"周期"是 1 秒轮询混叠造成的假象。
- **本次现状**：C1 与 C2 只支持"各自现象存在"；**"分配导致 CPU 抖动"目前是 UNKNOWN**，既不能确认，也不能否定。
- **一个最有价值的下一步**：P0 单 trace 同步采集 + P1 无 profiler 对照。这两项先过掉"观察者效应"和"时间上是否真的同时发生"两关，再决定是否值得投入 P4 的 CPU 归因与消融。
