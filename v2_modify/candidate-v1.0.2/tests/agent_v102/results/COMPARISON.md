# v1.0.1 vs v1.0.2 独立 Agent 行为对照

## 方法

- 六个独立子会话：B1/B2/B3 × v1.0.1/v1.0.2。
- 每个会话只允许读取对应候选目录的 `SKILL.md`、`references/`、`sql/`、`scripts/`、`tests/`；
  明确禁止读取 `v2_test/`、`v2_modify/`、`v2_modify2/`、其他候选和历史评分/纠错材料。
- 场景文件只描述用户输入，不提供预期答案；rubric 只给评审，不给被测 Agent。
- 同一套 DSH 子会话编排与模型路由；未显式控制 temperature，单次运行，不做统计显著性结论。
- 原始输出：`v101_B1.md`、`v102_B1.md`、`v101_B2.md`、`v102_B2.md`、
  `v101_B3.md`、`v102_B3.md`。

## 结果摘要

| 场景 | v1.0.1 | v1.0.2 | 结论 |
|---|---|---|---|
| B1 Linux 生命周期 | 有主机/目标变量表和停止/flush 段落；heapprofd 主路径仍以 `--system-sockets --background-wait` 为前提，失败后才给降级；没有复用包内生命周期脚本 | 直接使用 `scripts/linux_trace_session.sh`、`linux_heapprofd_session.sh`、`host_pull.sh`；明确 `--background-wait` 不作为 heapprofd 前提，增加 producer 等待、socket 只读降级、SCP 失败传播 | v1.0.2 更完整、可复用；v1.0.1 有风险路径 |
| B2 CPU 桶/spike | 明确说该问题不在 Skill 覆盖路由内，自行写出正确的区间交集和 episode SQL；数学正确，但不是包内可复用资产 | 直接引用 `sql/11`/`sql/12`，参数化 UPID/窗口/桶宽/阈值；指出“总量守恒不能判别逐桶对错”，并给出线程级变体与验证 | 两者数学都正确；v1.0.2 的交付一致性和复用性更好 |
| B3 证据边界 | 三条说法均正确否定；强调独立 trace 时钟、dump 快照、采样 count、profiler 成功不等于因果 | 同样正确，且与新增的 `06-quality` 检查项和证据等级一致；显式使用“四级验收/UNKNOWN” | 两者均通过；v1.0.2 与文档更一致 |

## 评分（按 `rubric.md`，仅本次单次运行）

| 场景 | v1.0.1 | v1.0.2 | 说明 |
|---|---|---|---|
| B1 | 部分通过 | 通过 | v1.0.1 的 `--background-wait` 主路径在 producer 未注册时可能等不到；v1.0.2 改为“起 trace → 起 app → 等 producer” |
| B2 | 部分通过（正确但自写） | 通过 | v1.0.1 未复用包内实现；v1.0.2 使用通用 SQL 且保留反例 |
| B3 | 通过 | 通过 | 两者都未把 profiler 成功当因果；v1.0.2 的表述更贴近质量指南 |

## 观察与限制

- v1.0.1 的两个 Agent 已经能凭通用知识写出不少正确内容（尤其 B2/B3），所以本次差异主要是
  **生命周期可靠性、包内复用和交付一致性**，不是“旧版完全不会”。
- v1.0.2 的 B1 输出直接引用了新脚本和 `PERFETTO_*_SOCK_NAME` 降级，说明入口指引被实际读取；
  B2 输出引用了 `sql/11`/`sql/12`，说明新增 SQL 被实际使用；B3 引用了 `06-quality` 新检查项。
- 单次运行、无温度控制、无第二评审；这些是行为烟雾测试，不是统计基准。不能据此声称
  v1.0.2 在所有模型/所有输入上普遍优于 v1.0.1。
- 原始输出可能包含模型自行补充的、Skill 未声明的细节；评审时应以 rubric 和实际证据为准。
- 三个场景均未上板、未执行真实 trace；所有设备/性能结论仍是待验证。
