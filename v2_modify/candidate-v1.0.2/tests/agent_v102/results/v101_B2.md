## 1. 定位路线

### 1.1 问题拆解

| 项 | 内容 |
|---|---|
| 待回答 | 目标进程（UPID 42）在 trace 内 1.2 s–4.8 s 里，**每线程每 100 ms** 消耗多少 CPU 时间；哪些连续 100 ms 桶构成高 CPU 的 spike episode |
| 已给证据 | 一份已有 trace；UPID、窗口、桶宽、阈值 |
| 假设 | “存在以 100 ms 为粒度的、连续高 CPU 的突发段；安静桶之间必须是不同 episode” |
| 数据源 | `thread_state` 中 `state='Running'` 的区间（由 `sched/sched_switch` 解析而来）；`sched_slice` 仅作独立对照 |
| **不覆盖** | Runnable/等待时间、off-CPU 原因、CPU 频率与 cycles、指令数、perf 采样热点、内存、帧时间；也不能证明“高 CPU 导致掉帧” |

### 1.2 CPU 时间的口径（必须先说清，否则桶值没有意义）

- **采用**：`Running` 状态的**墙钟时长**。运行 30 ms 记 30 ms，无论跑在哪个 CPU、什么频率。
- **不采用**：CPU cycles（需要 cpufreq/PMU，且不是 Perfetto 每线程时间线的默认口径）；
  也不采用 “Runnable + Running” 合并值（Runnable 是等 CPU，不是耗 CPU）。
- 单线程在一个 100 ms 桶内**最多 100 ms**（100% 占用）。→ 这直接给出下面 §8 最关键的不变量。
- 同一桶内把多个线程相加，进程级可以超过 100 ms；**per-thread 不可以**。

### 1.3 桶与 episode 的精确定义（这是本题的判分核心）

记桶宽 `w = bucket_ns`，网格锚点 `o = grid_origin`，第 k 个桶是**半开区间**

```
B_k = [ o + k·w , o + (k+1)·w )
```

1. **桶网格锚定在 `win_start`**（默认 `grid_origin = win_start`），所以本题 idx 0 = [1.2 s, 1.3 s)。
   若要与别处“绝对 100 ms 网格”对齐，把 `grid_origin` 设为 0（要求 ≤ `win_start`）。
   锚点不同 ⇒ 桶边界不同 ⇒ episode 起止桶不同，**报告里必须写锚点**。
2. **裁剪**：分析窗口与 `trace_bounds` 求交得到 `[a_start, a_end)`；每个 Running 区间先裁到窗口，
   再与桶求交。窗口外的时间**丢弃**，不能算进窗口。
3. **跨桶区间必须切开**。对单区间 `r = [t0,t1)`：

   ```
   overlap(k) = max(0, min(t1, o+(k+1)w) − max(t0, o+kw))
   ```

   这是唯一正确的记账方式，`Σ_k overlap(k) = t1 − t0`（守恒），且 `0 ≤ overlap(k) ≤ w`。
4. **阈值**：满桶 100 ms 对应 5 ms（即 5% 占空比）。含等号：`cpu ≥ 5 ms` 判高。
   对**部分桶**（窗口不是 `w` 整数倍时才会出现）按占空比归一：
   `cpu_ns · w ≥ threshold_ns · observed_ns`。满桶时代简化为 `cpu_ns ≥ threshold_ns`。
   本题 3.6 s / 100 ms = **恰好 36 个满桶**，但 SQL 仍保留这个保护。
5. **episode = 极长的连续高桶串**。默认 `min_quiet_buckets = 1`，即“**任何一个安静桶都切断**”。
   高桶 `idx` 与上一个高桶 `idx_prev` 满足 `idx − idx_prev > min_quiet_buckets` 时开新 episode；
   `= 1` 时就是严格连续。把该参数调大等于放宽题目要求（允许 1 个安静桶被吞掉），
   一旦调大必须在结论里声明，且注意 episode 区间内会合法地包含安静桶（SQL 用
   `n_quiet_inside` 显式暴露）。
6. **窗口边缘删失（censoring）**：episode 命中第一个/最后一个桶时，窗口外的延续情况不可知，
   长度只是**下界**，必须打 `left_censored` / `right_censored`，不能当完整 episode 报告。
7. **零桶必须显式存在**：线程存在但该桶没跑，是“0 ns”，必须有一行 0；
   否则“没有行”会被误读成“安静”或直接被跳过，episode 就会跨过安静间隔合并。
   —— 这一条只在那份 trace 的 sched 数据**完整**时成立；有丢事件时缺行 = UNKNOWN，不是 0
   （`SKILL.md` §5）。

### 1.4 复杂度

- 桶数 = `(a_end−a_start)/w`，本题 36；`dense = 线程数 × 36`，很小。
- `overlap` 是 `runs × 覆盖桶数` 的区间连接，不是 `runs × 全部桶` 的笛卡尔积
  （连接条件把范围限制在真正相交的桶）。
- 若窗口/桶宽改成“10 s / 1 ms”，单线程的 `runs` 可能有数万行，`dense` 上万行，
  仍然可跑；再大就应先按 utid 逐个分析。

## 4. Q1：每线程 × 100 ms 桶 CPU 时间（主查询，直接做 Counter Track）

```sql
-- ============================================================================
-- Q1  每线程 / 每桶 CPU 时间(ms)
-- 口径: thread_state 'Running' 与桶求交后求和(跨桶区间被切开), 不是整段记账
-- 参数: 只改 params; 不出现进程名; ts 全部 ns
-- UI  : Add debug track -> Counter Track; Timestamp=ts; Value=value; Pivot=series
-- 状态: 本 SQL 未在真实 trace_processor 执行(见 §0.2)
-- ============================================================================
WITH RECURSIVE
params AS (
  SELECT
    42            AS target_upid,       -- 目标进程 UPID
    1200000000    AS win_start,         -- 1.2 s
    4800000000    AS win_end,           -- 4.8 s (半开)
    100000000     AS bucket_ns,         -- 100 ms
    5000000       AS threshold_ns,      -- 5 ms / 满桶
    1200000000    AS grid_origin,       -- 桶网格锚点, 必须 <= win_start
    1             AS min_quiet_buckets  -- 1 = 任何安静桶都切断 episode
),
win AS (
  SELECT p.*,
         max(p.win_start, b.start_ts) AS a_start,
         min(p.win_end,   b.end_ts)   AS a_end,
         b.start_ts AS trace_start,
         b.end_ts   AS trace_end
  FROM params p CROSS JOIN trace_bounds b
),
grid AS (
  SELECT w.*,
         CAST((w.a_start - w.grid_origin) / w.bucket_ns AS INTEGER) AS first_idx,
         CAST((w.a_end - 1 - w.grid_origin) / w.bucket_ns AS INTEGER) AS last_idx
  FROM win w
  WHERE w.a_end > w.a_start
    AND w.bucket_ns > 0
    AND w.grid_origin <= w.a_start          -- 否则整数除法会向零截断而错位
),
buckets(idx) AS (                            -- 递归生成桶序号(本题 0..35)
  SELECT g.first_idx FROM grid g
  UNION ALL
  SELECT b.idx + 1 FROM buckets b CROSS JOIN grid g WHERE b.idx < g.last_idx
),
bkt AS (                                     -- 每个桶的"实际被窗口观测到"的半开区间
  SELECT b.idx,
         max(g.grid_origin + b.idx * g.bucket_ns,       g.a_start) AS obs_start,
         min(g.grid_origin + (b.idx + 1) * g.bucket_ns, g.a_end)   AS obs_end
  FROM buckets b CROSS JOIN grid g
),
threads AS (
  SELECT t.utid, t.tid, t.name, t.is_main_thread
  FROM thread t CROSS JOIN grid g
  WHERE t.upid = g.target_upid
),
runs AS (                                    -- Running 区间: 先裁到窗口内
  SELECT ts.utid,
         max(ts.ts,        g.a_start) AS c_start,
         min(ts.ts + ts.dur, g.a_end) AS c_end
  FROM thread_state ts CROSS JOIN grid g
  WHERE ts.state = 'Running'
    AND ts.dur >= 0                          -- -1 = 未结束, 不能当有限时长
    AND ts.utid IN (SELECT utid FROM threads)
    AND ts.ts < g.a_end
    AND ts.ts + ts.dur > g.a_start
),
overlap AS (                                 -- ★ 区间 × 相交桶, 每个贡献是交集长度
  SELECT r.utid, b.idx,
         SUM(min(r.c_end, b.obs_end) - max(r.c_start, b.obs_start)) AS cpu_ns
  FROM runs r
  JOIN bkt b
    ON r.c_start < b.obs_end
   AND r.c_end   > b.obs_start
  GROUP BY r.utid, b.idx
),
span AS (                                    -- 该线程在本窗口内"被观测到在跑"的覆盖
  SELECT utid, MIN(c_start) AS first_seen, MAX(c_end) AS last_seen
  FROM runs GROUP BY utid
),
dense AS (                                   -- ★ 线程 × 桶 补零, 保证安静桶有显式 0 行
  SELECT th.utid, th.tid, coalesce(th.name, '<unnamed>') AS thread_name, th.is_main_thread,
         b.idx, b.obs_start, b.obs_end,
         b.obs_end - b.obs_start AS observed_ns,
         coalesce(o.cpu_ns, 0)   AS cpu_ns
  FROM threads th
  CROSS JOIN bkt b
  LEFT JOIN overlap o ON o.utid = th.utid AND o.idx = b.idx
),
scored AS (                                  -- 部分桶按占空比归一; 满桶即 cpu_ns >= threshold_ns
  SELECT d.*, g.bucket_ns, g.threshold_ns,
         CASE WHEN d.cpu_ns * g.bucket_ns >= g.threshold_ns * d.observed_ns
              THEN 1 ELSE 0 END AS is_high
  FROM dense d CROSS JOIN grid g
)
SELECT s.obs_start                          AS ts,          -- ns
       s.cpu_ns / 1000000.0                 AS value,       -- ms, Counter 值
       'utid ' || s.utid || ' | tid ' || s.tid
         || ' | ' || s.thread_name
         || ' | CPU ms per ' || (s.bucket_ns / 1000000) || ' ms bucket' AS series,
       s.utid, s.tid, s.idx,
       s.bucket_ns, s.threshold_ns,
       s.cpu_ns, s.observed_ns,
       s.cpu_ns / 1000000.0                 AS cpu_ms,
       s.cpu_ns / 1000000.0 / (s.observed_ns / 1000000.0) AS duty,
       s.is_high,
       sp.first_seen, sp.last_seen
FROM scored s
LEFT JOIN span sp ON sp.utid = s.utid
ORDER BY s.utid, s.idx;
```

要点：

- `value` 用**毫秒**（便于人读、也便于阈值线同单位）；`ts` 保持**纳秒**（debug track 要求，A26）。
- `series` 含 `utid | tid | name`：**不能只用线程名做 pivot**，同名线程会合并成一个系列。
- `duty` 是桶内占空比（0–1），`observed_ns` 通常是 100 ms（满桶）。
- `first_seen/last_seen` 为 NULL ⇒ 该线程在本窗口内没有 Running 记录（从未运行或数据缺失，
  用 Q0 区分）；这类线程的 0 桶**不能**当作“安静”。
- 进程级变体见附录 A（注意：进程级桶值可以 > 100 ms，§8 的 I1 不变量要改写）。

```sql
         max(p.win_start, b.start_ts) AS a_start,
         min(p.win_end,   b.end_ts)   AS a_end
  FROM params p CROSS JOIN trace_bounds b
),
grid AS (
  SELECT w.*,
         CAST((w.a_start - w.grid_origin) / w.bucket_ns AS INTEGER) AS first_idx,
         CAST((w.a_end - 1 - w.grid_origin) / w.bucket_ns AS INTEGER) AS last_idx
  FROM win w
  WHERE w.a_end > w.a_start AND w.bucket_ns > 0 AND w.grid_origin <= w.a_start
),
buckets(idx) AS (
  SELECT g.first_idx FROM grid g
  UNION ALL
  SELECT b.idx + 1 FROM buckets b CROSS JOIN grid g WHERE b.idx < g.last_idx
),
bkt AS (
  SELECT b.idx,
         max(g.grid_origin + b.idx * g.bucket_ns,       g.a_start) AS obs_start,
         min(g.grid_origin + (b.idx + 1) * g.bucket_ns, g.a_end)   AS obs_end
  FROM buckets b CROSS JOIN grid g
),
threads AS (
  SELECT t.utid, t.tid, t.name, t.is_main_thread
  FROM thread t CROSS JOIN grid g WHERE t.upid = g.target_upid
),
runs AS (
  SELECT ts.utid, max(ts.ts, g.a_start) AS c_start, min(ts.ts + ts.dur, g.a_end) AS c_end
  FROM thread_state ts CROSS JOIN grid g
  WHERE ts.state = 'Running' AND ts.dur >= 0
    AND ts.utid IN (SELECT utid FROM threads)
    AND ts.ts < g.a_end AND ts.ts + ts.dur > g.a_start
),
overlap AS (
  SELECT r.utid, b.idx,
         SUM(min(r.c_end, b.obs_end) - max(r.c_start, b.obs_start)) AS cpu_ns
  FROM runs r JOIN bkt b
    ON r.c_start < b.obs_end AND r.c_end > b.obs_start
  GROUP BY r.utid, b.idx
),
dense AS (
  SELECT th.utid, th.tid, coalesce(th.name, '<unnamed>') AS thread_name,
         b.idx, b.obs_start, b.obs_end,
         b.obs_end - b.obs_start AS observed_ns,
         coalesce(o.cpu_ns, 0)   AS cpu_ns
  FROM threads th CROSS JOIN bkt b
  LEFT JOIN overlap o ON o.utid = th.utid AND o.idx = b.idx
),
scored AS (
  SELECT d.*,
         CASE WHEN d.cpu_ns * g.bucket_ns >= g.threshold_ns * d.observed_ns
              THEN 1 ELSE 0 END AS is_high
  FROM dense d CROSS JOIN grid g
),
high AS (                                   -- 只留高桶, 记住上一个高桶
  SELECT s.utid, s.tid, s.thread_name, s.idx, s.obs_start, s.obs_end, s.cpu_ns,
         LAG(s.idx) OVER (PARTITION BY s.utid ORDER BY s.idx) AS prev_idx
  FROM scored s WHERE s.is_high = 1
),
marked AS (                                 -- 安静桶数 >= min_quiet_buckets 就开新 episode
  SELECT h.*,
         CASE WHEN h.prev_idx IS NULL
                   OR (h.idx - h.prev_idx) > g.min_quiet_buckets
              THEN 1 ELSE 0 END AS new_ep
  FROM high h CROSS JOIN grid g
),
ep AS (
  SELECT m.*,
         SUM(m.new_ep) OVER (PARTITION BY m.utid ORDER BY m.idx
                             ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS ep_no
  FROM marked m
)
SELECT
  'utid ' || e.utid || ' | tid ' || e.tid || ' | ' || e.thread_name
    || ' | spike episodes'                                  AS series,
  e.utid, e.tid, e.thread_name, e.ep_no,
  MIN(e.obs_start)                                          AS ts,    -- episode 起点, ns
  MAX(e.obs_end) - MIN(e.obs_start)                         AS dur,   -- 墙钟时长, ns
  MIN(e.idx)                                                AS first_idx,
  MAX(e.idx)                                                AS last_idx,
  COUNT(*)                                                  AS n_high_buckets,
  MAX(e.idx) - MIN(e.idx) + 1                               AS n_span_buckets,
  MAX(e.idx) - MIN(e.idx) + 1 - COUNT(*)                    AS n_quiet_inside,
  SUM(e.cpu_ns)                                             AS cpu_ns,
  ROUND(SUM(e.cpu_ns) / 1000000.0, 3)                       AS cpu_ms,
  ROUND(MAX(e.cpu_ns) / 1000000.0, 3)                       AS peak_bucket_ms,
  ROUND(1.0 * SUM(e.cpu_ns) / (MAX(e.obs_end) - MIN(e.obs_start)), 4) AS duty,
  CASE WHEN MIN(e.idx) = g.first_idx THEN 1 ELSE 0 END      AS left_censored,
  CASE WHEN MAX(e.idx) = g.last_idx  THEN 1 ELSE 0 END      AS right_censored,
  'spike' || e.ep_no
    || ' cpu=' || ROUND(SUM(e.cpu_ns) / 1000000.0, 1) || 'ms'
    || ' n=' || COUNT(*) || 'b'
    || CASE WHEN MAX(e.idx) = g.last_idx OR MIN(e.idx) = g.first_idx
            THEN ' (censored)' ELSE '' END                   AS name
FROM ep e CROSS JOIN grid g
GROUP BY e.utid, e.tid, e.thread_name, e.ep_no
ORDER BY e.utid, e.ep_no;
```

判读要点：

- `dur` 是**墙钟**长度，不等于 CPU 时间；`cpu_ms` 才是 CPU。1 个桶的 episode `dur` 也是 100 ms。
- `n_quiet_inside` 在严格模式（`min_quiet_buckets = 1`）必须恒为 **0**；>0 说明有人把间隔合并了。
- `left_censored/right_censored = 1` ⇒ 该 episode 只是**下界**，不能写“持续 X ms 的 spike”。
- 没有 episode 的线程不会出现在结果里；若要显式列出“哪些线程没有 spike”，用
  `threads LEFT JOIN (Q2 结果)`，不要把“没出现”当成“没跑”。

## 7. Q4：跨桶区间明细（“跨桶到底怎么切”的直接证据）

```sql
-- Q4  列出窗口内每个跨桶 Running 区间被切成了几段, 并检查分段之和 == 裁剪后时长
--     这是 §10.1 跨桶验证的可视化证据; 结果可能很多, 先限一个 utid 或加 LIMIT
WITH RECURSIVE
params AS (

         1200000000 AS grid_origin, 1 AS min_quiet_buckets
),

  SELECT p.*, max(p.win_start, b.start_ts) AS a_start, min(p.win_end, b.end_ts) AS a_end
  FROM params p CROSS JOIN trace_bounds b
),
grid AS (
  SELECT w.*,
         CAST((w.a_start - w.grid_origin) / w.bucket_ns AS INTEGER) AS first_idx,
         CAST((w.a_end - 1 - w.grid_origin) / w.bucket_ns AS INTEGER) AS last_idx
  FROM win w
  WHERE w.a_end > w.a_start AND w.bucket_ns > 0 AND w.grid_origin <= w.a_start
),
buckets(idx) AS (
  SELECT g.first_idx FROM grid g
  UNION ALL
  SELECT b.idx + 1 FROM buckets b CROSS JOIN grid g WHERE b.idx < g.last_idx
),
bkt AS (
  SELECT b.idx,
         max(g.grid_origin + b.idx * g.bucket_ns,       g.a_start) AS obs_start,
         min(g.grid_origin + (b.idx + 1) * g.bucket_ns, g.a_end)   AS obs_end
  FROM buckets b CROSS JOIN grid g
),
threads AS (
  SELECT t.utid, t.tid, t.name FROM thread t CROSS JOIN grid g
  WHERE t.upid = g.target_upid
),
runs AS (
  SELECT ts.utid, max(ts.ts, g.a_start) AS c_start, min(ts.ts + ts.dur, g.a_end) AS c_end
  FROM thread_state ts CROSS JOIN grid g
  WHERE ts.state = 'Running' AND ts.dur >= 0
    AND ts.utid IN (SELECT utid FROM threads)
    AND ts.ts < g.a_end AND ts.ts + ts.dur > g.a_start
),
cuts AS (
  SELECT r.utid, r.c_start, r.c_end, b.idx,
         max(r.c_start, b.obs_start) AS seg_start,
         min(r.c_end,   b.obs_end)   AS seg_end
  FROM runs r JOIN bkt b
    ON r.c_start < b.obs_end AND r.c_end > b.obs_start
)
SELECT utid, c_start, c_end,
       c_end - c_start                         AS clipped_ns,
       COUNT(*)                                AS n_buckets_touched,
       MIN(idx)                                AS first_idx,
       MAX(idx)                                AS last_idx,
       SUM(seg_end - seg_start)                AS sum_segments_ns,
       CASE WHEN SUM(seg_end - seg_start) = c_end - c_start
            THEN 1 ELSE 0 END                  AS split_ok,
       MAX(seg_end - seg_start)                AS max_segment_ns
FROM cuts
GROUP BY utid, c_start, c_end
HAVING COUNT(*) > 1
ORDER BY utid, c_start
LIMIT 200;

-- 任一行 split_ok=0 => 分段算术坏了。
-- 若要看某个区间逐桶的段, 去掉 GROUP BY, 直接 SELECT cuts 行。
```

## 8. 反例：区分“正确实现”与“把完整 duration 记到起始桶”

### 8.1 错误实现（看起来很像正确 SQL）

```sql
-- ✗ 反例: 按 sched_slice/thread_state 的起始桶聚合, 完整 dur 一次记账
-- 问题: (a) 不按桶边界切开; (b) 不裁剪窗口; (c) 不补零
SELECT CAST((max(ts.ts, 1200000000) - 1200000000) / 100000000 AS INTEGER) AS idx,
       ts.utid,
       SUM(ts.dur) AS cpu_ns
FROM thread_state ts
WHERE ts.state = 'Running' AND ts.dur >= 0 AND ts.utid IN (SELECT utid FROM thread WHERE upid = 42)
  AND ts.ts < 4800000000 AND ts.ts + ts.dur > 1200000000
GROUP BY idx, ts.utid;
-- 它满足 "Σ 桶 = Σ 时长" 的守恒, 但每个桶值可以是桶宽的整数倍,
-- 并且跨桶区间在"起始桶"人为堆成一个尖峰。
```

### 8.2 可执行 fixture（**不依赖 trace**，UI Query 或 sqlite3 都能跑）

```sql
-- ============================================================================
-- 反例对照 fixture: 5 个合成 Running 区间, 窗口 [1.2s,4.8s), 100ms 桶, 阈值 5ms
-- 输出: impl='correct' 逐桶交集 vs impl='start_bucket' 整段记账
-- 状态: 未执行; 期望值见 §8.3 手算表
-- ============================================================================
WITH RECURSIVE
p AS (SELECT 100000000 AS bw, 5000000 AS thr,
             1200000000 AS origin, 4800000000 AS a_end),
fx(utid, tid, ts, dur) AS (VALUES
  (1, 101, 1296000000,   8000000),   -- 8 ms, 跨 1.3 s 边界
  (1, 101, 1500000000,   6000000),   -- 6 ms, 桶内
  (1, 101, 1700000000,   6000000),   -- 6 ms, 桶内, 与上一个隔 1 个安静桶
  (2, 102, 1300000000, 300000000),   -- 300 ms, 跨 3 个桶
  (2, 102, 4650000000, 200000000)    -- 200 ms, 右端被窗口裁掉 50 ms
),
buckets(idx) AS (SELECT 0 UNION ALL SELECT idx + 1 FROM buckets WHERE idx < 35),
runs AS (
  SELECT f.utid, f.tid,
         max(f.ts, p.origin)          AS c_start,
         min(f.ts + f.dur, p.a_end)   AS c_end
  FROM fx f CROSS JOIN p
  WHERE f.ts < p.a_end AND f.ts + f.dur > p.origin
),
correct AS (                                   -- 逐桶求交
  SELECT r.utid, r.tid, b.idx,
         SUM(min(r.c_end, p.origin + (b.idx + 1) * p.bw)
           - max(r.c_start, p.origin + b.idx * p.bw)) AS cpu_ns
  FROM runs r CROSS JOIN p CROSS JOIN buckets b
  WHERE r.c_start < p.origin + (b.idx + 1) * p.bw
    AND r.c_end   > p.origin + b.idx * p.bw
  GROUP BY r.utid, r.tid, b.idx
),
wrong AS (                                     -- 整段记到起始桶(仍裁窗口)
  SELECT r.utid, r.tid,
         CAST((r.c_start - p.origin) / p.bw AS INTEGER) AS idx,
         SUM(r.c_end - r.c_start) AS cpu_ns
  FROM runs r CROSS JOIN p
  GROUP BY r.utid, r.tid, idx
)
SELECT impl, utid, tid, idx,
       origin_ns, cpu_ns,
       cpu_ns / 1000000.0            AS cpu_ms,
       CASE WHEN cpu_ns >= thr_ns THEN 1 ELSE 0 END AS is_high,
       CASE WHEN cpu_ns > bw_ns     THEN 1 ELSE 0 END AS violates_bucket_width
FROM (
  SELECT 'correct' AS impl, c.utid, c.tid, c.idx,
         p.origin + c.idx * p.bw AS origin_ns, c.cpu_ns,
         p.bw AS bw_ns, p.thr AS thr_ns
  FROM correct c CROSS JOIN p
  UNION ALL
  SELECT 'start_bucket', w.utid, w.tid, w.idx,
         p.origin + w.idx * p.bw, w.cpu_ns,
         p.bw, p.thr
  FROM wrong w CROSS JOIN p
)
WHERE cpu_ns <> 0
ORDER BY utid, idx, impl;
```

### 8.3 手算期望值（**未执行**，用于判别；数值是推导结果）

正确实现（逐桶求交）：

| impl | utid | idx | 桶区间 | cpu_ms | is_high | 说明 |
|---|---|---|---|---|---|---|
| correct | 1 | 0 | 1.2–1.3 | 4.0 | 0 | 8 ms 跨边界被切成 4+4 |
| correct | 1 | 1 | 1.3–1.4 | 4.0 | 0 | 同上，两半都 **< 5 ms** |
| correct | 1 | 3 | 1.5–1.6 | 6.0 | 1 | 真 spike |
| correct | 1 | 5 | 1.7–1.8 | 6.0 | 1 | 真 spike |
| correct | 2 | 1 | 1.3–1.4 | 100.0 | 1 | 300 ms 被切成 3×100 |
| correct | 2 | 2 | 1.4–1.5 | 100.0 | 1 | 同上 |
| correct | 2 | 3 | 1.5–1.6 | 100.0 | 1 | 同上 |
| correct | 2 | 34 | 4.6–4.7 | 50.0 | 1 | 200 ms 被窗口裁成 150，再切 50 |

错误实现（整段记起始桶，仍裁窗口）：

| impl | utid | idx | cpu_ms | is_high | 现象 |
|---|---|---|---|---|---|
| start_bucket | 1 | 0 | 8.0 | **1** | **幻影 spike**：正确结果该桶只有 4 ms，不该触发 |

若不裁窗口：`start_bucket / utid2 / idx34 = 200.0 ms`，该线程窗口内 CPU 总和从 450 ms 变 500 ms。

### 8.4 三组可判别的结论（这就是“反例”的作用）

| 断言 | correct | start_bucket | 用哪条检查 |
|---|---|---|---|
| utid1 的 episode 数 | **2**（idx3、idx5） | **3**（idx0 幻影） | Q2 逐线程计数 |
| utid2 第 1 个 episode 的桶数 / 墙钟 | **3 桶 / 300 ms** | 1 桶 / 100 ms | Q2 `n_high_buckets`、`dur` |
| 任何桶值 ≤ 100 ms | 成立 | 2 处违反（300、150） | **I1** 或 fixture 的 `violates_bucket_width` |
| Σ桶 = Σ裁剪时长 | 20 / 450 ms | 20 / 450 ms（**也成立**） | I2 —— **抓不到**，正因如此才必须看 I1/逐桶 |

**关键提醒**：总量守恒（I2）在“整段记账”下同样成立（utid1 20 ms、utid2 450 ms 完全一致），
所以**只验总量会漏掉这个 bug**。必须验 (a) 每桶 ≤ 桶宽、(b) 跨桶切分、(c) 阈值判定逐桶。
另外 8 ms 这种“总量一样、分布不同”的情况，连总量和 ep 总数都可能一致，
只有 `idx0=4 vs 8` 与幻影高桶能区分 —— 这就是上表第一行的价值。

## 10. 怎么验证“跨桶区间”和“安静间隔”

### 10.1 验证跨桶区间

| 方法 | 操作 | 通过条件 | 备注 |
|---|---|---|---|
| M1 逐区间切分 | 跑 Q4，看 `split_ok` | 全部 = 1，且 `max_segment_ns ≤ 100 ms` | 直接回答“这个 300 ms 区间被切成什么” |
| M2 逐桶上界 | 跑 Q3 `I1` | `violations = 0` | 单线程桶值 > 桶宽 = 物理不可能 ⇒ 整段记账/重叠/未裁剪 |
| M3 fixture 精确断言 | 跑 §8.2，对照 §8.3 | `utid1 idx0 = 4.0 ms`（不是 8.0）；`utid2 = 100/100/100 + 50/100` | **唯一能精确判别“起始桶”与“切分”的测试** |
| M4 换桶宽 | `bucket_ns` 100 ms → 50 ms（锚点不变）重跑 | 每个 100 ms 桶 = 覆盖它的两个 50 ms 桶之和 | 能抓“错桶/锚点错位”；**抓不到整段记账**（总量守恒，见下） |
| M5 换锚点 | `grid_origin` 平移 +50 ms 重跑 | 桶内质量在 100 ms 内**重新分配**，任何跨桶区间的总量不变 | 整段记账会把同一整块**整体搬家**（值恒定、常 > 100 ms），形态明显不同 |
| M6 独立来源 | 把 Q1 的 `runs` 改成 `FROM sched_slice`（去掉 `state` 条件）重跑 | 逐桶与 `thread_state` 完全相等 | 两条独立实现互证；该表不存在时此对照取消 |

**M4 的诚实说明**：`start_bucket` 总是把整段放进“包含 t0 的那个粗桶”里，
而细网格的起始桶也落在同一粗桶内，所以细桶求和仍等于粗桶值 —— M4 期望“相等”，
错误实现**也能通过**。因此 M4 只能查对齐/错桶，**不能**用来证明切分正确。
真正能判别的是 M2/M3（以及 M5 的形态差异）。

### 10.2 验证安静间隔

| 方法 | 操作 | 通过条件 |
|---|---|---|
| N1 补零完整性 | Q3 `I5` | `= 0`：每个线程每个桶都有一行（安静桶是显式 0） |
| N2 episode 内无安静桶 | Q3 `I3` | 严格模式下 `= 0`；非 0 说明间隔被吞 |
| N3 相邻 episode 间隔 | Q3 `I4` | `= 0`：相邻 episode 之间 ≥ 1 个安静桶 |
| N4 fixture 间隔断言 | §8.2 的 utid1：idx3 与 idx5 之间 idx4 = 0 | 正确实现输出 **2 个** episode；任何合并逻辑会给 1 个 |
| N5 参数语义 | 把 `min_quiet_buckets` 临时改 2 重跑 | episode 数只应减少或不变，且被合并的 episode 的 `n_quiet_inside > 0`；这说明放宽必须显式声明 |
| N6 空 vs 不存在 | Q1 的 `first_seen/last_seen` 为 NULL 的线程 | 其 0 桶标为“窗口内未观测到运行”，不算安静桶；有 sched 丢包时整体 UNKNOWN |

**N4 细节**：正确实现的 utid1 在被 1 个安静桶（idx4）隔开后必须是 2 个 episode。
如果有人用“高桶之间时间接近就合并”“episode 内桶数用 index 差代替”之类的写法，
会得到 1 个或多个错误区间 —— 这条 fixture 专抓安静间隔。

## 11. 如何下结论

### 11.1 支持 / 反驳“存在连续高 CPU spike”

| 观察 | 结论 |
|---|---|
| Q2 有 episode，且 Q3 I1–I4 全 0、I5 = 0、I0 > 0、stats 无丢包 | **PASS**：在给定 100 ms/5 ms 口径下存在这些 episode（仍不是因果） |
| Q2 无行，且 Q0 `[4]` > 0、I1–I5 全 0 | **PASS（否定）**：该窗口没有任何线程出现“连续 100 ms 桶 ≥ 5 ms”；但 3 ms 级突发不可见 |
| Q2 无行，但 Q0 `[4]` = 0 或 `-1` 截断命中窗口或 stats 有丢包 | **UNKNOWN**：没有可用 sched 数据 ⇒ 不能说“无 spike” |
| 只有把桶宽放到 500 ms 才出现 episode | 说明能量集中在更短时间尺度，**不是** 100 ms 口径下的连续 spike；不要改口径凑结论 |
| episode 只在窗口边界出现（censored） | 只能说“窗口边缘附近在耗 CPU，长度 ≥ X”，不能报持续时长 |

### 11.2 必须同时写出的边界

- **相关性 ≠ 因果**：episode 与业务掉帧/卡顿同窗只说明同时发生；
  要证明因果还需要该线程的 off-CPU/等待、帧时间标记、以及对照组（`SKILL.md` §5）。
- **口径限制**：`Running` 墙钟时间不含等待 CPU（Runnable）、不含 IO/锁阻塞；
  一个线程 100% Running 也可能是在自旋等锁，这需要 off-CPU/调用栈数据才能区分。
- **分辨率限制**：100 ms 桶内 3 ms 的突发不可见；阈值 5 ms = 5% 占空比，是灵敏度选择而不是事实。
- **进程边界**：UPID 42 只覆盖该实例；fork 出的子进程是另一个 UPID，不要合并
  （`01-counters.md`：PID 复用/进程重启按 UPID 区分）。
- **删除标定**：窗口边缘 episode 的长度是下界。

### 11.3 最有价值的下一步（按证据缺口选一条）

1. 若窗口边缘有 censored episode：把 `win_start/win_end` 各外扩 0.5 s 重跑，看 episode 是否延续。
2. 若要把“高 CPU”升级成“谁在耗”：对该 episode 窗口展开该线程的调用栈/采样
   （perf/`linux.perf`），或用业务侧标记（`01-counters.md` §3 的“应用侧标记”）对齐。
3. 若要判断是不是“卡在等锁/自旋”：看同线程 `Runnable`/`Sleeping` 与 waker 链，
   确认它不是被高优先级挤占（那种情况 Running 反而变少）。
4. 若怀疑“CPU 尖峰导致掉帧”：加帧完成时间标记后做同轴对照，并保留未加标记的对照采集
   （`06-quality.md` §2 的对照要求）。

## 附录 B：常见错误清单（自查）

1. 用 `ts` 的起始桶 + `SUM(dur)`：跨桶堆成幻影峰，桶值可 > 100 ms（§8）。
2. 不裁窗口：把窗口外的时长算进边界桶（utid2 从 450 → 500 ms）。
3. 不补零：安静桶缺行，episode 跨过安静间隔合并，`n_buckets` 还算错。
4. 用线程名做 pivot：同名线程合并，桶值与 episode 全错。
5. 用 PID 而非 UPID：PID 复用会把两个进程实例混成一个（`01-counters.md` §2）。
6. 把 `dur = -1` 当有限时长或当 0：末段要么虚高要么被判“无 spike”。
7. 用浮点秒做参数：`(win_end - win_start) / bucket_ns` 变成实数除法，桶数/边界全错。
8. 阈值用 `>` 而非 `>=`：5.0 ms 整的边界桶判定与题意不一致。
9. 忽略部分桶：窗口非桶宽整数倍时，末桶拿 5 ms 与 100 ms 桶比，条件不可比。
10. 把 `dur`（墙钟）当 CPU 时长报告；或把 episode 的 `dur` 说成“CPU 时间”。
11. 没检查 sched 数据就把“0 行”写成“没有 spike”。
12. 用总量守恒（I2）当唯一验收 —— 整段记账也守恒，抓不到 bug。
