# 手动 Perfetto UI

只在真实 `.pftrace` 实际存在对应数据时承诺视图。本候选未执行 UI 操作，以下是基于官方能力的手动指南，不是截图验收。

1. 打开 app.pftrace，找到应用进程及三个 worker thread。展开线程事件可见 lat.stage 与 compute_kernel。Slice 长度是墙钟；嵌套 compute 是子片段，不能加到父片段时长上。
2. 找到 `Request lifecycle` 自定义 Track：显示从输入到某一终态的生命周期。多个并发请求可以有同名 Track，通过详情中的 run_id/stream_id/request_id 区分。交接不是默认线程 BEGIN/END。
3. 选中线程上的 `lat.send` 或 `lat.receive`，检查 Flow 箭头及对应 link_id。无 Flow 的事件不由本 Skill 补箭头。必要时用 `12-flow-inspection.sql` 核对 source/target 和业务身份。
4. 展开 `lat.queue_depth.pre/infer/post` Counter；查看积压是否与慢请求窗口重合。Queue custom Track 则显示单次入队到出队的墙钟时长，二者不是同一指标。
5. SQL：用 render_sql.py 产生 SQL，再逐条贴进 Query。不要把含 `${CATEGORY}` 的模板直接当执行过的 SQL。10–14 是探索视图，综合完整性看 analysis.json/requests.csv。
6. `analyze.py` 输出 `ui-request-track.sql`，执行后 Add debug track → Slice，Timestamp=ts、Duration=dur、Name=name；单位保持 ns。只显示严格合格请求，失败/丢弃另看原生终态事件与 CSV。
7. 需要帧间折线时，采用 frame_intervals.csv 对应的真实输出间隔或 13-frame-intervals 的探索查询，Add debug track → Counter，ts 为纳秒，值 interval_ns/1e6 为 ms；按 run+stream 分开。不自动改变线性/阶梯渲染造成“连续测量”的错觉。
8. 同一 Trace 有 ftrace 时选中真正线程 Track 上的阶段，手动对齐 CPU/Thread State 或用 14-thread-overlay。对自定义生命周期 Track，不允许虚构唯一执行线程。

首版不输出完整 DAG critical path，也不把最长 Slice 涂红就宣布根因。多个分支/阶段重叠用实际 Flow 和业务等待条件解释。
